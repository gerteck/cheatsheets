\section{1. \underline{Performance Metrics}}

\subsection{Link Rate / Bandwidth / Capacity}
\begin{itemize}
    \item How many bits can be ``pushed'' onto a link per unit time. (Bandwidth)
    \item E.g. Cable: in Mbps, Fiber optics: $1 \sim 10$ Gbps, Ethernet: $3$ Mbps to $100$ Gbps
    \item Link rate related to transmission delay, or ``putting furniture into the moving van''.
\end{itemize}

\subsection{Throughput}
\begin{itemize}
    \item Throughput of a TCP/UDP flow. (End-to-End, includes propagation delay).
    \item How many bits communicated / pushed throughout entire routing path per unit time.
\end{itemize}

\subsection{End-to-End Delay}
\begin{itemize}
    \item \textbf{Components}: Processing delay + Queueing delay + Transmission delay + Propagation delay
	 \item Processing (time taken by router/devices to process packet header), Queueing (time packet waits in buffer before it is transmitted, due to congestion), propagation delay (time taken for bit to travel from one end of link to the other.). Transmission delay is the time it takes for physical layer at source to send all bits of packet onto transmission medium.
	 \item \textbf{Variables}: Bandwidth, packet size, distance, propagation speed, queue size.
    \item Example: A packet of $L$ bits sent over a link with rate $R$ bits/sec takes. 
\end{itemize}

\subsection{Other Metrics}
\begin{itemize}
\item \textbf{Reponse Time}: Time taken from request to response, aka \textit{round-trip time}, including server processing time etc. Traffic there and back may take different routing paths. Roughly 2x of end-to-end delay, but not exactly.
\item \textbf{Dropping Probability}, \textbf{Utilization}
\end{itemize}

\subsection{1.1 Packet Switching: Store-and-Forward}
\begin{itemize}
    \item A packet of $L$ bits sent on a link with rate $R$ bps takes:
    \[
        \text{Transmission delay} = \frac{L}{R} \quad \text{seconds to push out.}
    \]
    
    \item \textbf{Store-and-forward}: entire packet must be at router before transmit to next link.
    \item E.g. $L = 7.5$ Mbits, $R = 1.5$ Mbps: Transmission delay per link = $\frac{L}{R} = 5$ sec. For 3 links: total delay $= \frac{3L}{R} = 15$ sec
\end{itemize}

\subsection{1.2 Packet Switching: Statistical Multiplexing}
\begin{itemize}
    \item Bandwidth shared on demand, no fixed pattern of packets. This is the origin of \textbf{queuing delay}. (Input rate $>$ output rate).
    \item Statistical multiplexing $\rightarrow$ efficient use of link capacity. Packet switching is more efficient to share resources among users. (Statistical: arrival of packets non-deterministic)
    \item Contrast with TDM (Time Division Multiplexing):
    \begin{itemize}
        \item TDM: each host gets same slot in a revolving frame.
        \item Statistical multiplexing: bandwidth allocated dynamically as needed.
    \end{itemize}
\end{itemize}

\subsection{Packet vs Circuit Switching}
\begin{itemize}
    \item Example: For Link capacity of 1 Mbps, where each user requires 100 kbps when active, active 10\% of time.
    \begin{itemize}
	    \item \textbf{Circuit switching} $\Rightarrow$ supports 10 users
		 \item \textbf{Packet switching} $\Rightarrow$ with 35 users, probability $>10$ active simultaneously is $<0.0004$.
	 \end{itemize}
    \item \textbf{Pros of packet switching}: Great for bursty, asynchronous data, Resource sharing, No call setup required.
    \item \textbf{Cons of packet switching}: Excessive congestion $\rightarrow$ packet delay and loss, requiring protocols for reliability and congestion control.
\end{itemize}


\subsection{1.3 Single-Server Queueing Model (Abstract System)}
\begin{itemize}
    \item Model (to understand queueing delay): one server with infinite queue.
    \item Arrival rate: $\lambda$ (packets per second).
    \item Service rate: depends on server capacity (e.g., 1.5 Mbps).
    \item Average queue length and waiting time linked by Little’s Law.
\end{itemize}
\centerline{\includegraphics[width=0.6\linewidth]{littlesLaw}}

\subsection{1.4 Little’s Law}
\[
    L = \lambda W
\]
\begin{itemize}
    \item $L$: average number of customers in system
    \item $\lambda$: average arrival rate
    \item $W$: average sojourn time (time spent in system)
\end{itemize}
\textbf{Examples:}
\begin{itemize}
    \item SoC admits 1500 students per year, has 6000 students enrolled at any time. 
    \[
        W = \frac{L}{\lambda} = \frac{6000}{1500} = 4 \text{ years}
    \]
    \item If average queue length $=5$ packets and arrival rate $=100$/sec, then
    \[
        W = \frac{L}{\lambda} = \frac{5}{100} = 0.05 \text{ sec}
    \]
\end{itemize}


\section{2. \underline{Network Queueing \& Models}}


\subsection{2.1 Packet Flow: Arrival Pattern}
\begin{itemize}
    \item Arrival times: $t_i$; \quad Inter-arrival times: $T_i \equiv t_{i+1} - t_i$
    \item Model $T_i$s as independent, identically distributed (i.i.d.) random variable (r.v.) $T$
\end{itemize}
\centerline{\includegraphics[width=0.6\linewidth]{packetArrivalModel}}

\subsection{2.2 Probability Basics and Recap}
\begin{itemize}
    \item Random experiment: outcome cannot be determined in advance
    \item Sample space $S$: set of all outcomes; \quad Event $E \subseteq S$: occurs if $s \in E$
    \item Probability function $P(E):  \quad 0 \le P(E) \le 1, \quad P(S) = 1 $
\end{itemize}

\subsection{Random Variables (r.v.)}
\begin{itemize}
    \item Random variable $X$ is a \textbf{mapping}: maps each outcome $s \in S$ to real value
    \item Distribution function $F(x) = P(X \le x)$
    \item Continuous r.v.: exists pdf $f(x) = \frac{d}{dx}F(x)$
    \item Independence: $f_{X,Y}(x,y) = f_X(x) f_Y(y)$
    \item Expectation:
    \[
        E[X] = \int_{-\infty}^\infty x f(x) dx \quad \text{or} \quad E[X] = \sum_x x P(X=x)
    \]
\end{itemize}

\subsection{Exponential Distribution (Time between Intervals)}
\begin{itemize}
    \item $T \sim \text{Exp}(\lambda)$ with $\lambda > 0$: (note interarrival times cannot be negative).
    \[
        f(x) =
        \begin{cases}
            \lambda e^{-\lambda x}, & x \ge 0 \\
            0, & x < 0
        \end{cases}
    \]
    
    \item \textbf{CDF $F(X)$: probability that event occurs within time x}, $P(T \le x)$
    \item $F(x) = P(T \le x) = \int_{0}^{x} \lambda e^{-\lambda u}\,du =  1 - e^{-\lambda x}, \quad x \ge 0$
    \item \textbf{Memoryless}: $P(T > s+t \mid T > s) = P(T > t)$
    \item \textbf{Expectation: (E[T]: Time till next event)}
    \[
        E[T] = \int_{0}^{\infty} x \, \lambda e^{-\lambda x} \, dx
    \]
    Integration by parts:
    \[
        E[T] = \left[ -x e^{-\lambda x} \right]_{0}^{\infty} +
        \int_{0}^{\infty} e^{-\lambda x} \, dx
        = 0 + \frac{1}{\lambda} \Rightarrow \; E[T] = \frac{1}{\lambda}
    \]
    \item \textbf{Physical meaning of $\lambda$:} 
    \begin{itemize}
        \item $\lambda$ is the \emph{arrival rate} (arrivals per unit time), unit: $\text{time}^{-1}$ (e.g., per second).
        \item On average, $\lambda$ events occur per unit time, or the mean interarrival time is $1/\lambda$.
    \end{itemize}
\end{itemize}

\subsection{\underline{2.3 Modeling Packet Flow}}


\subsection{Packet Arrival / Inter-arrival Times (Poisson Process, T$\sim$Exp($\lambda$).)}
\begin{itemize}
    \item Inter-arrival times $T_i \sim \text{Exp}(\lambda)$, i.e. each inter-arrival time is an RV with rate $\lambda$.
    \item \textbf{Arrival pattern}: Poisson process (\# arrivals in an interval follow Poisn. distribn.)
    \item \textbf{Properties}: Memoryless $\Rightarrow$ starting time irrelevant, and \\
    Merging: Poisson($\lambda_1$) (combination) Poisson($\lambda_2$) $\Rightarrow$ Poisson($\lambda_1 + \lambda_2$)
\end{itemize}

\subsection{Service Time (Exponential / i.i.d.)}
\begin{itemize}
    \item Service time (processing time) of packet $i$: $S_i$, under fixed link rate.
    \item $S_i$ are i.i.d. with mean $E[S] = 1/\mu$.
    \item \textbf{Physical meaning of $\mu$}: \emph{service rate}, avg packets per unit time that can be handled
    \item Depends on link rate and packet size, as packet size may vary, hence, take average.
\end{itemize}

\subsection{\underline{2.4 M/M/1 Model} {\tiny M (Markovian Poisson arrival), M (Markovian memoryless service time), 1 (\# servers)  }}

\centerline{\includegraphics[width=0.8\linewidth]{mm1Model}}
\begin{itemize}
    \item Assumptions:
    \begin{itemize}
        \item Single server, infinite queue size, 
        \item Poisson \underline{arrivals rate $\lambda$}, Exponential \underline{service time rate $\mu$}
        \item Independent arrivals and service, FIFO service discipline
    \end{itemize}
    \item \textbf{Utilization $\rho$}| (\% time or probability of observation that server busy):
    \[
        \rho = \frac{\lambda}{\mu}, \quad \text{need } \lambda < \mu \text{ for stability}
    \]
\end{itemize}


\subsection{Birth-Death Process}
\centerline{\includegraphics[width=0.8\linewidth]{birthDeath}}
\begin{itemize}
    \item State Transition Diagram for M/M/1 System.
    \item System state $L(t)$ = (random) number of users in system.
    \item Transitions: $ i \to i+1 \text{ at rate } \lambda, \quad i \to i-1 \text{ at rate } \mu $
\end{itemize}

\subsection{Stationary Distribution (Long-term behavior of System)}
\begin{itemize}
    \item For a M/M/1 system, denote $\pi_i$ as \% time exactly $i$ packets in system (ie. server + queue) / probability $P=\{L=i\}$ of random observation of $i$ packets in system.
    \item $\pi_i= P(L=i) = (1-\rho) \rho^i$,  (follows a geometric distribution)
    \item $\pi_0 = 1-\rho$ (utilization), and $\sum_i \pi_i = 1$
\end{itemize}

\subsection{M/M/1 Results}
\begin{itemize}
    \item Avg. \# packets in system: $ E[L] = \frac{\rho}{1-\rho} $
    \item Avg. sojourn time (system delay): $ E[W] = \frac{1}{\mu - \lambda} $
    \item Avg. \# packets in queue: $ E[Q] = \frac{\rho^2}{1-\rho} $
    \item Avg. queueing delay of packets: $E[D] = E[W] - \frac{1}{\mu} $
	\item If $\lambda \ge \mu$, server keep up w. arrivals and queue grows without bound.  
	      In particular, $\lambda = \mu$ is unstable (graphically approaches vertical asymptote at $\lambda = \mu$):
	      \[
	        E[L] = \frac{\rho}{1-\rho} \to \infty, \quad
	        E[W] = \frac{1}{\mu - \lambda} \to \infty
	      \]
	      Stability requires $\lambda < \mu$ (i.e., $\rho < 1$). ($\lambda = \mu$ insufficient bc. randomness).
\end{itemize}

\subsection{2.6 Effective Bandwidth}
\begin{itemize}
    \item Physical link capacity: theoretical hardware processing limit (E.g. 10Mbps cable)
    \item \textbf{Effective bandwidth}: actual throughput achievable, given service quality constraints. E.g. for $\mu$ capacity of M/M/1 link:
    \item (utilization constraint of $\rho \le \hat{\rho}$ , low delay (delay bounded by  $D \le \hat{D}$, where $E[D] = \frac{\rho}{\lambda - \mu} $, low loss etc) .
\end{itemize}

\subsection{2.7 Statistical Multiplexing vs Time Division Multiplexing}
\begin{itemize}
	\item \textbf{Time Division Multiplexing (TDM)}: Each of k users given fixed fraction of link capacity $\mu/k$, regardless of idleness (wasted capacity).
    \item With $k$ streams, $\rho = \frac{\lambda}{\mu} = \frac{\lambda/k}{\mu/k} = \rho$ (same server utilization), but avg. sojourn time ($E[W]$) increased by $k$ times under TDM. Queue length ($E[Q]$) and total users ($E[L]$) also $k$ times larger
    \item \textbf{Statistical Multiplexing}: Multiple traffic streams share the common link dynamically, each flow sends when has data, link schedules packets one by one from queue, bandwidth allocated statistically (random arrivals), not deterministically. (e.g. M/M/1 FIFO queue model)
    \item Statistical better than TDM. (same utilization, average less delay, shorter queue).
\end{itemize}

\subsection{2.8 Variants of Queueing Models}
\begin{itemize}
    \item Multiple servers: M/M/2, Limited queue size: M/M/1/K
    \item Different service: M/M/1/LIFO, General distributions: M/G/1, G/M/1, G/G/1
\end{itemize}

\subsection{\underline{2.9 Burke’s Theorem}}
\begin{itemize}
	\item For \textbf{M/M/1 queue} in steady state with arrival rate $\lambda$ and service rate $\mu > \lambda$
    \item \textbf{Departure} process of form Poisson process of rate ($\lambda$)
    \item \textbf{Independence}: System size at time $t$ independent of past departure times
    \item Implication is that output of one M/M/1 queue can be treated as Poisson input for the next queue, simplifying analysis of multi-hop queueing systems.
\end{itemize}

\subsection{2.10 Tandem Queues}
\begin{itemize}
	\item \textbf{Tandem Queue}: System where jobs pass through multiple servers in sequence, one after another. Each server $i$ modelled as an M/M/1 queue with own service rate, and utilization of server $i$: $\rho_i = \lambda / \mu_i$
    \item Joint probability of no. of jobs in each subsystem (independent):
    \[
        P(L_1=j, L_2=k) = (1-\rho_1)\rho_1^j (1-\rho_2)\rho_2^k
    \]
\end{itemize}

\subsection{\underline{2.11 Jackson Network of Queues}}

\begin{itemize}
	\item Firstly, a \textbf{Acyclic Network with Probabilistic Routing} is where jobs arrive at a network node, and choose next node randomly. Poisson property preserved, departures remain independent Poisson processes (Poisson splitting)
    \item \textbf{Jackson Network}: Network of queues (e.g. M/M/1) with probabilistic routing  between servers $P_{ij}$, and can be acyclic or have feedback (cyclic).
\end{itemize}
\centerline{\includegraphics[width=1\linewidth]{jackson}}	    
\begin{itemize}
	\item \textbf{Solve Jackson Network}, Burke's theorem merge \& split of Poisson still apply. 
	\item \textbf{Two-step procedure}: determine utilization $\rho_i$ for each server, and product form solution.
    \item \underline{Effective arrival rate}: $\lambda_i$ at server $i$: $\lambda_i = r_i + \sum_{j=1}^n \lambda_j P_{ji} $ ($r$ is outside arrival)
    \item In matrix form: $\lambda = r + \lambda P \quad \Rightarrow \quad \lambda = r (I-P)^{-1}$
    \item Product form solution: $P(L_1=l_1, \dots, L_n=l_n) = \prod_{i=1}^n (1-\rho_i)\rho_i^{l_i}$
\end{itemize}

\section{3. \underline{Resource Allocation}}
\subsection{3.1 Queues - Delay (sojourn $ E[W] $), capacity (service $\mu$), arrival ($\lambda$)}

\begin{itemize}
	\item \textbf{Average waiting (sojourn) time} in an M/M/1 queue is $ E[W] = \frac{1}{\mu - \lambda}$, where $\mu$ is the service rate (i.e. called capacity) while $\lambda$ is arrival rate. More capacity (higher service rate) means higher throughput, and lower delay. 
	\item \textbf{Max throughput $\lambda$} for a given delay requirement $ E[W] $ would be $\lambda = \mu - \frac{1}{E[W]}$, determined by service rate.
	\item \textbf{Physical Interpretation of $\lambda$}: Here, because we want to guarantee some delay requirement, for a given service rate / capacity, the total throughput has to be bounded. `Arrival rate' $\lambda$ (throughput) here is instead admission control, where system limits the incoming rate of incoming flow to guarantee latency. Not the senders decision (e.g.UDP), but instead, it is a resource allocation problem.
\end{itemize}

\subsection{3.2 Motivation of Resource Allocation}
 Internet provides \textbf{best-effort} service. Network resources (bandwidth, buffer space, processing time) are limited.
 Hence, problem to allocate resources fairly and efficiently across competing flows. Tradeoff between \textbf{efficiency} (maximize utilization) and \textbf{fairness} (avoid starvation).

\subsection{Resource Allocation in Networks}

\textbf{General Utility Perspective}
\centerline{\includegraphics[width=1\linewidth]{utility}}	    

\textbf{Metrics}: \textit{Throughput}: average rate of successful packet delivery, \textit{Delay}: time from packet arrival to departure, 
	\textit{Fairness}: how equally bandwidth is shared among flows, \textit{Loss rate}: fraction of packets dropped due to congestion.

\subsection{\underline{3.3 Max-Min Fairness}}
Idea of fairness where low demand users get what they need, large demand users share the rest equally (fair allocation).
\begin{itemize}
	\item \textbf{Max-min fair}: A feasible allocation max-min fair iff cannot increase anyone's rate without decreasing someone else's rate that is smaller or equal.
	\item Also exists, typically unique. Ensures no flow is starved. 
	\item \textbf{Flow's Bottleneck Resource}: A resource $r$ is a bottleneck for flow $i$ if $r$ is saturated (fully used) and flow $i$ has max rate among all flows using resource $r$ (both conditions).
	\item Note: \textbf{weighted ($\phi$) flow}: For flow bottleneck resource for weighted max-min, flow $i$ has max (\textbf{normalized}) rate among all flows. (Not max absolute rate).
	\item \textbf{Theorem}: With infinite demand, a max-min fair allocation iff every flow $i$ has a bottleneck resource $r$ .
\end{itemize}

\subsection{Water-Filling Algorithm}
The water-filling algorithm is a practical way to compute max-min fair allocations.  
\begin{itemize}
	\item \textbf{Flow} = bucket, \textbf{water} = system resources
\end{itemize}
Each flow’s demand is “bucket” with volume $d_i$ and system resources as “water” poured until capacity is exhausted.  

\begin{itemize}
	\item \textbf{Step 1:} Represent each demand $d_i$ as a bucket (capacity limit).
	\item \textbf{Step 2:} Start filling all buckets equally (same rate for each flow).
	\item \textbf{Step 3:} When a bucket demand full (or the flow's bottleneck link saturates - flow hits bottleneck), stop filling; continue distributing remaining capacity among other unfinished buckets. (I.e. stop partial allocations for certain flows that have been constrainted by their bottleneck link).
	\item \textbf{Step 4:} Continue until all capacity is allocated or all demands are satisfied.
\end{itemize}

\subsection{Weighted Max-Min Fairness}
Extension of the water-filling algorithm with weights $\phi_i$. Weighted fairness generalizes the idea to assign priorities via weights.
\begin{itemize}
	\item Buckets now have different \textit{widths} proportional to $\phi_i$ (instead of equal).  
	\item Each flow’s rate grows proportionally to its weight until either demand is satisfied or capacity is exhausted.  
	\item No user receives more than their demand. Remaining resources are split proportionally.
\end{itemize}

\subsection{Implementation of Water-Filling Algorithm}
We do not know in advance which resource will be the next bottleneck, or at what ``water level'' capacity will be fully utilized.
    \begin{enumerate}
      \item Start by increasing all flows equally (or proportionally if weighted).
      \item For each resource, check its capacity constraint $\sum_{i \in R} x_i \leq C_R$.
      \item The first resource that saturates defines the next bottleneck; flows using this resource are then capped.
      \item Remove the capped flows from further consideration and continue filling the others.
    \end{enumerate}
 This can be executed locally:
    \begin{itemize}
      \item Each router enforces per-flow constraints on its outgoing link.
      \item Flows naturally converge to a max-min fair allocation since no flow can exceed its bottleneck capacity.
    \end{itemize}


\subsection{Implementation of Max-Min Fairness}
In practice, implementing max-min fairness in the Internet is challenging due to the lack of centralized control.  
Routers must make local scheduling decisions in a distributed fashion.

\begin{itemize}
  \item \textbf{Challenge:} No single global controller; each router only sees its local queues.
  \item \textbf{Classical solutions:}
    \begin{itemize}
      \item GPS (Generalized Processor Sharing): theoretical ideal where packets are served bit-by-bit in perfect proportion to their weights.
      \item WFQ (Weighted Fair Queueing): practical approximation of GPS, where each packet is stamped with a virtual finish time and routers serve packets in increasing finish-time order.
    \end{itemize}
  \item \textbf{Modern solution:} SDN (Software Defined Networking) provides centralized or global control of flows, enabling explicit allocation strategies across the network.
\end{itemize}

\section{4. \underline{Software Defined Networking (Design Principles)}}

\textbf{Software Defined Networking (SDN)} is a new approach to implement and manage networks based on 
\underline{fundamental principles} that impact both network design and the pace of innovation.  
Traditional networking has been successful, but has significant limitations:
\begin{itemize}
  \item Closed and proprietary equipment $\rightarrow$ little room for innovation.
  \item Over-specified protocols $\rightarrow$ slow standardization and evolution.
  \item Complex, hard-to-manage systems $\rightarrow$ high operational costs and frequent outages.
\end{itemize}

SDN proposes to solve these challenges by separating the \textbf{control plane} and the \textbf{data plane}, 
centralizing control, and enabling programmability.

\subsection{4.1 Why SDN? Problems with Traditional Networking}
\begin{enumerate}
  \item \textbf{Tremendous success, but only at the edge:}  
  The Internet evolved from research to global infrastructure, great innovation at the 
  application layer (7) (web, VoIP, P2P, etc.), but very little innovation inside the network.

  \item \textbf{Inside the network:} Closed equipment where hardware and software bundled vendor specific interfaces limit flexibility. Over specified, Protocol standardization is slow $\rightarrow$ decades to evolve routing protocols. Innovation only up to equipment vendors, so slow.

  \item \textbf{Networks are hard to manage:} Operating costs exceed hardware costs. Human error largest cause of outages. Network software is massive and buggy (e.g., routers with 20M+ lines of code).

  \item \textbf{Networking lags behind other systems:} (Compute, Storage, Networks) Computation and storage have been virtualized, enabling rapid innovation. Networking, however, is still highly manual and primitive in management. - New control requirements just lead to greater complexity (isolation, packet processing, payload analysis). 
\end{enumerate}

\subsection{Networking as a Discipline}
Unlike OS or DB systems, networking has not converged around basic principles or abstractions.  
Instead, it is taught as a \textit{``bag of protocols''}.  
SDN tries to extract simplicity using modular abstractions, much like programming evolved 
from machine code to higher-level languages with abstracted functions etc.

\subsection{The Network Control Problem}
The traditional (complex) control problem is:  
\begin{itemize}
  \item Compute forwarding tables for each device.
  \item Operate without reliable communication guarantees.
  \item Operate within given distributed routing protocols (e.g. OSPF, RIP, BGP).
\end{itemize}
This distributed complexity makes it difficult to innovate or manage.

\subsection{4.2 Control Plane vs. Data Plane}
Two key functions of router and switch at the core: Routing algorithms/protocol vs. Forwarding datagrams.
\begin{itemize}
  \item \textbf{Control Plane:} Decides how packets should be forwarded (routing, traffic engineering, firewalling).  
  Operates at slower time scales (per-event basis).
  \item \textbf{Data Plane:} Forwards packets based on control plane instructions.  
  Operates at very fast timescales (per-packet basis).
\end{itemize}

\subsection{Principle 1: Disaggregation}
Traditional networking devices bundle control and data plane tightly.  
\textbf{Disaggregation} separates them via open interfaces:
\begin{itemize}
  \item Commodity switches handle packet forwarding (data plane).
  \item Control plane software can run independently, possibly from different vendors.
  \item \textbf{Forwarding Abstraction}: need to define, as a general-purpose way for control plane to tell data plane to forward pkts in specific way.
  \item E.g.: \textit{OpenFlow} defines \textbf{flow rules} (match-action pairs) as forwarding abstraction.
\end{itemize}

\subsection{Principle 2: Centralized Control}
Instead of every router running its own control software:
\begin{itemize}
  \item A logically centralized controller has a global network view.
  \item Simplifies management compared to distributed routing (contrast: OSPF’s 244 pages vs Dijkstra’s 4 pages).
  \item Physically centralized controllers may have fault-tolerance issues, hence the need for logically centralized 
  but physically distributed implementations.
\end{itemize}

\subsection{Principle 3: Programmability}
\begin{itemize}
  \item Control shift: vendors $\rightarrow$ operators $\rightarrow$ users.
  \item Networks programmable via high-level policies. Debug, verification easier.
  \item Enables rapid innovation and new services (e.g., network slicing in 5G, dynamic security policies in data centers).
\end{itemize}

\subsection{4.3 Benefits of SDN}
\begin{enumerate}
  \item \textbf{Easier management:}  
  Network policies are written at a high level; low-level configurations are handled by the controller.
  \item \textbf{Faster innovation:}  
  Network control software evolves independently from hardware. Disaggregation shifts control from vendors to operators or open source that build networks to meet their users needs.
  \item \textbf{Cheaper infrastructure:}  
  Commodity (standardized) forwarding devices replace expensive proprietary hardware.
  \item \textbf{New use case:} Data center virtualization, traffic engineering, dynamic QoS...
\end{enumerate}

\subsection{4.4 Abstraction Concepts}
These 3 principles modularize the \textbf{network control problem} into something similar to OS computation abstractions:
\begin{itemize}
  \item \textbf{Specification abstraction:}  
  Control applications specify desired behavior without worrying about implementation.
  \item \textbf{Distribution abstraction:}  
  Shields applications from distributed system complexity, presenting a logically centralized view..
  \item \textbf{Forwarding abstraction:}  
  Provides a generic interface to define how packets should be forwarded (e.g., OpenFlow).
\end{itemize}

SDN makes networks easier to program, easier to manage, and cheaper to build, while enabling 
faster innovation and richer functionality.

\subsection{4.5 Recap: Core Principles of SDN}
SDN is built on three core design principles that aim to simplify and modularize the control of large-scale networks:
\begin{enumerate}
  \item \textbf{Separation of Control Plane and Data Plane} – Network devices focus only on packet forwarding (data plane), while decision-making logic (control plane) is moved to a separate controller.
  \item \textbf{Logically Centralized Control} – A centralized controller maintains a global view of the entire network, enabling coherent and optimized control decisions.
  \item \textbf{Programmability} – The controller exposes APIs that allow applications and operators to program the network dynamically, enabling automation, customization, and rapid innovation.
\end{enumerate}

Each principle leverages set of \textbf{abstractions} to network control complexity:
\begin{itemize}
  \item \textbf{Specification abstraction} – Allows applications to express \textit{what} behavior is desired, without specifying \textit{how} it is implemented.
  \item \textbf{Distribution abstraction} – Presents a logically centralized view, hiding the distributed nature of devices and controllers.
  \item \textbf{Forwarding abstraction} – Defines how the control plane communicates forwarding behavior to the data plane (e.g., OpenFlow rules).
\end{itemize}

\end{itemize}
Companies may serve customers in different countries, needing to adhere to local data laws. SDN enables enterprises to replace expensive MPLS circuits w. cheaper broadband or 5G links while maintaining performance guarantees.

\subsection{5.3 OpenFlow API (Forwarding Abstraction)}
\textbf{Standard interface} btw. control plane (SDN controller) and data plane (switch). 
\textbf{OpenFlow}: foundational protocol, controller communication (how to process packets) w. forwarding devices (switches, routers). 
\begin{itemize}
  \item \textbf{Open southbound API:} Enables ext software control over device forwardg tables.
  \item \textbf{OpenFlow switch:} Implements packet-matching and action-execution pipelines.
  \item Each switch has set of \textbf{Flow Tables}. Flow Entry has \textbf{Match fields} (conditions on header/pipeline fields (e.g., IP, TCP port)), \textbf{Priority} (on multiple entry matches), \textbf{Instruction set:} (actions to perform - forward, drop, or send to controller).
  \item A packet is processed through one or more flow tables. Matching rules accumulate an \textbf{action set}, which executes once processing is complete.
  \item Default “table-miss” entry defines for unmatched packets (e.g. send to controller)
\end{itemize}

\subsection{5.4 Open Network Operating System (Specification Abstraction)}

\textbf{ONOS}: distributed system, open-source \textbf{SDN controller} developed by the Open Networking Foundation (ONF).
\begin{itemize}
  \item \textbf{Specification abstraction (northbound APIs):}  
  Apps can query network state, define intents (high-level connectivity goals), or request packet interception w/o implementation details.
  \item \textbf{Distribution abstraction (core services):}  
  Presents logically centralized view by syncing state across distributed controller cluster.
  \item \textbf{Forwarding abstraction (southbound interface):}  
  Communicates with devices using protocols such as OpenFlow or NETCONF.
\end{itemize}

\centerline{\includegraphics[width=1\linewidth]{ONOS}}
\textbf{ONOS Architecture:} \textit{Northbound Interface (NBI)}, APIs used by apps to query topology, intercept packets, control forwarding behavior. \textit{Distributed Core} maintains network state using a scalable key/value store (\textit{Atomix}), ensuring high availability and consistency. \textit{Southbound Interface (SBI)}, plugin-based interface for different device protocols and drivers.

\textbf{ONOS programming constructs:} \textit{Intent:} High-level general policy (e.g. connect Host A - Host B w. 10 Mbps guarantee). \textit{Flow Objective:} Mid level, device agnostic rule translating intent to device-specific logic. \textit{Flow Rule:} Low-level hardware rule installed in device tables (e.g., OpenFlow entries).

\textbf{ONOS (Network Operating System) as a horizontally scalable cloud application}: has set of loosely coupled subsystems, often associated with micro-service architecture, coordinating distributed network devices, like how traditional OS manages hardware resources.

SDN abstracts the network into three layers: \textbf{Apps} that express high-level policies via APIs, \textbf{Control Plane (Controller)} that implements logic, optimization, and state management and \textbf{Data Plane (Devices)} that executes rules defined by controller. SDN transforms rigid networks to open programmable infrastructures.

\section{6.  \underline{SDN - P4 Programming Language}}

\subsection{6.1 What is P4}
\begin{itemize}
\item \textbf{P4} is a programming language for controlling packet forwarding planes in networking devices, such as routers and switches.
\item \textbf{Domain-specific} language with constructs optimized for network data forwarding. Open source. P4: Programming Protocol-Independent Packet Processors.  (i.e. domain is network packet processing)
\end{itemize}

\subsection{Why P4}
\begin{itemize}
  \item \textbf{Limitation of traditional switches:} Fixed-function ASICs (app-specific integrated circuits) can only process a pre-defined set of protocols (e.g., Ethernet, IPv4, TCP). Any new header format or protocol change requires new hardware. Slow innovation cycle, standardization, ASIC redesign take years.
  \item \textbf{Limitations of OpenFlow}: OpenFlow gives standard API for programming behavior of switches (remote control), but only supports fixed set of header fields (e.g. TCP, VLAN). New protocol (e.g. QUIC, custom headers) means must update OpenFlow standard and hardware vendors.
  \item Control over flow table rules, but none over packet type, packet parsing, processing inside switch. 
\end{itemize}

\textbf{Goal of P4:}
\begin{itemize}
  \item \textbf{Program the data plane itself}, and not just configure flow rules.
  \item Define new packet header formats, parsing logic, match-action tables, and actions.
  \item Enable switches to process any kinds of packets, support protocol evolution with need for hardware redesign, acheiving protocol independence (e.g. no assumption on IPv4, TCP, etc.)
\end{itemize}

P4 defines the data plane pipeline, can describe fast pipelines (e.g. ASIC, FPGA) and slower ones (e.g. SW switch). Good for both programmable, fixed-function switches. Defines contract btw. control plane and data plane for runtime control.

\centerline{\includegraphics[width=0.8\linewidth]{P4PorFixed}}


\subsection{6.2 P4 Logical Pipeline: Programmable Match–Action Pipeline}
Every P4-based switch implements a \textbf{logical pipeline} of match–action tables that process packets at line rate.

\[
\text{Input Packet} \rightarrow \text{Parser} \rightarrow \text{Ingress Tables} \rightarrow \text{Traffic Manager} 
\]
\[
 \text{Traffic Manager} \rightarrow \text{Egress Tables} \rightarrow \text{Deparser} \rightarrow \text{Output Packet}
\]

\begin{itemize}
  \item \textbf{Parser:} Extracts header fields (Ethernet, IP, etc.) using a finite-state machine.
  \item \textbf{Ingress Pipeline:} Match–action stages that determine forwarding or modification.
  \item \textbf{Traffic Manager (TM):} Handles queuing, buffering, and replication (typically fixed-function but configurable).
  \item \textbf{Egress Pipeline:} Processes packets before transmission (e.g., tagging, metering).
  \item \textbf{Deparser:} Reassembles headers and payloads into a valid packet.
\end{itemize}

Parser “reads” packet, tables “decide” what to do, deparser “writes” final packet.

\centerline{\includegraphics[width=0.8\linewidth]{programmableMatchActionPipeline}}


\subsection{6.3 Formalization: (PISA) Protocol-Independent Switch Architecture}
\textbf{PISA} is a \textbf{logical reference model}, defines the standard logical architecture that programmable data planes follow.

\begin{itemize}
  \item Provides a vendor-neutral abstraction for packet processing, defining programmable blocks: \textit{parser}, \textit{ingress}, \textit{egress}, and \textit{deparser}. It allows the same P4 program to be compiled for different hardware targets.
  \item \textbf{Benefits:} Hardware independence, program can run on different vendor devices. Clean abstraction of logical packet processing from physical implementation. Faster innovation, new protocols, header fields can be supported instantly.
\end{itemize}

\centerline{\includegraphics[width=0.8\linewidth]{PISA}}

\subsection{6.4 P4 Architecture and Targets}
\textbf{Mapping from Logical to Physical}: P4 still needs to account for different chips implementing different physical pipelines. Hence, allows for vendor-specific logical pipelines, through different architectures, evolve from P4$_{14}$ to P4$_{16}$. P4 separates concepts of \textbf{architecture} and \textbf{target}:

\begin{itemize}
  \item \textbf{Architecture:} Logical model / interface defining programmable components.
  \item \textbf{Target:} Specific hardware implementation running the compiled P4 program.
	\item Concept of an architecture defines what target hardware supports. P4 compiler translates logical design from P4 source to what fits physical chip architecture targeted.
\end{itemize}

\textbf{Common Architectures:}
\begin{itemize}
  \item \textbf{V1Model:} Basic architecture used in software switches like \texttt{bmv2}.
  \item \textbf{PSA (Portable Switch Architecture):} A standardized, general-purpose model.
  \item \textbf{PNA (Programmable NIC Architecture):} For smart network interface cards.
\end{itemize}

\textbf{Common Targets:}
\begin{itemize}
  \item \texttt{bmv2} (Behavioral Model v2) – software switch for development and testing.
  \item Intel Barefoot Tofino ASIC – high-performance programmable hardware switch.
\end{itemize}

\centerline{\includegraphics[width=1\linewidth]{P4Architectures}}

\subsection{6.5 Writing a P4 Program: A Practical Look}

A P4 program for the \texttt{V1Model} architecture follows a well-defined structure that corresponds to the programmable match--action pipeline.

\begin{itemize}
  \item \textbf{Includes \& Definitions:}  
  The program begins by including the core P4 libraries and the architecture model file (e.g., \texttt{v1model.p4}).  Also defines \textit{Packet headers} (e.g. Ethernet and IPv4, and \textit{Metadata}, both standard (e.g., \texttt{ingress\_port}) and user-defined.
    \item \textbf{Parser:} Implements a finite-state machine that reads incoming packets and extracts relevant header fields to identify the packet type.
  \item \textbf{Control Blocks (Ingress/Egress):}  
  The core logic of packet processing is defined here as a series of match--action tables.
  Each table specifies:
  \begin{itemize}
    \item \textbf{Key:} Field(s) to match on (e.g., \texttt{ipv4.dstAddr} using longest-prefix match).
    \item \textbf{Actions:} Possible operations to perform (e.g., \texttt{ipv4\_forward}, \texttt{drop}).
    \item \textbf{Size:} Maximum number of table entries allowed.
  \end{itemize}
  Actions themselves are defined as procedures that manipulate headers or metadata, such as setting \texttt{egress\_port} or decrementing the \texttt{TTL}.

  \item \textbf{Deparser:}  Reassemble modified headers, payload into packet for transmission.
  \item \textbf{Instantiation:}  Last, all components (\textit{parser, ingress, egress, deparser}) wired together to form full logical pipeline. 
\end{itemize}

\noindent
Overall, P4 program describes logical behavior of packet processing from parsing headers, making forwarding decisions, to rewriting and emitting packets, mapped to the architecture’s programmable pipeline.



\subsection{6.6 P4Runtime and Control–Data Plane Interaction}
\begin{itemize}
\item \textbf{Data Plane:} Executes the P4 program, processes each packet according to installed table entries.
\item \textbf{Control Plane:} Runs externally (e.g., ONOS, Ryu, or custom controller). It inserts, updates, and deletes entries in match–action tables. Uses the \textbf{P4Runtime API} to communicate with the data plane.
\item \textbf{P4Runtime:} A standard, gRPC-based API between the control plane and P4 devices. It allows runtime configuration, counter reading, and table management. Makes P4 switches vendor-independent and interoperable.
\item \textit{Example:} The control plane can install a routing rule (destination prefix → output port) in a P4 switch using P4Runtime.
\end{itemize}



\subsection{6.7 Real-World Constraints and Considerations}

\begin{itemize}
  \item \textbf{Hardware limits:} P4 targets have finite memory and pipeline stages.
  \item \textbf{Limited arithmetic:} Only simple operations (add, shift, subtract) are allowed to maintain line-speed.
  \item \textbf{Offload to control plane:} Complex computations can be sent to CPU if needed.
  \item \textbf{Compiler mapping:} P4 compilers optimize logic based on the hardware’s capacity.
\end{itemize}


\subsection{6.8 Example: IPv4 Router in P4}
\begin{itemize}
\item \textbf{Parser:} Extract Ethernet and IPv4 headers.  
\item \textbf{Ingress Table:} Match destination IP (LPM) $\rightarrow$ next-hop MAC + output port.  
\item \textbf{Action:} Rewrite MAC, decrement TTL, forward.  
\item \textbf{Control Plane:} Installs and updates routing table entries at runtime.
\item \textbf{Result:} A fully functional IPv4 router implemented purely in P4 — extendable to other protocols (e.g., IPv6, MPLS) without hardware change.
\end{itemize}


\subsection{6.10 P4 Summary and Key Takeaways}

\begin{itemize}
  \item P4 introduces true \textbf{data plane programmability}.
  \item PISA provides a universal, logical model for switch pipelines.
  \item \textbf{P4Runtime} bridges control and data planes via a vendor-neutral API.
  \item Tools like \texttt{bmv2} and Mininet enable software experimentation.
  \item \textbf{Mindset:} Move from configuring fixed hardware to programming network logic directly. Enables networks to evolve as fast as software.
\end{itemize}

\section{7. \underline{Internet Interconnection}}

\subsection{7.0 The Internet}
The Internet is fundamentally a \textbf{network of networks}. These networks are organized, interconnected, and governed by both technical and business relationships. Focus on three key components:
\begin{enumerate}
  \item \textbf{Autonomous Systems (AS):} the basic unit of Internet organization.
  \item \textbf{Internet Peering:} bilateral interconnection through business relationships.
  \item \textbf{Internet Exchange Points (IXP):} multilateral interconnection for efficient traffic exchange.
\end{enumerate}

Internet interconnection defines how ASes cooperate \& compete to maintain global connectivity, shaped by technical routing policies and commercial incentives. \textbf{Inter-domain routing protocols}, particularly the Border Gateway Protocol (BGP), enforces these policies across the global Internet.


\subsection{7.1 Autonomous Systems (AS)}
\begin{itemize}
\item \textbf{Autonomous System (AS)} is a collection of routers operated under a single administrative domain that shares a consistent routing policy.
\item Each AS is uniquely identified by an \textit{Autonomous System Number (ASN)}, which is allocated by the \textbf{Internet Assigned Numbers Authority (IANA)} through one of the five \textbf{Regional Internet Registries (RIRs)}.
\item Public AS databases include \texttt{db-ip.com/asn} and \texttt{peeringdb.com}.
\item An organization, such as an ISP, corporation, or university, may manage multiple ASes. Each AS determines which other networks to interconnect with,
which routing policies to apply, and how to manage internal routing. ASes use a common internal routing protocol and appear as single entities in inter-domain routing.
\item \textbf{Logical Unit}: AS is like a unit of network organization, with defined routing policy and networks.
\end{itemize} 

\subsection{7.2 Internet Hierarchy and Structure}
The Internet has a loosely hierarchical structure:
\begin{itemize}
  \item \textbf{Tier-1 ISPs}: At the \textbf{core}/top, few large and globally connected. (e.g., AT\&T, Level 3, Sprint, NTT). Peer with one another in full mesh, do not pay for transit.
  \item \textbf{Tier-2 ISPs} have national or regional coverage, purchasing transit from Tier-1 ISPs while also peering selectively.
  \item \textbf{Stub ASes}, such as universities or corporate networks, connect to one or more upstream providers and do not provide transit for others.
\end{itemize}

Internet Service Providers and ASes:
\begin{itemize}
\item \textbf{ISP}: provides internet access, owns and operates one or more ASes.
\item Content providers like Google have also developed private global networks that often bypass traditional Tier-1 ISPs via direct peering and IXPs. The hierarchical view is thus flattening as more large networks interconnect directly.
\end{itemize}

\subsection{7.3 Business Relationships Between ASes}
AS interconnection is primarily governed by economics and mutual agreements rather than a central authority. Two dominant business models exist:
\begin{enumerate}
\item \textbf{Customer–Provider Relationship}: \textbf{Customer} pays \textbf{provider} for Internet access and global reachability. Provider offers transit services, forwards traffic btw. customer and rest of Internet. For forwarding, traffic always flows \textit{upstream} (from customer to provider). Customer does not carry transit traffic between providers (if multi-homed).

\begin{itemize}
\item Some customers \textbf{multi-homed}, connect to multiple providers for redundancy/reliability/load balancing. They must ensure traffic from one provider not transited to other (bc. no incentive to do so).
\end{itemize}

\item \textbf{Peer-to-Peer (Settlement-Free Peering)}: Two ASes may establish p2p relationship, interconnect directly to exchange traffic between their customers. Peers do not transit traffic to third parties, generally do not pay each other. \textit{Settlement-free peering} reduces upstream transit costs and improves latency.

\begin{itemize}
\item Peering policies vary: providers selectively peer based on traffic ratios, geographic presence, network scale. E.g. Verizon policy requires balanced traffic exchange (below 1.8:1 ratio), presence across multiple geographic regions, minimum interconnection capacity (e.g., OC-192 in US).
\end{itemize}
\end{enumerate}

\subsection{7.4 Transit, Non-Transit ASes, Valley-Free Property}
\begin{itemize}
\item \textbf{Transit ASes} provide connectivity between their customers and other networks, often operating as ISPs.
\item  \textbf{Non-transit ASes}, by contrast, connect only to their own upstream providers without carrying traffic for others. Most enterprise networks, universities (e.g., NUS), and content networks fall under this category. (Multi-homed, but don't carry traffic for and between upstream providers).
\item \textbf{Valley-Free Property}: A routed network with no traffic flow valleys for any source-destination inter-domain routing path pair has valley-free routing, reflecting economic hierarchy. Traffic flows \textbf{uphill} from a customer to a provider, may traverse one \textbf{peer-to-peer} link, and flows \textbf{downhill} from provider to customer. Traffic does not dip into a valley (e.g. dual-homed customer), through a route leak.
\item Invalid paths such as provider to customer to peer, or peering to provider, violate business incentives and are filtered by routing policies.
\end{itemize}

\centerline{\includegraphics[width=1\linewidth]{valleyFree}}

\subsection{7.5 Tier-1 ISPs, Internet Exchange Points (IXPs), Flattening Internet}
\begin{itemize}
\item \textbf{Tier-1 ISPs} at top of Internet hierarchy. Reach entire Internet solely through settlement-free peering, no upstream providers. 10–12 such ASes exist worldwide (e.g., AT\&T, Sprint, Level 3). Form full-mesh peering topology ensures complete reachability.
\item \textbf{Internet Exchange Point (IXP)} provides shared switching fabric, enables multiple ASes to interconnect efficiently at single physical location. Promotes local traffic exchange, reduce latency and upstream transit costs.
\item Many regional ISPs, content providers rely on IXPs to peer directly instead of route through upstream transit providers.
\item Internet becoming increasingly \textbf{flat}. Content giants (Google, Amazon) operate private backbones, directly peer at IXPs or regional ISPs, bypass Tier-1 providers. Improves end-user latency and reduces reliance on traditional transit services.
\end{itemize}

\subsection{7.6 Peering Dilemmas and Policies}
\begin{itemize}
  \item \textbf{Peering Advantages}: reduced transit costs, better performance, essential connectivity to parts of the Internet. 
  \item \textbf{Peering Challenges}: Peers are often competitors, agreements require periodic renegotiation. Traffic imbalances or asymmetric benefits may lead to disputes.
  \item Consequently, peering arrangements are typically confidential and governed by private agreements or published criteria.
  \item \textbf{Peering Dispute \& Impact}: 2005, Level 3 (AS3356) and Cogent (AS174). Level 3, a major Tier-1 provider with over 49 K on-net prefixes, accused Cogent, a fast-growing underdog, of traffic imbalance. Disconnected Cogent on 5 Oct 2005, cut off traffic between two. Around 4.3\% of global prefixes became unreachable, affecting about 1\% of visible ASes. High-profile victims included \textit{The Washington Post}, \textit{CNET Networks}, and the U.S. Department of Health and Human Services. Under public and political pressure, Level 3 restored connectivity two days later.
\end{itemize}

\section{8. \underline{Inter-Domain Routing and Policy}}
\subsection{8.1 Inter-Domain Routing}
The Internet can be viewed as a `network of networks', consisting of over 50,000 Autonomous Systems (ASes) and millions of routers supporting more than 200,000 IP prefixes. 

\begin{itemize}
	\item \textbf{Inter-domain routing}: involves connecting distinct administrative domains, each with its own policies and operational objectives.
    \item \textbf{Challenges for inter-domain routing protocol}:
\begin{itemize}
	\item  \textbf{Scale:} Handling vast numbers of routers, prefixes, and ASes.
    \item \textbf{Privacy:} ASes unwilling to reveal internal topology or business relationships.
    \item \textbf{Policy-Driven Routing:} Each AS has own objectives e.g. minimize cost, maximize revenue, or reduce latency; no universal metric for best paths.
    \item \textbf{Diverse Objectives:} Choices influence by technical \& business considerations.
\end{itemize}
\end{itemize}


\subsection{8.2 Intra-Domain Protocols / IGPs and Limitations}
Two major intra-domain routing protocols, and understand why we cannot directly borrow ideas from the protocol and where changes and relaxations are needed. Also called interior gateway protocols or IGP.
\begin{enumerate}
\item \textbf{Link-State Protocols}: Link-state protocols (e.g., OSPF) require every router to know the entire network topology to compute shortest paths using algorithms such as Dijkstra’s. At Internet scale, this approach is infeasible due to:
\begin{itemize}
    \item Flooding topology info across millions of routers too expensive. High bandwidth and storage overhead, entire path computed locally per node requires high processing overhead.
    \item Privacy concerns prevent ASes from sharing internal network details.
    \item No universal metric to define shortest path across heterogeneous AS policies.
\end{itemize}

\item \textbf{Distance-Vector Protocols}: Distance-vector protocols (e.g., RIP) rely on routers exchanging hop-count information with neighbors iteratively using the Bellman-Ford algorithm. Considerations for inter-domain use include:
\begin{itemize}
    \item Still requires a shared metric to determine the `best' path.
    \item Convergence is too slow for Internet-scale networks.
    \item Better, hides details of network topology, only needs to determines next hop. So solution, we can extend the notion of a DV with BGP.
\end{itemize}
\end{enumerate}


\subsection{8.3 Border Gateway Protocol (BGP): Path-Vector (PV) Routing}

\begin{itemize}
\item \textbf{BGP}: the de facto inter-domain routing protocol. Extends distance-vector routing by specifying \textbf{entire AS path} instead of distance metric. Each route advertisement carries sequence of ASes to destination. 
\item \textbf{Advantages / Features of BGP}:
	\begin{itemize}
	    \item \textbf{Loop Prevention:} An AS can detect routing loops by checking whether its own AS number appears in the advertised path.
	    \item \textbf{Policy Enforcement:} AS-path information allows each AS to apply policies for route selection and advertisement.
	\end{itemize}
\item \textbf{Key Features of BGP}
	\begin{itemize}
	    \item Operates over TCP (port 179) to provide reliable delivery of routing information.
	    \item Supports policy-based decisions rather than purely metric-based selection.
	    \item Provides mechanisms to interconnect ASes via eBGP and propagate routes internally using iBGP.
	\end{itemize}
\end{itemize}

\subsection{8.4 BGP Architecture and Sessions}

\begin{itemize}
\item \textbf{BGP Peers/Speakers}: Routers running BGP establish sessions (TCP connections) to exchange route information. 
There are two main types:
	\begin{itemize}
	    \item \textbf{Exterior BGP (eBGP):} Between BGP speakers in different ASes. Should be directly connected.
	    Primarily used to exchange reachability information across AS boundaries.
	    \item \textbf{Internal BGP (iBGP):} Between BGP speakers within the same AS. Not required to be directly connected, IGP takes care of inter-BGP speaker connectivity.
	    Used to propagate externally learned routes to all routers in the AS.
	\end{itemize}
\end{itemize}

\centerline{\includegraphics[width=1\linewidth]{BGPOps}}

\begin{itemize}
\item \textbf{iBGP Full Mesh Rule}:
\begin{itemize}
    \item iBGP peers must form a logical full mesh to ensure route propagation.
    \item Routes learned from one iBGP peer not re-advertised to another iBGP peer to prevent loops and unnecessary flooding.
    \item The underlying IGP (e.g., OSPF routing protocol) handles physical connectivity between iBGP speakers.
\end{itemize}
\end{itemize}



\subsection{8.5 BGP Message Types and Mechanics}
BGP maintains connectivity, route propagation w. four primary message types:
\begin{itemize}
    \item \textbf{OPEN:} Opens TCP connection to peer, authenticates sender.
    \item \textbf{UPDATE:} Advertises new routes or withdraws existing ones.
    \item \textbf{KEEPALIVE:} Maintains the session during idle periods.
    \item \textbf{NOTIFICATION:} Reports errors and terminates sessions if necessary.
\end{itemize}

\textbf{BGP Routes and Withdrawn Routes}:
\begin{itemize}
\item \textbf{No expiration timer}: BGP does not use periodic timers to delete routes, unlike distance vector routing protocol RIP. Once BGP router learns routes, keep indefinitely until told no longer valid.
\item \textbf{Actively withdrawn or replaced}: Routes are actively withdrawn or replaced by original advertiser through a BGP UPDATE message.
\item \textbf{Invalidation}: routes from a peer become invalid when the peer goes down.
\end{itemize}


\subsection{8.6 UPDATE Message Format and Route Control}
BGP uses  \texttt{UPDATE} message to advertise new routes, modify existing ones, or withdraw invalid routes. 
Event-driven, sends \texttt{UPDATE} only when routing changes occur, either withdraws prefix if unreachable, or replace existing entry with new set of path attributes and NLRI.

\textbf{UPDATE Message Structure:}
\begin{itemize}
    \item \textbf{Withdrawn Routes:} Lists of IP prefixes that are no longer reachable. Sent actively to invalidate outdated routes.
    \item \textbf{Path Attributes:} Metadata describing characteristics or policies of each advertised route (e.g., \texttt{AS-PATH}, \texttt{NEXT-HOP}, \texttt{LOCAL-PREF}). Determines how routers select among multiple available paths.
    \item \textbf{Network Layer Reachability Information (NLRI):} Set of destination IP prefixes newly advertised as reachable, and their path attributes.
\end{itemize}

\centerline{\includegraphics[width=1\linewidth]{BGPUpdate}}

\subsection{8.7 Path Attributes and Policy Control}
The \texttt{Path Attributes} field in \texttt{UPDATE} message is central to BGP’s flexibility and policy-based routing. 
Each attribute conveys information that influences route selection and propagation behavior across Autonomous Systems (ASes).

BGP classifies attributes into four categories:
\begin{itemize}
    \item \textbf{Well-Known Mandatory:} Must appear in all \texttt{UPDATE} messages and be recognized by all BGP routers (e.g., \texttt{ORIGIN}, \texttt{AS-PATH}, \texttt{NEXT-HOP}).
    \item \textbf{Well-Known Discretionary:} Optional to include but must be understood if present (e.g., \texttt{LOCAL-PREF}).
    \item \textbf{Optional Transitive:} May be propagated to other peers even if not recognized by a router (e.g., \texttt{COMMUNITY}).
    \item \textbf{Optional Non-Transitive:} Ignored and not propagated if not recognized (e.g., experimental or vendor-specific attributes).
\end{itemize}

\textbf{Key Well-Known Mandatory Attributes}
\begin{itemize}
    \item \textbf{ORIGIN:} Indicates where the route originated—Interior Gateway Protocol (IGP), Exterior Gateway Protocol (EGP), or \textit{incomplete} (learned indirectly).
    \item \textbf{AS-PATH:}  Sequence of ASes traversed by the route. Used for loop prevention and as a key decision factor in path selection.
    \item \textbf{NEXT-HOP:} Specifies the IP address of the next-hop router outside the AS to reach advertised destination. 
\end{itemize}


\subsection{8.7 Forwarding Table Construction (Learning, Choosing Routes)}
The router integrates BGP routes into forwarding table using following process:
\begin{enumerate}
    \item \textbf{Route Learning:} Routes are learned via eBGP (external) and iBGP (internal). Multiple possible paths may exist for the same prefix.
    \item \textbf{Best Route Selection:} 
    \begin{itemize}
        \item \textbf{Shortest AS-Path}: Prefer path with fewest AS hops.
        \item \textbf{Closest NEXT-HOP}: If tied, prefer the route with the closest exit AS. (aka hot potato routing).
        \item \textbf{Custom Policies}: Policies (e.g., LOCAL-PREF) can let network operators prioritize certain routes for business or performance reasons. (See 8.11)
    \end{itemize}
    \item \textbf{Forwarding Table Population:} Once the best path is selected, the router uses its IGP (like OSPF or IS-IS) to determine which local interface (port) should be used to forward packets to the NEXT-HOP.
    \item The resulting forwarding table maps destination prefixes → output interfaces, so traffic can be sent efficiently.
\end{enumerate}

\subsection{8.8 BGP Routing Information Bases (RIBs)}
BGP keeps multiple logical tables to separate different stages of processing. Separate RIBs ensures policy control, dont advertise unapproved or invalid route.
\begin{itemize}
    \item \textbf{Adj-RIBs-In:} Routes learned from peers, before apply import policies. Raw unprocessed routes via inbound UPDATE. (E.g. peer sent 1000 prefixes).
    \item \textbf{Loc-RIB:} Router's selected best local routes after applying import policies and path finding. (E.g. Out of 3 paths to 10.0.0.0/24, install best in forwarding table).
    \item \textbf{Adj-RIBs-Out:} Routes to be advertised to other peers after applying export policies. (E.g. tell peer about 500 prefixes allowed by policies).
\end{itemize}

\subsection{8.9 Policy Implementation in BGP (Routes to accept and announce)}
\begin{itemize}
    \item \textbf{Import Policies:} Applied to incoming routes to filter unwanted routes or rank preferred paths (e.g., using LOCAL-PREF).
    \item \textbf{Export Policies:} Applied to outgoing routes to enforce business relationships (See 8.10)
    \begin{itemize}
        \item To a provider: advertise all own routes and customer routes.
        \item To a customer: advertise all known routes (so customer can use).
        \item To a peer: advertise only own and customer routes.
        \item I.e. Never advertise peer or provider's routes to another peer or provider.
    \end{itemize}
    \item \textbf{AS Path Prepending:} Artificially lengthens AS-PATH to make routes less attractive, controlling inbound traffic. (E.g. don't want traffic coming from particular provider, prepend AS number multiple times to make path longer.)
\end{itemize}

\subsection{8.10 Business Relationships and BGP Policy}
\begin{itemize}
    \item \textbf{Customer-Provider Relationship:} Customer exports all own and customers’ routes to the provider. Provider exports all known routes (other customers, peers, and providers) to the customer, offering full Internet reachability.
    \item \textbf{Peer-to-Peer Relationship:} Peers export only own and customer routes to each other, avoid transit for routes learned from other peers or providers.
    \item Export/import policies as technical implementation to enforce relationships.
\end{itemize}

\subsection{8.11 BGP Attributes in Route Selection}
BGP uses various attributes to decide which path is preferred among multiple available routes to the same prefix. These attributes reflect both technical performance and business policy.

\begin{itemize}
    \item \textbf{LOCAL\_PREF (Local Preference):} 4-byte unsigned int (default value 100, higher = preferred), for BGP speaker to inform other internal peers of preference for a route within the same AS (used in iBGP). Use to prefer certain outbound paths (e.g., prefer customer over peer or provider). Should not send to external eBGP peers.

    \item \textbf{AS\_PATH:} Sequence of AS numbers route traverses, prefer shorter sequences, used to prevent routing loops.

    \item \textbf{MULTI\_EXIT\_DISC (MED):} 4-byte unsigned int (default value 0, lower = more preferred), hint sent by one AS to a neighboring AS, suggest which entry point to use when multiple physical links exist between them. Influences \textit{inbound} traffic when multiple links exist between two ASes. Share only between neighboring ASes, may be propagated over iBGP, but not propagated further to neighbouring ASes.

    \item \textbf{COMMUNITY:} 4-byte tag attached to routes to classify or “group” them logically. Allows bulk policy application — routers can apply import/export rules based on community tags rather than listing prefixes individually. (e.g., “no-export” community). Used to tag customer routes, control export, or trigger remote actions.
\end{itemize}

\subsection{8.12 BGP Security Issues: Prefix Hijacking}
\begin{itemize}
    \item \textbf{Prefix Hijacking:} When an AS accidentally or maliciously advertises ownership of an IP prefix it does not own. Other ASes believe, send traffic for that prefix to it.
    \item \textbf{Subprefix Hijacking:} Attacker AS advertises more specific prefix (e.g., /24 of a victim's /16), causing other AS pick that route following longest matchin prefix, and most traffic to be rerouted to the attacker.
    \item \textbf{Consequences:} 
    \begin{itemize}
        \item \textit{Blackholing:} Traffic is discarded and dropped.
        \item \textit{Snooping:} Traffic is intercepted and inspected, and redirected back.
        \item \textit{Impersonation:} Traffic is redirected to fake destinations.
    \end{itemize}
    \item \textbf{Prevention:}
    \begin{itemize}
        \item Route filtering, where ISPs should only accept prefixes customers legitimately own. However, not everyone applies these practices, hard to filter routes initiated from far away, so BGP remains vulnerable to hijacks.
        \item \textbf{RPKI (Resource Public Key Infrastructure):} Cryptographically verifies prefix ownership.
        \item \textbf{ROA (Route Origin Authorization):} Specifies which AS is authorized to originate specific prefixes.
    \end{itemize}
\end{itemize}

\subsection{8.13 Summary of BGP used in Practice}
Overall, BGP can be controlled in three main ways:  \\
1. \textbf{Preference:} Modify attributes such as LOCAL\_PREF or AS path prepending to prefer certain routes or providers, e.g., to reduce cost. \\
2. \textbf{Filtering:} Inbound/outbound filters to accept/advertise only desired routes.  \\
3. \textbf{Tagging:} Use COMMUNITY attributes to classify routes for policy enforcement, either locally or remotely. \\
These mechanisms allow enforcement of business relationships, traffic engineering, and remote control (request behavior, not enforce) over how other ASes treat your routes.

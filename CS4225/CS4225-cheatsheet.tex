\subsection{2. \underline{Principles of Big Data Systems}}

\begin{itemize}
\item \textbf{Data Center Infrastructure}
	\begin{itemize}
	    \item \textbf{Single Server}: A commodity hardware unit.
	    \item \textbf{Rack}: Dozens of servers, connect to rack switch (top-of-rack switch).
	    \item \textbf{Data Center}: Hundreds of racks, connect to data center switch (core switch).
	\end{itemize}
\item \textbf{Bandwidth vs. Latency}
	\begin{itemize}
	    \item \textbf{Bandwidth}: Max amt of data transmittable per unit time (e.g., in GB/s). Calculate as minimum bandwidth among all components in the data access path.
	    \item \textbf{Latency}: Time taken one packet travel src to dest (one-way) / round-trip (in ms). Sum of the latency caused by all components in the data access path.
	    \item \textbf{Throughput}: Rate data is actually transmitted in network in given time period.
	\end{itemize}
\item When transmitting \textit{(large/small)} amount of data, \textit{(bandwidth/latency)} - roughly how long transmission will take (bottleneck variable).
\item \textbf{Storage Hierarchy in Data Centers}: based on capacity, latency, bandwidth. 
	\begin{itemize}
	    \item \textbf{DRAM}: Fast but limited capacity. \textbf{Flash}: Intermediate btw. DRAM and disk.
	    \item \textbf{Disk}: Slow but large capacity. Disk reads more expensive than DRAM (higher latency, lower bandwidth).
	\end{itemize}
\end{itemize}


\subsubsection{Data Flow Paths}
Data flow paths depend on the location of the source and destination. Data access may cross several components, e.g. hard disk, DRAM, rack switch, cluster switch.

\begin{itemize}[itemsep = -2pt]
\item E.g. Local DRAM $\rightarrow$ Local Disk in same server.
\item Server A DRAM to server B DRAM in same rack (i.e.  Local DRAM  $\rightarrow$ Rack Switch  $\rightarrow$ Server B’s DRAM)
\item Transfer across different rack, same cluster etc. (i.e. Local DRAM $\rightarrow$ Rack Switch  $\rightarrow$ Datacenter Switch  $\rightarrow$ Server C’s Rack Switch $\rightarrow$ Server C’s DRAM).
\item To load from disk, usually need to load into DRAM first. (i.e. Local Disk $\rightarrow$ Local DRAM $\rightarrow$ Rack Switch etc.)
\end{itemize}
\textbf{Calculate latency, bandwidth based on data flow path}. Approximate order of magnitude, for simplify, assume one-way communication, no failures.

\centerline{\includegraphics[width=1\linewidth]{storageHierarchy}} \smallskip

\textbf{Capacity} increases, \textbf{Costs} (Latency increase, bandwidth decrease) increases from local to rack to data center, along storage hierarchy.


\subsubsection{Building Efficient Big Data Systems}
\begin{enumerate}
    \item \textbf{Scale "Out", Not "Up"}: Horizontal Scaling over vertical scaling. Combine many cheaper machines (out) over increase power of individual machine (up).
    \item \textbf{Seamless Scalability}: Ideal (linear) scalability, performance increases proportionally to added resources. 
    \item \textbf{Move Processing to the Data}: As clusters limited bandwidth; move tasks to machine where data is stored.
    \item \textbf{Process Data Sequentially, Avoid Random Access}: Disk seeks expensive; sequential access provides better throughput.
\end{enumerate}

\subsubsection{Challenges in Big Data Systems}
\begin{enumerate}
    \item \textbf{Machine Failures}: With enough scale, expect daily server machine failure.
    \item \textbf{Synchronization}: Difficult due to unknown order of worker execution, interruptions, and shared data access. Tools like semaphores, conditional variables, and barriers are used to address synchronization issues.
    \item \textbf{Programming Difficulty}: Concurrency hard to reason about, especially at scale. Debugging and managing failures add complexity.
\end{enumerate}
\textbf{API for Data Centers}: Given challenges, "API" of data center abstracts system-level details from developers. Execution frameworks (e.g., Hadoop, Spark) handle task assignment, replication, synchronization, etc.


\subsection{3. \underline{MapReduce}}
Big data requires new prog. abstractions, runtime systems. Hadoop MapReduce widely used for efficient, process large datasets in e.g. databases, data mining. \\
\textbf{MapReduce}: prog. model \& associated runtime system to process large datasets in parallel across distributed cluster. (Parallel $+$ Divide \& Conquer Paradigm). MapReduce provides functional abstractions for two operations.

\begin{itemize}
    \item \textbf{Map function}:  \texttt{(k1, v1) → List(k2, v2)}. Processes each input key-value pair and emits intermediate key-value pairs. 
    \item \textbf{Reduce}: Aggregate intermediate results to generate the final output.  \texttt{reduce(k2, List(v2)) → List(k3, v3)}. All values with same key sent to same reducer.
	\item \textbf{Typical Workflow of MapReduce}: \\
	Iterate over a large number of records. Extract relevant info from each. (\textbf{Map}) \\
	Shuffle and sort intermediate results by key (\textbf{Shuffle}). \\
	Aggregate intermediate results (\textbf{Reduce}). Generate the final output.
\end{itemize}

\centerline{\includegraphics[width=1\linewidth]{mapReduce}} 

\begin{itemize}
    \item \textbf{Worker}: single component of cluster, performs storage, processing tasks.
    \item \textbf{Map Task}: A unit of work, processing one input split (e.g., 128 MB).
    \item \textbf{Map Function}: A call to user-defined map function, for each input split k-v pair.
    \item \textbf{Reduce Task}: A unit of work processing a subset of intermediate keys.
    \item \textbf{Barrier}: barrier between map and reduce phases. Else, reduce phase may compute wrong answer. Shuffle phase can begin copying intermediate data earlier. 
\end{itemize}

\subsubsection{Partition and Combiner}
Optionally specify \textbf{partition, combine} functions, optimize, reduce network traffic.
\begin{itemize}
    \item \textbf{Partition Step}: By default, keys assigned to reducers using hash function (e.g., \texttt{hash(key) \% num\_reducers}). Can implement custom partitioner to balance load among reducers. (E.g. if some keys much more values than others).
    \item Partitioner runs in local write phase, knowledge of which keys to which reducer.
    \item \textbf{Combiner Step}: Combiners locally aggregate map outputs to reduce disk and network I/O. ('mini-reducers') (E.g. Sum counts for each key before write to disk). \textit{Correctness}: Must not affect correctness of final output, regardless of how many times it runs (incld. 0 times). E.g. \texttt{sum}, \texttt{max} ok, but \texttt{mean}, \texttt{minus} not ok.
    	\item Combiner runs after map phase, done during local write phase, before actual disk write to save disk I/O.
\end{itemize}

\textbf{Notes and Other Optimizations}
\begin{itemize}
    \item If reduce task handles multiple keys, will process keys in sorted order.
    \item \textbf{Secondary Sort}: Use this property to sort values associated with key. (reduce work done in reducer by using inbuild distributed sorting process of Hadoop). Combine key and value into composite key e.g. (UserID $\rightarrow$ [UserID-Timestamp]), define custom comparator (sort by ID then timestamp) \& partitioner (group by ID only).
    \item Size of split too big or small:  $\rightarrow$  Limited parallelism vs. high overhead.
    \item \#map fn calls = \# input key-value pairs. \# map tasks = \# input splits.
    \item Reduce function calls = no. of distinct intermediate keys.
    \item \textbf{Preserving State in Map / Reduce Tasks}: In MapReduce, state variables can be used to store information that persists across multiple calls to map() or reduce() functions within same task. Sharing data or resources between function calls. 
\end{itemize}

\subsubsection{General Performance Guidelines (Basic Algorithm Design)}
\begin{itemize}
    \item \textbf{Linear Scalability}: More nodes should enable more work done in same time.
    \item \textbf{Minimize Disk and Network I/O}: Sequential access over random access. Send data in bulk over small chunks.
    \item \textbf{Reduce Memory Working Set}: Avoid large in-memory data structures to prevent out-of-memory errors.
\end{itemize}

\subsection{4. \underline{MapReduce \& Databases}}
\subsection{HDFS: Hadoop Distributed File System}
Distributed file system designed to store, manage large datasets across multiple machines in a cluster. Core component of Apache Hadoop ecosystem (open source), optimized for high-throughput access to big data.

\begin{itemize}
	\item \textbf{Purpose}: handle massive datasets (tb/pb), scalable, fault-tolerant storage.
    \item E.g. MapReduce input, output stored in HDFS (3 copies etc.) Intermediate files on hard disk on local machine though (local fs).
    \item \textbf{Architecture}: \textit{Master-Slave Model}.
    \\ \textbf{NameNode}: Master node, manage file system metadata (e.g., dir structure, file locations, rebalance, heartbeat) - No data moved through NN. If NN data lost, cannot reconstruct files from raw block data. Hadoop has NN backup, checkpointing.
    \\ \textbf{DataNodes}: Worker nodes, store the actual data blocks. \\
    
    \centerline{\includegraphics[width=0.9\linewidth]{HDFSHadoop}} 
    	\item \textbf{Data Locality}: Move computation to data, over other way round. Minimize network traffic, improve performance. Same set of nodes used for both HDFS, Hadoop. Hadoop tries to schedule map tasks run on machines containing data.
    	\item \textbf{Fault Tolerance}: Each block replicated (default: 3 copy) across different DataNodes to ensure reliability. If node fails, HDFS retrieves data from another replica.
    \item \textbf{Rack Awareness}: Aware of physical location of nodes (e.g., which rack). Replicas placed on diff rack, balance fault tolerance, network efficiency. 
	\item \textbf{Block Size}: Files divide to large chunks (default: 128 or 256 MB), reduce overhead. Large block sizes improve sequential read/write perform. ($\uparrow$ throughput).
	\item \textbf{Scalability}: Scales horizontally by adding more machines to the cluster. Supports thousands of nodes and handles large datasets efficiently.
	\item \textbf{Write Once, Read Many}: Files written once, can be read multiple times. Files cannot be modified after written (append-only in some cases).
    \item \textbf{Use Cases}: Store log files, web server data, social media data, etc. Support big data processing frameworks like MapReduce, Spark, Hive, and Pig.
\end{itemize}

\centerline{\includegraphics[width=1\linewidth]{HDFSArchitecture}} 
   
\textbf{Disadvantages of HDFS}: Not suited for small files, inefficient for large no. of small files, due to metadata overhead. High latency, not ideal for real-time or low-latency applications. Limited Random Access: design for seq access, not random reads/writes.

\subsection{Relational Databases DB}
Relational database comprised of tables, each table represents a relation, which is a collection of tuples (rows). Each tuple consists of multiple fields. Develop large-scale relational database using Hadoop / MapReduce.


\subsubsection{Star Schema and SQL Queries}
The Star Schema is a common database schema for data warehousing. Organizes data into single (central) fact table and dimension tables. Fact table linked via foreign key r/s to PK of each dimension. Faster query and simpler queries.

\centerline{\includegraphics[width=1\linewidth]{starSchema}} 

\subsubsection{SQL (Relational) Operations in MapReduce}
\begin{itemize}[itemsep = 0.5pt]
\item \textbf{Projection in SQL/MapReduce}: Projection selects specific columns from table. \\
 (E.g. \texttt{SELECT <columns> FROM Sales}). Only selected columns returned.
	\begin{itemize}
	\item \textbf{Map Phase}: Input: Tuples (t. ID as key), emit tuples (w. only select attributes).
	\item \textbf{No Reducer Needed}: "map-only" job, no need for shuffling or reducing.
	\end{itemize}
\item \textbf{Selection in SQL/MapReduce}: Selection filters rows based on condition. (E.g.  \texttt{SELECT * FROM Sales WHERE price > 10}). Only rows satisfying the predicate (condition) are returned.  MapReduce implementation:
	\begin{itemize}
	\item \textbf{Map Phase}: Input: Tuples (tuple ID as key) emit tuples satisfying predicate.
	\item \textbf{No Reducer Needed}: Similar to projection, this is a map-only job.
	\end{itemize}
\item \textbf{Group By and Aggregation}: Aggregation operations. Shuffle phase is the 'group by'. Framework auto groups tuples by key.
(E.g. \texttt{SELECT product\_id, AVG(price) FROM sales GROUP BY product\_id}). Output avg per product.
	\begin{itemize}
	\item \textbf{Map Phase}: Emit key-value pairs: $\langle \text{product\_id}, \text{price} \rangle$.
	\item \textbf{Shuffle Phase}: Framework groups tuples by key (\texttt{product\_id}).
    \item \textbf{Reduce Phase}: Compute average price for each \texttt{product\_id}. (Same Reducer). Optimize using combiners to reduce network traffic.
	\end{itemize}
\item \textbf{Relational Joins (Inner Join)}: Joins combine data from two tables based on a common key. (E.g. \texttt{SELECT A.Id, A.attr1, B.attr2 FROM A JOIN B ON A.bID = B.bID}) Many-to-many r/s (can appear multiple times in both tables).  
	\begin{enumerate}[itemsep=0pt, topsep=0pt]
		\item \textbf{Broadcast (Map) Join}: Requires the smaller table to fit in memory. Mappers store copy of small table as hash table. Iterate over large table, perform join. (Hash Join. Smaller table 'broadcasted' to all mappers/processing nodes.)
	    \item \textbf{Reduce-side (Common) Join}: Mappers emit records with join key as primary key. Reducers group records by join key. Can use secondary sorting to ensure all keys from one table arrive before the other. Hold keys from first table in memory, cross them with records from second table (to do join).
	\end{enumerate}
\end{itemize}

\item Performance analysis, algorithm design crucial for efficient, effective applications.

\subsection{5. \underline{MapReduce \& Data Mining}}

\subsection{Similarity Search}
Similarity search is a fundamental problem in data mining and machine learning, often used to find objects "similar" to each other. Real-world applications e.g.:
\begin{itemize}
	\item Finding documents with similar words for duplicate detection, topic classification. Clustering similar news articles, research papers.
	\item Identifying customers purchasing similar products for recommendation systems.
	\item Grouping users with similar browsing behaviors for targeted advertising.
\end{itemize}

\subsubsection{Distance and Similarity Measures}
Between objects $x$ and $y$, use \textbf{distance measure} $d(x, y)$ or \textbf{similarity measure} (opposite). 'Near Neighbours' are points small distance apart. Common metrics:
\begin{itemize}
	\item \textbf{Euclidean Distance}: Straight-line distance btw two points in space.
	\item \textbf{Manhattan Distance}: Sum of absolute differences along axes.
	\item \textbf{Cosine Similarity}: Measures the cosine of the angle between two vectors, focusing only on direction (ignoring magnitude).
	\item \textbf{Jaccard Similarity}: Similarity between sets $A$, $B$: $s_{\text{Jaccard}}(A, B) = \frac{|A \cap B|}{|A \cup B|}$
	\item \textbf{Jaccard Distance}: Complement $s_{\text{Jaccard}}$: $d_{\text{Jaccard}}(A, B) = 1 - s_{\text{Jaccard}}(A, B)$
\end{itemize}
    
\subsubsection{Case Study: Finding Similar Documents}

\textbf{Problem Definition}: Given a large collection of $N$ documents: 
\begin{itemize}
\item \textbf{All-Pairs Similarity}: Find all pairs of docs w. Jaccard similarity above threshold.
\item \textbf{Similarity Search}: Given a query document, find all documents similar to it.
\end{itemize}

\textbf{Approach:} To efficiently find similar documents, we do shingling and min-hash.
\centerline{\includegraphics[width=0.8\linewidth]{similarDocuments}} 

\subsubsection{Shingling}
\begin{itemize}
\item A \textbf{k-shingle} (or k-gram) is sequence of $k$ tokens (words / chars) that appears in document.
E.g. 'the cat is glad' $\rightarrow$ set of 2-shingles: $\{\text{'the cat'}, \text{'cat is'}, \text{'is glad'}\}$ 
\item \textbf{Similarity Metric for Shingles}: Each document $D_i$ represented as set of shingles $C_i$. Similarity of ($D_1$, $D_2$):
$\text{s}_{Jaccard}(D_1, D_2) = \frac{|C_1 \cap C_2|}{|C_1 \cup C_2|}$
\item \textbf{Challenge}: For large datasets, comparing all pairs directly computationally expensive ($O(N^2)$ comparison). To address this, use \textbf{Min-Hashing}.
\end{itemize}

\subsubsection{Min-Hashing \textnormal{\scriptsize(Each shingle hashes to a int, get min int value of all shingles)}}
Convert large sets of shingles into short signatures while preserving similarity. Highly similar $=$ high probability of same signature. Dissimilar docs low prob.

\begin{enumerate}[itemsep =0pt]
	\item Define a hash function $h$ that maps each shingle to an integer.
	\item For each document, compute min hash value across all shingles $\rightarrow$ 'signature'.
	\item Use \textit{multiple} independent hash functions to generate \textit{multiple} signatures.
\end{enumerate}
\begin{itemize}
\item \textbf{Key Property of Min-Hashing}: probability two documents have same MinHash signature is equal to Jaccard similarity.
\item \textbf{Candidate Pairs}: Compare signatures (e.g. $> k$ matching signatures). Pairs either directly used as output or further compared to confirm similarity.
\end{itemize}

\subsubsection{MapReduce Implementation}
\begin{itemize}
\item \textbf{Map Phase}: Read each document, extract shingles. Hash each shingle, compute MinHash signature. Emit $\langle \text{signature}, \text{document\_id} \rangle$. (Either run multiple times for diff hash, or use signature\_vector, custom partitioner to send same reducer.)
\item \textbf{Reduce Phase} Receive all documents with the same MinHash signature. Generate candidate pairs from these documents. (Optional, confirm pair further similarity).
\item \textbf{Parallelism}: \# map node $\rightarrow$ \# docs chunks. \# reduce node $\rightarrow$ \# keys (signature).
\end{itemize}

\subsection{Clustering}
\begin{itemize}
\item \textbf{Clustering}: Fundamental technique in data mining, machine learning to group unlabeled data points into clusters of similar items. Ideally, points have high intra-cluster similarity, low inter-cluster similarity.
\item \textbf{Applications of Clustering}: Microbiology gene/protein identification, recommendation systems, social networks, information retrieval.
\end{itemize}

\subsubsection{K-Means Algorithm}
Clustering technique. Separates data points into $K$ clusters by iteratively optimizing positions of cluster centers.
\begin{enumerate}[itemsep=-0.2pt, topsep=0.5pt]
    \item \textbf{Initialization}: Randomly select $K$ points as initial cluster centers.
    \item \textbf{Repeat until convergence}:
    \begin{enumerate}[itemsep=0pt, topsep=0pt]
        \item \textbf{Assignment Step}: Assign each data point to nearest cluster center based on distance metric (e.g., Euclidean distance).
        \item \textbf{Update Step}: Move each cluster center to average (mean) position of all points assigned to it.
    \end{enumerate}
    \item \textbf{Stopping Condition}: Stop when no assignments change between iterations (i.e., the algorithm converges).
\end{enumerate}

\textbf{Challenge with K-Means}: Iterative algorithms like K-Means are not inherently optimized for distributed systems like MapReduce!

\subsubsection{MapReduce Implementation of K-Means}

\centerline{\includegraphics[width=1\linewidth]{cluster}} 

\textbf{MapReduce Usage in Data Mining, Machine Learning}
\begin{itemize}
\item MapReduce still needs to iteratively run till convergence.
\item Iterative algorithms like K-Means maybe not ideal for MapReduce, high network, disk I/O overhead (input disk read for every iteration). 
\item \textbf{In-mapper combiner}: aggregate values directly in mapper using in-memory structures to emit fewer k-v pairs, reducing number of combiner calls. Reduce disk I/O since fewer intermediate records, but hgiher memory usage in mapper. 
\item \textbf{System Combiner}: Use dedicated combiner function (run after map phase before data sent to reducer), run by system. More suitable when memory is limited.
\item \textbf{Secondary Sort} - No aggregation, records (same key) go reducer in specific order.
\item While optimizations such as in-mapper combiners can reduce computational cost, but not fully address inefficiencies of iterative algorithms in MapReduce. (Other frameworks e.g. Spark can overcome instead by using caching, in memory)
\end{itemize}

\subsection{6. \underline{NoSQL \& Distributed Databases}}

NoSQL: non-relational databases, store data in formats other than relational tables. 
\begin{itemize}
\item "SQL" here refers to traditional relational DBMS (relation databases, not querying language). NoSQL systems often involve SQL-like querying languages.
\item "NoSQL" originally "Not SQL," but evolved to mean "Not Only SQL".
\item \textbf{Coexistence} of relational \& relational databases in modern systems, each for tasks they are suited for, e.g. graph, vector databases.
\item \textbf{Key Motivations}: Growth in web apps, big data, distributed systems. 
	\begin{itemize}
	\item \textbf{Volume and Velocity}: Handling large-scale data and high-speed data ingestion.
	\item \textbf{Scalability}: Horizontal scalability to distribute data across multiple servers.
	\item \textbf{Flexibility}: Support for unstructured/ semi-structured data w. flexible schemas.
	\item \textbf{Performance}: Optimize specific use case, e.g. fast read/write, efficient storage.
	\end{itemize}
\end{itemize}

\subsection{Major Types of NoSQL Databases}
NoSQL databases categorizable into several types, based on their data models:
\begin{enumerate}[itemsep=0pt]
    \item \textbf{Key-Value Stores}: Store data as key-value pairs (e.g., Redis, DynamoDB).
    \item \textbf{Wide Column Databases}: Store data in tables with rows and columns, but allow flexible schemas (e.g. Cassandra, HBase).
    \item \textbf{Document Stores}: Store as documents, JSON-like (e.g. Mongo, CouchDB).
    \item \textbf{Graph Databases}: Data as nodes, edges to model relationships (e.g. Neo4j).
    \item \textbf{Vector Databases}: Store high-D vectors for similarity search (e.g., Milvus).
\end{enumerate}

\subsubsection{Key-Value Stores}
\begin{itemize}
\item \textbf{Data Model}: Key-value stores associate keys with values. 
\item \textbf{Keys:} Unique identifiers. Primitives e.g. ints, strings, raw bytes, queryable. 
\item \textbf{Values}: can be simple or complex data types, e.g. primitives, lists, JSON objects, or binary large objects (BLOBs). Usually cannot be queried.
\item \textbf{Operations}: simple API, \texttt{Get} (fetch value of key), \texttt{Put} (set value associated w. key). Optional operations include Multi-get, multi-put, range queries.
\item \textbf{Use Cases}: Optimized for fast reads \& writes, caching, session storage, small-continuous read/write, uses w. simple query patterns (e.g., Redis, DynamoDB).
\item \textbf{Persistence}: \textbf{Non-persistent} (just big in-memory hashtable, but back up data to disk periodically) e.g. Memcached, Redis. 
	\textbf{Persistent}: Data stored persistently to disk. E.g. RocksDB, Dynamo, Riak
\end{itemize}


\subsubsection{Document Stores}
\begin{itemize}
\item \textbf{Data Model}: Organize data into collections of documents. 
\begin{itemize}
\item \textbf{Database} contains multiple collections. A \textbf{collection} contains multiple documents. A \textbf{document} is a JSON-like object with fields and values.
\item Documents can be nested (JSON objects as values), varying fields, flexibility for unstructured / semi-structured data.
\end{itemize}
\item \textbf{Querying}: Unlike basic k-v stores, document stores support querying based on document content. Common operations: CRUD (create, read, update, delete).
\item \textbf{Example: MongoDB Architecture}: MongoDB uses a distributed architecture.
\end{itemize}
\centerline{\includegraphics[width=1\linewidth]{mongoDB}} 

\subsubsection{Wide Column Databases}
 Store data in tables w. rows \& columns, like relational DB, allow flexible schemas.
 \begin{itemize}
\item Each row can have different columns, data partitioned by partition key column.
\item \textbf{Column Stores}: 'Mix between relational database and document store'.
\item Ideal for large-scale, distributed datasets (e.g., Cassandra, HBase, open source).
\end{itemize}


\subsubsection{Graph Databases}
\begin{itemize}
\item Represent data as nodes (entities) and edges (relationships), enabling efficient traversal and querying of relationships.
\item These databases are particularly useful for applications like social networks, recommendation engines, and fraud detection, where relationships between entities are critical (e.g., Neo4j).
\end{itemize}


\subsubsection{Vector Databases}
\begin{itemize}
	\item \textbf{Vector Databases}: Each row represent point in $d$-dimensional space.
    \item Vectors typically represent embeddings from machine learning models. These databases enable fast similarity searches, such as finding nearest neighbors, and are widely used in AI/ML workflows for tasks like recommendation systems, image search, and clustering (e.g., Milvus, Pinecone).
    \item Algorithms like Locality-Sensitive Hashing (LSH) enable fast similarity search.
    \item \textbf{Examples}: Milvus, Redis, Weaviate, MongoDB Atlas
\end{itemize}


\subsubsection{Pros and Cons of NoSQL Systems}
\begin{itemize}
\item \textbf{Advantages}: Flexible schemas for semi/unstructured data. Horizontally scalable. High performance and availability due to relaxed consistency models. 
\item \textbf{Disadvantages}: Lack of declarative query languages (e.g., SQL). Weaker consistency guarantees, which may require application-level handling. Challenges with schema evolution and data duplication.
\item Choice between NoSQL and relational databases depends on: \textit{app requirements} (e.g., consistency vs. availability), query complexity (e.g., joins vs. simple read/writes), data volume and scalability needs.
\end{itemize}

\subsubsection{Key Concepts in NoSQL / Distributed Databases}
\begin{itemize}
\item \textbf{ Brewer's / CAP theorem}: Any distributed system/ data store can simultaneously provide only 2 of 3 guarantees: consistency, availability, partition tolerance (CAP).
\item \textbf{BASE}: Basically Available, Soft state, and Eventually consistent.
	\begin{itemize}
	\item \textbf{ACID} databases prioritize consistency (correctness) over availability—the whole transaction fails if an error occurs in any step within the transaction.
	\item \textbf{BASE } databases prioritize availability over consistency. Basic read write available most of time. Instead of fail, users access inconsistent data temporarily (\textit{soft state}, no guarantees). Data consistency is achieved eventually.
	\end{itemize}

\item \textbf{Consistency Models} {\scriptsize Different from ACID consistency - data integrity.}
	\begin{itemize}
	\item \textbf{Strong Consistency}: Any reads after update give same result on all observers. 
	\item \textbf{Eventual Consistency}: Updates propagate over time, and readers may see stale data temporarily. Offers higher availability but weaker guarantees.
	\end{itemize}
\item \textbf{Denormalization}: (duplication of data across tables) - tradeoff between query efficiency and propogation of data updates. Design around queries expected.
\item \textbf{Partitioning} across distributed databases: (e.g. by Range / specific column) - Related queries efficent, (entries co-located, no need scan entire database). However, may have imbalanced partitions, maintenance (shift from one partition to another on change), inefficency of incompatible queries - need scan multiple partitions.
\end{itemize}

\textbf{NoSQL Overall}: {\scriptsize Evaluate pros cons, select right DB system for app use case}
\begin{itemize}
\item NoSQL DB good for modern apps, flexible dynamic schema, (horizontal) scalability, performance \& availability (due to sacrificing strong consistency, removing need for locks, concurrency mechanisms).
\item  Trade-offs in consistency guarantees (outdated data, additional work to handle on app side), and query capabilities (e.g. no joins).
\end{itemize}

\subsection{7. \underline{Spark}}
\begin{itemize}
\item \textbf{Apache Spark}: fast, distributed computing framework, large-scale data processing. Leverage in-memory computation. Outperforms Hadoop MapReduce, especially iterative, interactive workloads, reduced latency, improved throughput.
\item \textbf{Addresses Limitation}: issue w. Hadoop MapReduce of high network, disk I/O costs as write intermediate data to local disk, shuffle across machines. Not ideal for iterative process (e.g. ML / graph algo), each step a separate MapReduce job.
\item \textbf{Advantages of Spark}: Store intermediate results in memory, speed up iterative processing. Falls back to disk I/O when memory insufficient.
\item \textbf{Ease of Programmability}: Simpler, more intuitive API compared to Hadoop MapReduce. E.g. implement WordCount in Spark concise \& expressive:
	\begin{verbatim}
	val file = sc.textFile("hdfs://...")
	val counts = file.flatMap(line => line.split(" "))
	                .map(word => (word, 1))
	                .reduceByKey(_ + _)
	counts.save("...")
	\end{verbatim}
\end{itemize}

\subsection{Spark Architecture}
\begin{itemize}
\item \textbf{Driver Process}: Manages Spark application, responds to user input, and distributes work to executors.
\item \textbf{Executors}: Run the assigned tasks by driver, sends results back to driver.
\item \textbf{Cluster Manager}: Allocates resources (e.g., Spark's standalone cluster manager, YARN, Mesos, or Kubernetes).
\item \textbf{Local Mode}: All processes run on a single machine for testing and development.
\end{itemize}

\centerline{\includegraphics[width=1\linewidth]{SparkArchitecture}} 
\begin{itemize}
\item Spark achieves simplicity by providing fundamental abstraction of simple logical data structure called Resilient Distributed Dataset (RDD) upon which all other
higher-level structured data abstractions, DataFrames and Datasets, constructed.
\item Through set of transformations and actions as operations, Spark offers simple programming model to build big data applications in familiar languages.
\end{itemize}

\subsection{Resilient Distributed Datasets (RDDs) {\scriptsize  (Foundational abstraction)}}
\begin{itemize}
\item \textbf{RDDs}: A distributed collection of objects that can be processed in parallel.
\item \textbf{Immutable}: Once created, RDDs cannot be modified.
\item \textbf{(R) Fault Tolerance}: Achieved through lineage, which allows Spark to recompute lost partitions using the DAG (Directed Acyclic Graph).
\item \textbf{(DD) Partitioned}: Data divided into partitions distributed across worker nodes.
\end{itemize}

\subsection{Transformations and Actions}
\begin{itemize}
\item \textbf{Transformations}: Lazy operations, create new RDDs from existing RDD (e.g., \texttt{map}, \texttt{filter}, \texttt{join}, \texttt{groupBy}, \texttt{select}). Lazy - nothing happens till action.
\item \textbf{Actions}: Trigger computations, return results to driver (e.g., \texttt{count}, \texttt{save}). 
\item Read, transforms, actions execute in parallel, results sent only in final step.
\end{itemize}

\begin{verbatim}
# Create an RDD of names, distributed over 3 partitions
dataRDD = sc.parallelize(["Alice", "Bob", "Carol", "Daniel"], 3)
nameLen = dataRDD.map(lambda s: len(s)) # Transform
nameLen.collect()  # Action Output: [5, 3, 5, 6]
\end{verbatim}


\subsection{Caching}
\begin{itemize}
\item Caching: Improve performance by storing frequently used RDDs in memory.
\item \textbf{When}: Cacje expensive to compute RDD that will be reused multiple times.
\item \textbf{Methods}: \texttt{cache()}: Saves RDD in memory. \texttt{persist(options)}: Allows caching in memory, disk, or off-heap memory.
\item \textbf{Memory Management}: If memory is insufficient, evict LRU RDDs.
\end{itemize}

\subsection{Spark Directed Acyclic Graph (DAG)}
\begin{itemize}
\item Spark constructs DAG to represent RDD transformations and dependencies.
	\begin{itemize}
	\item  \textbf{Narrow dependencies}: where each partition of parent RDD used by at most 1 partition of child RDD (e.g. \texttt{map}, \texttt{contains})
	\item \textbf{Wide dependencies}: opposite - each partition of parent RDD used by multiple partitions of child RDD (e.g. \texttt{reduceByKey}, \texttt{groupBy})
	\end{itemize}
\item \textbf{Stages}: In DAG, consecutive narrow dependencies grouped into “stages”. Within stages, perform consecutive transforms on same machines.
\item \textbf{Across Stages}: Wide dependencies trigger \textit{shuffling} (exchange across partitions like mapreduce), which involves write intermediate results to \textit{disk}. Minimize shuffling to improve performance (due to disk I/O not in memory).
\item \textbf{Fault Tolerance}: Spark uses lineage to recompute lost partitions instead of relying on replication (costly as in-memory). If worker node goes down, replace with new worker, use DAG recompute only RDDs from lost partition.
\end{itemize}
 

\subsection{DataFrames}
\begin{itemize}
\item \textbf{Dataframe}: Represent tabular data like SQL tables / pandas DataFrames.
\item Provide higher-level interface w. SQL-like operations (e.g. \texttt{groupBy}, \texttt{orderBy}).
	\begin{verbatim}
flightData2015 = spark.read.option("inferSchema", "true")
                         .option("header", "true")
                         .csv("/path/to/data.csv")
flightData2015.sort("count").take(3)
    \end{verbatim} \vspace{-1.5em}
\item Generally, transform functions (groupBy, sort) take strings or “column objects”.
\item Can use SQL queries to transform DataFrames (returns output DataFrame).
\end{itemize}

\item DataFrames, but type-safe. (Spark (Scala) - DataFrame alias of Dataset[Row].)

\subsubsection{RDD vs DataFrame on Execution Efficiency}

\begin{itemize}

\item \textbf{Code Generation}: Generating highly optimized machine code for execution.

\subsection{8. \underline{Stream Processing}}
\begin{itemize}

\end{itemize}

\begin{itemize}
\item \textbf{Stream processing systems} not limited to trivial record-at-a-time transformations. 
	\begin{itemize}
	\item Store and access intermediate data. (Local state, periodic checkpoint)
	\item Maintain state in prog variables, local files, embedded DBs, external systems.
	\end{itemize}

\subsection{Spark Structured Streaming}
\begin{itemize}
\item \textbf{Stream processing pipelines} should be as easy as writing batch pipelines.
\item Unified programming model and interface for both batch and stream processing.
\item Broader definition stream processing: data stream as an unbounded table.
\end{itemize}

\subsection{Micro-Batch Stream Processing}
\begin{itemize}
\item \textbf{Micro-Batch processing model} of Spark Structured Streaming.
	\begin{itemize}
	\item Divide input stream into small batches.
	\item Process each batch in Spark cluster in a distributed manner.
	\item Generate output in micro-batches using deterministic tasks.
	\end{itemize}
\item \textbf{Advantages} of Micro-Batch:
	\begin{itemize}
	\item Efficient recovery from failures.
	\item Ensures end-to-end exactly-once processing guarantees.
	\end{itemize}
\item \textbf{Disadvantages} of Micro-Batch:
	\begin{itemize}
	\item Latencies of a few seconds, which may be acceptable for many applications.
	\item Applications may incur additional delays in other parts of the pipeline.
	\end{itemize}
\end{itemize}


\subsection{Structured Streaming Processing Model}
Structured Streaming processes data streams in five steps:

\begin{enumerate}[itemsep=0pt, topsep=0pt]
    \item \textbf{Define Input Sources}: Specify where the data is coming from.
    \item \textbf{Transform Data}: Apply transformations to the data.
    \item \textbf{Define Output Sink and Output Mode}: Where, how to write output.
    \item \textbf{Specify Processing Details}: 
    \begin{itemize}[itemsep=0pt, topsep=0pt]
	\item \textbf{Triggering details}: When to trigger results, process new stream data.
        \item \textbf{Checkpoint location}: Store stream query process information (fail recovery).
    \end{itemize}
    \item \textbf{Start the Query}: Begin processing the stream.
\end{enumerate}

\subsection{Data Transformation (Streaming Data)}
\subsubsection{Stateless Transformations}
\begin{itemize}
\item Process each row independently without relying on previous rows. E.g.
\item Projection operations: \texttt{select()}, \texttt{explode()}, \texttt{map()}, \texttt{flatMap()}.

\item \textbf{Stateful streaming aggregations} include:

\item Event-Time window Aggregations (E.g. \texttt{window('eventTime', '5 min')})

\subsection{Time Semantics}
\begin{itemize}
\item \textbf{Processing Time}: Time at which stream processing machine processes event.
\item \textbf{Event Time}: The time when the event actually occurred.
\item \textbf{Benefits of Event Time}: Decouples processing speed from results.
	\begin{itemize}
	\item Operations based on event time are \textbf{predictable, deterministic}.
	\item Event time window computation yields same result regardless processing speed or event arrival order (out-of-order data arrival).
	\end{itemize}
\item \textbf{Watermarks}: mechanism handling late-arriving data, state of streaming queries. 
\end{itemize}

\centerline{\includegraphics[width=1\linewidth]{trigger}}     

\subsubsection{Trigger in Spark Structured Streaming}
\begin{itemize}
\item \textbf{Trigger} define how often and when streaming query process new available data.
\item \textbf{Default} (Micro-batch Processing): process data ASAP without waiting.
\item \textbf{Fixed Interval Trigger}: process data at fixed interval (e.g. 5 sec). 
\item Manage execution of stream query, control latency, throughput, resource usage.
\end{itemize}

\subsubsection{Watermarking in Spark Structured Streaming}
\begin{itemize}
\item \textbf{Defines threshold} for how late data can arrive before considered irrelevant. 
\begin{itemize}
\item \textbf{Watermark: timestamp}, point in time up to which all data has been processed.
\item Any data arriving w. event time earlier than watermark is "too late", discarded.
\end{itemize}
\item Watermark \textbf{dynamically updated} based on maximum observed event time in stream minus a user-specified delay threshold.
\item \textbf{Watermark Delay Threshold}: user-defined parameter, specify how long Spark waits for late data. E.g. if delay threshold 10 min, Spark assume any data arriving more than 10 minutes after latest observed event time is irrelevant. $(\mathrm{Watermark} = \mathrm{Max Observed Event Time} - \mathrm{Delay Threshold})$
\end{itemize}

\subsection{Overview of Apache Kafka}
\centerline{\includegraphics[width=1\linewidth]{kafka}}     
\smallskip
\begin{itemize}
\item \textbf{Apache Kafka}: distributed event streaming platform for high-throughput, fault-tolerant, real-time data processing. Build real-time data pipelines, streaming apps.
	\begin{itemize}
	\item \textbf{Event Logs}: Kafka stores streams of records (events) in categories called topics.
	\item \textbf{Decoupling}: Kafka decouples data producers (senders) and consumers (receivers), enabling asynchronous, non-blocking event transfer.
	\item \textbf{Scalable}: Supports large volumes of data across multiple nodes in a cluster.
	\item \textbf{Durable}: Data persist on disk, replicate across multiple brokers, fault tolerance.
	\end{itemize}
\item \textbf{Key Concepts in Kafka}
	\begin{itemize}
	\item \textbf{Topics}: A topic is a category or feed name to which records are published. Topics partitioned, replicated across multiple brokers.
	\item \textbf{Partitions}: Each topic divided into partitions, allow horizontal scaling. Each partition is ordered, immutable sequence of records.
	\item \textbf{Producers}: Producers publish data to Kafka topics.
	\item \textbf{Consumers}: Consumers subscribe to topics and process the data.
	\item \textbf{Brokers}: Kafka runs as a cluster of brokers. Each broker manages a subset of the partitions for the topics.
	\item \textbf{Offsets}: Each record in a partition has a unique offset, which acts as an identifier for the record's position in the partition.
	\end{itemize}
\item \textbf{Partitioning}: partitioning mechanism, distribute data across multiple brokers:
	\begin{itemize}
	\item \textbf{Partition Key}: Messages assigned to partitions based on a key. If no key is provided, messages are distributed in a round-robin fashion.
	\item \textbf{Hash Function}: Partition number determine using hash function: 
	$\text{Partition Number} = \text{hash(key)} \% \text{number of partitions}$. Ensures all messages with same key sent to the same partition, preserving order within partition.
	\end{itemize}
\item \textbf{Data Retention}: configurable period or size limit or log compaction (retain only the latest value for each key, reducing storage requirements).
\item \textbf{Consumer Groups}: allow multiple consumer read from same topic in parallel. 
	\begin{itemize}
	\item \textbf{Load Balancing}: Each partition consume by only one consumer within group.
	\item \textbf{Fault Tolerance}: If consumer fail, partition reassign to other consumer in group.
	\end{itemize}
\item \textbf{Use Cases of Kafka}: Real-time analytics, event sourcing, microservice comm.
\item \textbf{Kafka vs Traditional Message Queues}: Data persistence on disk, scalability, order guarantee, replayability.
\item \textbf{Example: Kafka in Photos Synchronization System}: (e.g. iCloud, GPhotos). 
	\begin{itemize}
	\item \textbf{Producer}: Photos uploaded from a phone or laptop are sent to Kafka as events.
	\item \textbf{Topic}: Events are stored in a Kafka topic, such as "photo-uploads."
	\item \textbf{Consumer}: Servers subscribe topic, process events, synchronize device photos.
	\item \textbf{Fault Tolerance}: Photo uploads not lost even if some server fail.
	\end{itemize}
\item \textbf{Advantages of Kafka}: High Throughput, Low Latency, Durability, Scalability.
\item \textbf{Challenges with Kafka}: Complexity, Resource Intensive, Latency for small messages.
\end{itemize}

\begin{itemize}[itemsep=-0.5pt]
\item Tasks in a running application continuously exchange data.
\item TaskManagers handle data shipping from sending tasks to receiving tasks.

\end{itemize}

\subsubsection{Flink Event-Time Processing}
\begin{itemize}
\item \textbf{Timestamps}: Every record will include an \textbf{event} timestamp (when they occured, vs. using process / ingestion-time timestamps).
\item \textbf{Watermarks}: Special records indicating progress of event time. Flow alongside regular records, \textbf{triggers (event-time-related) computations}. Specified by user!
	\begin{itemize}
	\item \textbf{Periodic Watermarks}: Generated at fixed intervals.
	\item \textbf{Punctuated Watermarks}: Generate based on specific events in stream.
	\end{itemize}
\item \textbf{Allowed Lateness}: specifies how much event delay tolerated. Signals: "All events with timestamps earlier than this watermark have been received."
\item Event arriving after watermark's timestamp considered "late", handled accordingly (e.g., dropped, sent to a side output).
\item \textbf{Watermarks} implemented as records holding a timestamp (Long value). Tells Flink when to finalize results for given time window. (E.g. watermark at 10:00 indicates Flink can now process all events with timestamps before 10:00). 
\end{itemize}
        

\subsubsection{Flink State Management}
\begin{itemize}[itemsep=0pt]
\item Robust state management for stateful stream processing. \textbf{State Backend}:
\item \textbf{Local State Management}: 
	\begin{itemize}[itemsep=0pt]
	\item \textbf{Task of a stateful operator} reads, updates its state for each incoming record.
	\item \textbf{Each parallel task} maintains its state locally in memory for fast access.
	\end{itemize}
\item \textbf{Checkpointing}:
	\begin{itemize}[itemsep=0pt]
	\item \textbf{A TaskManager} process may fail at any point, hence storage considered volatile
	\item \textbf{Checkpoints persist state} to remote, persistent storage (e.g., distributed filesystems or database system), for fault tolerance to recover from failure.
	\end{itemize}
\end{itemize}

\subsubsection{Checkpoints}
Flink's checkpointing mechanism ensures \textbf{consistent} state across distributed tasks: (similar to Spark micro-batch \textbf{consistent} checkpoints).
\begin{itemize}
\item \textbf{Spark (micro-batch) Checkpointing}: Pause ingestion of all input streams, process all in-flight data of all tasks, take checkpoint by copying state of all tasks to remote persistent storage. Resume ingestion of all streams. (`stop-the-world')
\item \textbf{Failure Recovery} (from a consistent checkpoint): Restart entire application, Reset states of all stateful tasks to latest checkpoint. Resume processing from the point of failure.  - costly delays.
\end{itemize}

\subsubsection{Flink's Checkpointing Algorithm}
\begin{itemize}
\item \textbf{Checkpoint algorithm}: based on \textbf{Chandy-Lamport} distributed snapshot algo.
\item \textbf{Checkpoint barriers} inject into stream, cannot overtake or pass by other records.
\item Barriers logically split the stream into two parts:
	\begin{itemize}
	\item State modifications due to records preceding barrier included in checkpoint.
	\item Modifications due to subsequent records included in later checkpoint.
	\end{itemize}
\item Checkpointing is async, allow tasks to continue process, while others persist state.
\end{itemize}
\textbf{Checkpointing Algorithm}:
\begin{enumerate}[itemsep=0pt]
    \item JobManager initiates checkpoint, send a message to all source operators.
    \item Source operators checkpoint their state and emit a \textbf{checkpoint barrier}.
    \item Tasks buffer records until \textbf{all checkpoint barriers received}.
    \item Once all barriers are received, tasks checkpoint state, \textbf{forward the barrier}.
    \item Sinks acknowledge receipt of the checkpoint barrier to the JobManager.
    \item A checkpoint is complete when all tasks have acknowledged their state.
\end{enumerate}

\subsection{Comparison: Spark vs. Flink}
\begin{itemize}
\item \textbf{Spark}: Micro-batch streaming processing with latencies of a few seconds. 
	\begin{itemize}
	\item Checkpoints are synchronous ("stop the world"). 
	\item Watermarks are configured to determine when to drop late events.

\item \textbf{Flink}:  Real-time streaming processing with latencies in milliseconds. 
	\begin{itemize}
	\item Checkpoints are asynchronous and distributed, enabling lower latency.
	\item Watermarks are special records that trigger event-time-related computations. 
	\item Late events are handled using watermark-related functions.
	\end{itemize}
\end{itemize}

\subsection{9. \underline{Graphs, Graph Data, PageRank}}

Graph data is a fundamental structure used to represent relationships between entities. Consists of two primary components:
\begin{itemize}
\item \textbf{Nodes (Vertices)}: Represent objects or entities (e.g., people, journals, cities).
\item \textbf{Edges}: Relationships between nodes. Undirected (bidirectional) or directed.
\end{itemize}

Graphs used in various domains, e.g. \textit{Information Networks} (journals, citations), \textit{Traffic , Social Networks, Web Graphs} (webpages, hyperlinks between pages).

\subsubsection{Graph Processing}

Graph processing involves analyzing, extracting meaningful insights from graph data. Tasks include finding patterns, measuring centrality, identifying communities. Key operations in graph processing include:
\begin{itemize}
\item Traversal: Exploring the graph by visiting nodes and edges.
\item Search: Finding specific nodes or paths that satisfy certain conditions.
\item Aggregation: Metrics e.g. degree distribution, clustering coefficients. 
\end{itemize}

Graph processing computationally intensive, (interconnected nature of graphs, large-scale datasets). Distributed systems (Apache Spark, specialized graph processing frameworks (e.g., GraphX, Neo4j)) used to handle tasks efficiently.

\subsection{PageRank Algorithm}

PageRank graph algorithm, originally developed by Google to rank importance of webpages in a network, based on link structure. Can be formulated in two primary ways: \textbf{Flow Formulation} and \textbf{Random Walk Formulation}. Additionally, the introduction of teleports addresses issues of dead ends, spider traps.

\subsubsection{Flow Formulation}
In flow formulation, PageRank models distribution of "importance" across nodes (web pages) in a graph. Each page distributes its importance equally among its outgoing links, and the importance of a page is determined by the sum of the importance it receives from other pages.
\begin{itemize}
\item \textbf{Votes}: Links as `votes'. Higher importance page contribute more weight. 
\item \textbf{Recursive}: Importance of page depends on importance of upstream pages.
\item \textbf{Flow Equations}: For a page $ j $, its rank $ r_j $ is given by $r_j = \sum_{i \to j} \frac{r_i}{d_i}$, \\
where $ d_i $ is the out-degree of node $ i $ (number of outgoing links).
\item Example: small web graph with three pages $ y, a, m $:
  \[
  r_y = \frac{r_y}{2} + \frac{r_a}{2}, \quad r_a = \frac{r_y}{2} + r_m, \quad r_m = \frac{r_a}{2}
  \]
  Solving simultaneous equations yields relative importance scores of each page.
\item \textbf{Challenges:} \textbf{Dead Ends}: Pages with no outgoing links cause importance to "leak out." \textbf{Spider Traps}: Pages only linking to self or small group absorb all importance.
\end{itemize}

\centerline{\includegraphics[width=1\linewidth]{simplifiedPageRank}}

\subsubsection{Random Walk Formulation/Interpretation}
PageRank as probability distribution of \textit{random surfer} visiting pages over time. Each step, surfer follows outgoing link uniformly at random with probability $ \beta $ (typically $ 0.8 $ to $ 0.9 $). Teleports to a random page with probability $ 1 - \beta $. (with teleports enabled). As $ t \to \infty $, the probability distribution of the surfer converges to a steady state, corresponds to PageRank scores. \textit{(Stationary Distribution)}.
\begin{itemize}
\item Random walk form mathematically eqv. to flow form. Both define rank vector $ r $ recursively: $r = M \cdot r$,  $ M $ is stochastic adjacency matrix of graph (column-stochastic, all columns sum to one).
\item Teleports ensure convergence, allow surfer to escape dead ends and spider traps.
	\begin{itemize}
	\item \textbf{Dead Ends}: importance leaks out, as matrix is not column stochastic. Make matrix column stochastic by always teleporting when at a dead end.
	\item \textbf{Spider-traps}: importance gets trapped. With teleport, not trapped, as teleport out in finite number of steps.
	\end{itemize}
\end{itemize}

\subsection{PageRank with Teleports}
To address dead ends and spider traps, algorithm incorporates teleports. Ensures random walk always converges to a meaningful, unique stationary distribution, ensuring robust and reliable rankings.

\begin{itemize}
\item \textbf{Modified Equation}: include teleportation term:
  \[
  r_j = \sum_{i \to j} \beta \frac{r_i}{d_i} + (1 - \beta) \frac{1}{N}
  \]
 $ N $: total no. of pages, $ \beta $ controls probability of following links vs. teleporting.
\item \textbf{Google Matrix}: Expressible in matrix form $A$:
  \[
  A = \beta M + (1 - \beta) \frac{1}{N} \mathbf{1}
  \]
  where $ M $ is the column-stochastic adjacency matrix, and $ \mathbf{1} $ is a matrix of ones.
\end{itemize}

\centerline{\includegraphics[width=1\linewidth]{PageRank}}


\subsubsection{Power Iteration Method}
To compute PageRank efficiently for large graphs, power iteration method used:
\begin{enumerate}[itemsep=0pt]
\item \textbf{Initialization}: Start with uniform rank vector $ r^{(0)} = [1/N, \dots, 1/N]^T $.
\item \textbf{Iteration}: Update rank vector iteratively: $r^{(t+1)} = A \cdot r^{(t)}$
\item \textbf{Stopping Criterion}: Change falls below threshold. $\|r^{(t+1)} - r^{(t)} \|_1 < \epsilon$
\end{enumerate}

\subsubsection{Problems \& Extensions of PageRank}
While powerful, PageRank has certain limitations, and extensions.
\begin{itemize}
	\item \textbf{Generic Popularity}: Measures overall importance, but does not account for topic-specific relevance. Use \textbf{Topic-Specific PageRank}, incorporates topic relevance into ranking process.
	\item \textbf{Susceptibility to Spam}: Artificial link structures / topography can manipulate rankings. Use \textbf{TrustRank}, combines PageRank w. trust signals to combat spam.
	\item \textbf{Single Metric}: Relies on a single measure of importance, ignoring other factors like content quality. Use \textbf{Hubs and Authorities}, distinguish pages linking to many important pages (hubs) and pages linked by many important pages (authorities).
\end{itemize}

\subsection{Topic-Specific PageRank}

Evaluate web pages by popularity and how related to particular topic. Enable personalized search results based on user preferences / query context.

\subsubsection{Key Idea: Biasing the Random Walk}
Topic-Specific PageRank: random walk biased to favor pages related to topic:
\begin{itemize}
\item Teleportation is restricted to a \textbf{topic-specific set of relevant pages (teleport set)}. The teleport set $ S $ contains only pages relevant to topic, e.g. pages from Open Directory Project (DMOZ) for a given topic or query.
\item \textbf{Teleports}: When random walker teleports, picks page from set $ S $. For each teleport set $ S $, a different rank vector $ r_S $ is computed, reflecting the importance of pages within that topic.
\item \textbf{Matrix Formulation}: (modify teleportation)
\[
A_{ij} = 
\begin{cases} 
\beta M_{ij} + (1-\beta)/|S| & \text{if } i \in S \\
\beta M_{ij} + 0 & \text{otherwise}
\end{cases}
\]
- $ A $: updated stochastic matrix, $M$: original column-stochastic adjacency matrix.
- $ \beta $: probability of following a link, $|S|$: size of teleport set $ S $.
\item Pages in the teleport set $ S $ are usually weighted equally, but we could also assign different weights to pages in $ S $.
\item As $ \beta $ decreases, influence of teleportation increases, biasing ranks further toward teleport set. Larger teleport sets distribute importance more evenly across the included pages.
\end{itemize}

\subsubsection{Discovering the Topic Vector $ S $}
How do we know teleport set $ S $ in the first place?
\begin{itemize}
\item To create different PageRanks for different topics approach includes using predefined categories e.g. 16 DMOZ top-level categories (e.g., arts, business, sports). 
\item To determine topic ranking to use, base on query or user context: (E.g. user selection, query classification, contextual clues, user context).
\end{itemize}
 
\subsection{PageRank Implementation}
Implementation can be approached through various frameworks, such as Pregel and Spark GraphX, which leverage vertex-centric computation and message passing to process large-scale graphs efficiently. Abstract away complexities of distributed computing, enable focus on algorithm design while ensuring scalability and fault tolerance.

\subsubsection{Characteristics of Graph Algorithms}
\begin{itemize}
\item \textbf{Local Computations}: Each vertex performs computations based on its local state and messages from neighboring vertices. (Distributed computation).
\item \textbf{Message Passing}: Vertices communicate by sending messages to one another. 
\item \textbf{Vertex-Centric Design}: Algorithms implement from vertex perspective, user defines behavior of a vertex in each iteration using a function like \texttt{compute()}.
\item \textbf{Framework Abstraction}: Underlying framework handles scheduling, communication, fault tolerance. Allow users to focus on logic of algorithm.
\end{itemize}

\subsubsection{Pregel: Computational Model}
Pregel is a system for large-scale graph processing that introduces a vertex-centric computational model. 
Key characteristics: 
\begin{itemize}
\item \textbf{Supersteps}: Computation proceeds in a series of supersteps. In each superstep, the \texttt{compute()} function is invoked for every active vertex.
\item \textbf{Behavior of \texttt{compute()}}: Reads messages sent to vertex in previous superstep. Sends messages to other vertices to be processed in next superstep. Updates vertex's value or modifies its edges.
\item \textbf{Termination}: Vertices deactivate themselves by voting to halt. Halted vertex reactivated if receives new messages. Computation halts when all vertices inactive.
\end{itemize}

\subsubsection{E.g.: Compute Max Value {\scriptsize (Across vertices in graph with Pregel)}}
\begin{verbatim}
Compute(v, messages):
  changed = False
  for m in messages:
    if v.getValue() < m:
      v.setValue(m)
      changed = True
  if changed:
    for each outneighbor w:
      sendMessage(w, v.getValue())
  else:
    voteToHalt()
\end{verbatim}

Each vertex compares its current value with incoming messages and updates its value to the maximum. If the value changes, the vertex sends its updated value to its neighbors. If no change occurs, the vertex votes to halt.

\subsubsection{Pregel: Implementation Details}
Pregel's architecture and fault-tolerance mechanisms include:
\begin{itemize}
\item \textbf{Master-Worker Architecture}: Vertices are hash-partitioned across workers. (edge cut).  Each worker maintains the state of its portion of the graph in memory. Each worker maintains the state of its portion of the graph in memory. Messages are buffered locally and sent in batches to reduce network traffic.
\item \textbf{Fault Tolerance}: Periodic checkpointing ensures recovery from failures. Worker failures are detected through heartbeats and recovered by reloading from checkpoints.
\end{itemize}

\subsubsection{PageRank Implementation in Pregel (Pseudocode)}
\begin{verbatim}
Compute(v, messages):
  if getSuperStep() == 0:
    v.setValue(1 / getNumVertices())
  if getSuperStep() >= 1:
    sum =0
    for m in messages:
      sum += m
    v.setValue(0.15 / getNumVertices() + 0.85 * sum)
  if getSuperStep() < 30:
    sendMsgToAllEdges(v.getValue() / len(getOutEdgeIterator()))
  else:
    voteToHalt()
\end{verbatim}

Compute the sum of incoming messages and update the vertex's PageRank value. Send outgoing messages to neighbors by dividing the vertex's value equally among its out-neighbors. Terminate after a fixed number of iterations (e.g., 30).


\subsubsection{Frameworks for Graph Processing}
Several frameworks are designed to handle graph processing efficiently:
\begin{itemize}
\item \textbf{Apache Spark GraphX}: A distributed graph processing framework built on top of Spark. It provides APIs for graph creation, transformation, and analysis. Extends RDDs to support property graphs, provides map-like operations and Pregel-like aggregations. Achieves performance parity with specialized graph systems while integrating seamlessly with Spark's dataflow model.
\item \textbf{Neo4j}: A popular graph database that supports querying and analyzing graph data using the Cypher query language.
\item \textbf{Giraph}: A distributed graph processing system inspired by Google's Pregel, developed by Facebook, designed for large-scale graphs. Can efficiently handle trillion-scale graphs.
\item \textbf{NetworkX}: A Python library for creating, manipulating, and studying the structure of complex networks.
\end{itemize}

\subsection{10. \underline{Delta Lake (Big Data Storage Layer)}}

Delta Lake is an open-source storage layer (Lakehouse) that sits on top of existing distributed file systems like HDFS or cloud storage (e.g., AWS S3). It brings reliability and performance optimizations to data lakes. It addresses the limitations of traditional data lakes by introducing features such as ACID transactions, schema enforcement, and unified batch and streaming processing.

\centerline{\includegraphics[width=1\linewidth]{dataLake}}
\begin{itemize}
\item \textbf{Transactional ACID Guarantees}: Ensures atomicity, consistency, isolation, and durability for read/write operations.
\item \textbf{Full DML Support}: Supports Data Manipulation Language (DML) operations like `INSERT`, `UPDATE`, `DELETE`, and `MERGE`.
\item \textbf{Audit History}: Maintains a log of all changes made to the dataset, enabling time travel and reproducibility.
 \item \textbf{Schema Enforcement and Evolution}: Enforces schema constraints while allowing schema evolution over time.
 \item \textbf{Unification of Batch and Streaming}: Combines batch and streaming workloads into a single processing model.
 \item \textbf{Rich Metadata Support}: Provides detailed metadata for efficient querying and indexing.
\end{itemize}

\subsubsection{Data Lakehouse Architecture}
Delta Lake serves as the foundation for building a \textit{data lakehouse}, combines best features of data lakes and data warehouses:

\begin{itemize}
\item \textbf{Data Lake Benefits}: Cost-effective storage for large-scale data. Flexibility in choosing storage systems, file formats, and processing engines. Support for structured, semi-structured, and unstructured data.
\item \textbf{Data Warehouse Benefits}: Strong ACID guarantees for transactional integrity. (Relational DB). Optimized query performance using metadata and indexing. Schema enforcement for improved data quality.
\end{itemize}

\subsubsection{Layered architecture of data lakehouse {\scriptsize (typically includes:)}}
\begin{enumerate}
\item \textbf{Storage Layer}: Distributed file systems like HDFS or cloud storage (e.g., AWS S3).
\item \textbf{Metadata Layer}: Delta Lake manages metadata, caching, and indexing.
\item \textbf{Processing Layer}: Batch and streaming engines like Apache Spark, Presto, or Flink.
\end{enumerate}

\centerline{\includegraphics[width=1\linewidth]{lakeHouse}}

\subsubsection{Delta Lake Format}
Delta Lake stores data in the \textbf{Parquet format} with additional metadata to support advanced features:
\begin{itemize}
\item \textbf{Parquet Files}: Column-oriented storage for efficient compression and query performance.  Open-source and self-describing, containing both data and metadata (schema and file structure).
\item \textbf{Delta Log}: Transaction log (`DeltaLog`) is a critical component of Delta Lake. It records every transaction made against a Delta table, acting as the "single source of truth." Enables features like ACID transactions, scalable metadata handling, and time travel.
	\begin{itemize}
	\item Transaction Log ensures consistency and reliability in distributed environments. Tracks all changes to a Delta table since its creation, and allows multiple readers, writers to operate on same dataset simultaneously without conflicts.
	\item ACID Transactions: Each operation is recorded in the transaction log. If an operation is not logged, it is considered invalid.
	\item Scalable Metadata Handling: Efficiently manages metadata for large datasets.
	\item Time Travel: Enables querying previous versions of the dataset for auditing or reproducibility.
	\end{itemize}
\end{itemize}

\subsubsection{Breaking Down Transactions into Atomic Commits}
Delta Lake breaks down complex transactions into smaller atomic commits for reliability. Possible Actions in a Transaction Log Entry: 
\begin{itemize}
\item Add File: Records the addition of new data files.
\item Remove File: Marks data files as deleted.
\item Update Metadata: Modifies the schema or other metadata properties.
\item Commit Info: Logs details about the transaction (e.g., timestamp, user).
\end{itemize}
Checkpoint files optimize the transaction log by periodically compacting log entries. Reduces the overhead of reading the entire log for large datasets.

\subsubsection{Advantages of Delta Lake}
\begin{itemize}
\item Reliability: ACID transactions ensure data integrity and consistency.
\item Flexibility: Supports diverse data formats and processing engines.
\item Cost-Effectiveness: Leverages distributed storage systems for scalable and affordable storage.
\item Performance: Optimized metadata handling and indexing improve query performance.
\end{itemize}
Delta Lake bridges the gap between data lakes and data warehouses by providing a unified platform for analytics and machine learning. Its support for ACID transactions, schema enforcement, and scalable metadata handling makes it an ideal choice for modern big data ecosystems. By enabling organizations to build robust data lakehouses, Delta Lake empowers both business intelligence and AI/ML workflows in cloud environments.

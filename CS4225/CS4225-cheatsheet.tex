\section{CS4225/5425 Big Data Systems, Data Science}

(Big) Data science. Interdisciplinary field about processes and systems 
to extract knowledge or insights from data in various forms.
\begin{itemize}
\item \textbf{Processing} diff. types of data (large data volume, graph data, stream data).
\item \textbf{Models of Computation}: MapReduce/Spark, Large graph processing engines, Streams and online algorithms.
\end{itemize}

\subsection{1. \underline{Introduction}}
\begin{itemize}
\item \textbf{Big Data (4 `V's)}: \textit{Volume}: (Scale of data). \textit{Velocity}: (Speed of new (streaming) data).
	\textit{Variety}: (Different types).  \textit{Veracity}: (Accuracy, trustworthiness of data).
\item \textbf{Challenges of 4 `V's}: Performance, Cost, Reliability, Algorithm design complexity. Data integration challenges, multi-modal learning (Variety). Dirty and noisy data, data provenance, uncertainty (Veracity).
\item Big data - Virtuous Product Cycle, where useful service $\rightarrow$ data to analyze $\rightarrow$ insightful action  $\rightarrow$ useful service.
\end{itemize}	


\subsubsection{Utility Computing (Cloud Computing Infrastructure)}
Cloud computing - scalable, elastic infrastructure for big data systems.

\begin{itemize}
    \item \textbf{Utility Computing}: Computing resources as a metered service ("pay as you go"). Ability to dynamically provision virtual machines.
    \item \textbf{Scalable}: ("Infinite" capacity). \textbf{Elastic}: (Scale up or down on demand).
    \centerline{\includegraphics[width=0.5\linewidth]{containers}}
    \item \textbf{How}: \textbf{Virtual Machines (VMs)}: Enable sharing of hardware resources, run each app in isolated virtual machine. High overhead as each VM has its own OS. 
    \\ \textbf{Containers}: Lightweight sharing of resources. Apps run in isolation but share same OS. Container encapsulates an app and environment.
    \item \textbf{Everything as a Service}:
    	\begin{itemize}
	  \item \textit{Infrastructure (IaaS)}: User rents a virtual machine. (e.g. Amazon EC2).
	  \item \textit{Platform (PaaS)}: Provide hosting web apps. Cover hardware maintain, upgrade.
	  \item \textit{Software (SaaS)}:  Pre-built apps. (e.g., Gmail). Covers entire stack.	
	\end{itemize}
\end{itemize}
Data science, cross-disciplinary, emerging research area w. applications in engineering, commerce, etc. Clouds as natural infrastructures for data science.

\subsection{2. \underline{Principles of Big Data Systems}}

\begin{itemize}
\item \textbf{Data Center Infrastructure}
	\begin{itemize}
	    \item \textbf{Single Server}: A commodity hardware unit.
	    \item \textbf{Rack}: Dozens of servers, connect to rack switch (top-of-rack switch).
	    \item \textbf{Data Center}: Hundreds of racks, connect to data center switch (core switch).
	\end{itemize}
\item \textbf{Bandwidth vs. Latency}
	\begin{itemize}
	    \item \textbf{Bandwidth}: Max amt of data transmittable per unit time (e.g., in GB/s). Calculate as minimum bandwidth among all components in the data access path.
	    \item \textbf{Latency}: Time taken one packet travel src to dest (one-way) / round-trip (in ms). Sum of the latency caused by all components in the data access path.
	    \item \textbf{Throughput}: Rate data is actually transmitted in network in given time period.
	\end{itemize}
\item When transmitting \textit{(large/small)} amount of data, \textit{(bandwidth/latency)} - roughly how long transmission will take (bottleneck variable).
\item \textbf{Storage Hierarchy in Data Centers}: based on capacity, latency, bandwidth. 
	\begin{itemize}
	    \item \textbf{DRAM}: Fast but limited capacity. \textbf{Flash}: Intermediate btw. DRAM and disk.
	    \item \textbf{Disk}: Slow but large capacity. Disk reads more expensive than DRAM (higher latency, lower bandwidth).
	\end{itemize}
\end{itemize}


\subsubsection{Data Flow Paths}
Data flow paths depend on the location of the source and destination. Data access may cross several components, e.g. hard disk, DRAM, rack switch, cluster switch.
\begin{itemize}[itemsep = -2pt]
\item E.g. Local DRAM $\rightarrow$ Local Disk in same server.
\item Server A DRAM to server B DRAM in same rack (i.e.  Local DRAM  $\rightarrow$ Rack Switch  $\rightarrow$ Server B’s DRAM)
\item Transfer across different rack, same cluster etc. (i.e. Local DRAM $\rightarrow$ Rack Switch  $\rightarrow$ Datacenter Switch  $\rightarrow$ Server C’s Rack Switch $\rightarrow$ Server C’s DRAM).
\item To load from disk, usually need to load into DRAM first. (i.e. Local Disk $\rightarrow$ Local DRAM $\rightarrow$ Rack Switch etc.)
\end{itemize}
\textbf{Calculate latency, bandwidth based on data flow path}. Approximate order of magnitude, for simplify, assume one-way communication, no failures.

\centerline{\includegraphics[width=1\linewidth]{storageHierarchy}} \smallskip

\textbf{Capacity} increases, \textbf{Costs} (Latency increase, bandwidth decrease) increases from local to rack to data center, along storage hierarchy.


\subsubsection{Building Efficient Big Data Systems}
\begin{enumerate}
    \item \textbf{Scale "Out", Not "Up"}: Horizontal Scaling over vertical scaling. Combine many cheaper machines (out) over increase power of individual machine (up).
    \item \textbf{Seamless Scalability}: Ideal (linear) scalability, performance increases proportionally to added resources. 
    \item \textbf{Move Processing to the Data}: As clusters limited bandwidth; move tasks to machine where data is stored.
    \item \textbf{Process Data Sequentially, Avoid Random Access}: Disk seeks expensive; sequential access provides better throughput.
\end{enumerate}

\subsubsection{Challenges in Big Data Systems}
\begin{enumerate}
    \item \textbf{Machine Failures}: With enough scale, expect daily server machine failure.
    \item \textbf{Synchronization}: Difficult due to unknown order of worker execution, interruptions, and shared data access. Tools like semaphores, conditional variables, and barriers are used to address synchronization issues.
    \item \textbf{Programming Difficulty}: Concurrency hard to reason about, especially at scale. Debugging and managing failures add complexity.
\end{enumerate}
\textbf{API for Data Centers}: Given challenges, "API" of data center abstracts system-level details from developers. Execution frameworks (e.g., Hadoop, Spark) handle task assignment, replication, synchronization, etc.


\subsection{3. \underline{MapReduce}}
Big data requires new prog. abstractions, runtime systems. Hadoop MapReduce widely used for efficient, process large datasets in e.g. databases, data mining. \\
\textbf{MapReduce}: prog. model \& associated runtime system to process large datasets in parallel across distributed cluster. (Parallel $+$ Divide \& Conquer Paradigm). MapReduce provides functional abstractions for two operations.
\begin{itemize}
    \item \textbf{Map function}:  \texttt{(k1, v1) → List(k2, v2)}. Processes each input key-value pair and emits intermediate key-value pairs. 
    \item \textbf{Reduce}: Aggregate intermediate results to generate the final output.  \texttt{reduce(k2, List(v2)) → List(k3, v3)}. All values with same key sent to same reducer.
	\item \textbf{Typical Workflow of MapReduce}: \\
	Iterate over a large number of records. Extract relevant info from each. (\textbf{Map}) \\
	Shuffle and sort intermediate results by key (\textbf{Shuffle}). \\
	Aggregate intermediate results (\textbf{Reduce}). Generate the final output.
\end{itemize}

\centerline{\includegraphics[width=1\linewidth]{mapReduce}} 

\begin{itemize}
    \item \textbf{Worker}: single component of cluster, performs storage, processing tasks.
    \item \textbf{Map Task}: A unit of work, processing one input split (e.g., 128 MB).
    \item \textbf{Map Function}: A call to user-defined map function, for each input split k-v pair.
    \item \textbf{Reduce Task}: A unit of work processing a subset of intermediate keys.
    \item \textbf{Barrier}: barrier between map and reduce phases. Else, reduce phase may compute wrong answer. Shuffle phase can begin copying intermediate data earlier. 
\end{itemize}

\subsubsection{Partition and Combiner}
Optionally specify \textbf{partition, combine} functions, optimize, reduce network traffic.
\begin{itemize}
    \item \textbf{Partition Step}: By default, keys assigned to reducers using hash function (e.g., \texttt{hash(key) \% num\_reducers}). Can implement custom partitioner to balance load among reducers. (E.g. if some keys much more values than others).
    \item Partitioner runs in local write phase, knowledge of which keys to which reducer.
    \item \textbf{Combiner Step}: Combiners locally aggregate map outputs to reduce disk and network I/O. ('mini-reducers') (E.g. Sum counts for each key before write to disk). \textit{Correctness}: Must not affect correctness of final output, regardless of how many times it runs (incld. 0 times). E.g. \texttt{sum}, \texttt{max} ok, but \texttt{mean}, \texttt{minus} not ok.
    	\item Combiner runs after map phase, done during local write phase, before actual disk write to save disk I/O.
\end{itemize}

\textbf{Notes and Other Optimizations}
\begin{itemize}
    \item If reduce task handles multiple keys, will process keys in sorted order.
    \item \textbf{Secondary Sort}: Use this property to sort values associated with key. (reduce work done in reducer by using inbuild distributed sorting process of Hadoop). Combine key and value into composite key e.g. (UserID $\rightarrow$ [UserID-Timestamp]), define custom comparator (sort by ID then timestamp) \& partitioner (group by ID only).
    \item Size of split too big or small:  $\rightarrow$  Limited parallelism vs. high overhead.
    \item \#map fn calls = \# input key-value pairs. \# map tasks = \# input splits.
    \item Reduce function calls = no. of distinct intermediate keys.
    \item \textbf{Preserving State in Map / Reduce Tasks}: In MapReduce, state variables can be used to store information that persists across multiple calls to map() or reduce() functions within same task. Sharing data or resources between function calls. 
\end{itemize}

\subsubsection{General Performance Guidelines (Basic Algorithm Design)}
\begin{itemize}
    \item \textbf{Linear Scalability}: More nodes should enable more work done in same time.
    \item \textbf{Minimize Disk and Network I/O}: Sequential access over random access. Send data in bulk over small chunks.
    \item \textbf{Reduce Memory Working Set}: Avoid large in-memory data structures to prevent out-of-memory errors.
\end{itemize}

\subsection{4. \underline{MapReduce \& Databases}}
\subsection{HDFS: Hadoop Distributed File System}
Distributed file system designed to store, manage large datasets across multiple machines in a cluster. Core component of Apache Hadoop ecosystem (open source), optimized for high-throughput access to big data.

\begin{itemize}
	\item \textbf{Purpose}: handle massive datasets (tb/pb), scalable, fault-tolerant storage.
    \item E.g. MapReduce input, output stored in HDFS (3 copies etc.) Intermediate files on hard disk on local machine though (local fs).
    \item \textbf{Architecture}: \textit{Master-Slave Model}.
    \\ \textbf{NameNode}: Master node, manage file system metadata (e.g., dir structure, file locations, rebalance, heartbeat) - No data moved through NN. If NN data lost, cannot reconstruct files from raw block data. Hadoop has NN backup, checkpointing.
    \\ \textbf{DataNodes}: Worker nodes, store the actual data blocks. \\
    
    \centerline{\includegraphics[width=0.9\linewidth]{HDFSHadoop}} 
    	\item \textbf{Data Locality}: Move computation to data, over other way round. Minimize network traffic, improve performance. Same set of nodes used for both HDFS, Hadoop. Hadoop tries to schedule map tasks run on machines containing data.
    	\item \textbf{Fault Tolerance}: Each block replicated (default: 3 copy) across different DataNodes to ensure reliability. If node fails, HDFS retrieves data from another replica.
    \item \textbf{Rack Awareness}: Aware of physical location of nodes (e.g., which rack). Replicas placed on diff rack, balance fault tolerance, network efficiency. 
	\item \textbf{Block Size}: Files divide to large chunks (default: 128 or 256 MB), reduce overhead. Large block sizes improve sequential read/write perform. ($\uparrow$ throughput).
	\item \textbf{Scalability}: Scales horizontally by adding more machines to the cluster. Supports thousands of nodes and handles large datasets efficiently.
	\item \textbf{Write Once, Read Many}: Files written once, can be read multiple times. Files cannot be modified after written (append-only in some cases).
    \item \textbf{Use Cases}: Store log files, web server data, social media data, etc. Support big data processing frameworks like MapReduce, Spark, Hive, and Pig.
\end{itemize}

\centerline{\includegraphics[width=1\linewidth]{HDFSArchitecture}} 
   
\textbf{Disadvantages of HDFS}: Not suited for small files, inefficient for large no. of small files, due to metadata overhead. High latency, not ideal for real-time or low-latency applications. Limited Random Access: design for seq access, not random reads/writes.

\subsection{Relational Databases DB}
Relational database comprised of tables, each table represents a relation, which is a collection of tuples (rows). Each tuple consists of multiple fields. Develop large-scale relational database using Hadoop / MapReduce.


\subsubsection{Star Schema and SQL Queries}
The Star Schema is a common database schema for data warehousing. Organizes data into single (central) fact table and dimension tables. Fact table linked via foreign key r/s to PK of each dimension. Faster query and simpler queries.

\centerline{\includegraphics[width=1\linewidth]{starSchema}} 

\subsubsection{SQL (Relational) Operations in MapReduce}
\begin{itemize}[itemsep = 0.5pt]
\item \textbf{Projection in SQL/MapReduce}: Projection selects specific columns from table. \\
 (E.g. \texttt{SELECT <columns> FROM Sales}). Only selected columns returned.
	\begin{itemize}
	\item \textbf{Map Phase}: Input: Tuples (t. ID as key), emit tuples (w. only select attributes).
	\item \textbf{No Reducer Needed}: "map-only" job, no need for shuffling or reducing.
	\end{itemize}
\item \textbf{Selection in SQL/MapReduce}: Selection filters rows based on condition. (E.g.  \texttt{SELECT * FROM Sales WHERE price > 10}). Only rows satisfying the predicate (condition) are returned.  MapReduce implementation:
	\begin{itemize}
	\item \textbf{Map Phase}: Input: Tuples (tuple ID as key) emit tuples satisfying predicate.
	\item \textbf{No Reducer Needed}: Similar to projection, this is a map-only job.
	\end{itemize}
\item \textbf{Group By and Aggregation}: Aggregation operations. Shuffle phase is the 'group by'. Framework auto groups tuples by key.
(E.g. \texttt{SELECT product\_id, AVG(price) FROM sales GROUP BY product\_id}). Output avg per product.
	\begin{itemize}
	\item \textbf{Map Phase}: Emit key-value pairs: $\langle \text{product\_id}, \text{price} \rangle$.
	\item \textbf{Shuffle Phase}: Framework groups tuples by key (\texttt{product\_id}).
    \item \textbf{Reduce Phase}: Compute average price for each \texttt{product\_id}. (Same Reducer). Optimize using combiners to reduce network traffic.
	\end{itemize}
\item \textbf{Relational Joins (Inner Join)}: Joins combine data from two tables based on a common key. (E.g. \texttt{SELECT A.Id, A.attr1, B.attr2 FROM A JOIN B ON A.bID = B.bID}) Many-to-many r/s (can appear multiple times in both tables).  
	\begin{enumerate}[itemsep=0pt, topsep=0pt]
		\item \textbf{Broadcast (Map) Join}: Requires the smaller table to fit in memory. Mappers store copy of small table as hash table. Iterate over large table, perform join. (Hash Join. Smaller table 'broadcasted' to all mappers/processing nodes.)
	    \item \textbf{Reduce-side (Common) Join}: Mappers emit records with join key as primary key. Reducers group records by join key. Can use secondary sorting to ensure all keys from one table arrive before the other. Hold keys from first table in memory, cross them with records from second table (to do join).
	\end{enumerate}
\end{itemize}

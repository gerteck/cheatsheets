\subsection{1. \underline{Software Engineering}}
Concerned with all aspects of software production, initial conception to operation and maintenance. Team development of multiversion programs. People at core, code important but only small part of building product.
\begin{itemize}
\item \textbf{Software engineering}: \textit{practicalities} of developing, delivering useful software. Programming integrated over time. Software sustainability to keep software evolvable over time. People as first-order success driver.
\item \textbf{Origins}: 1965s software crisis, Margaret Hamilton coins software eng. Bugs cost - 2022 US \$2.41 trillion, technical debt biggest obstacle to existing codebases. E.g. crowdstrike 2024 outage, DBS 2023, Java Log4J 2021 zero-day vulnerability. Fred B. -- no silver bullet (M. Man-Month). 
\item \textbf{Complexity}: \textit{Essential complexity} - inherent, e.g. work w. stakeholders to determine product. \textit{Accidental complexity} - solvable, e.g. buffer overflow exploitation protection. Hardest single part -- deciding what to build. 
\item \textbf{Techniques to address key challenges}: Address users' needs with software, correctness and reliable, efficiency with limited resources.
\end{itemize}

\subsubsection{Central Software Engineering Activities}
\textbf{Software Specification}: Define functionality, constraints on operation. \\
\textbf{Software Development}: Implement to meet specification. \\
\textbf{Software Validation}: Ensure performance \& requirements met. \\
\textbf{Software Evolution}: Adapts the software to evolving customer needs. \\
\smallskip
“Shifting Left” - more costly to address a defect late in the process. SE processes have been “shifting left”.

\subsubsection{SWE Qualities}
\begin{itemize}
\item \textbf{Personal Pinciples}: Humility (Recognize limitations, self-improvement), Respect, Trust. Thrive in ambiguity, value feedback, challenge status quo, users first. Improving, Passionate, Knowledge about People/Org, Sees Forest \& Trees, Create shared context, Creates safe haven. Working alone increases risks, design mistakes, irrelevance, and "bus factor."
\item \textbf{Software Product Attributes}: \textit{Elegant}: Simple, intuitive designs: easy to understand, maintain. \textit{Anticipates Needs and future requirements}.
\end{itemize}

\subsection{2. \underline{Software Engineering Processes}}
\textbf{Software process model}: rep. of software process (sequence of activities). Illustrates different approaches to developing software.
\begin{itemize}
	\item \textbf{Waterfall Model}:  Simple, linear plan-driven software process model. Output of one phase feeds into the next. Development starts only after req. eng and design. \textbf{Pros/Use Cases}: Embedded-hardware /Safety-critical /Large systems. Works well if requirements clear, large projects, or distributed teams. \textbf{Cons}: accommodate change difficult.
	\item \textbf{Incremental Development}: Overlapping phases of specification, development, and validation. Built in increments, adding functionality. Can be plan-driven, agile, or mix. \textbf{Pros}: Lower cost of accommodating change, faster delivery. \textbf{Cons}: Harder to measure progress, may lead to system degradation (require refactoring). 
	\item \textbf{Integration and Configuration / Reuse-based}: Reuse existing components/framework/library over from scratch. May need redefine reqs. based on identified components. \textbf{Pros}: Reduce amt. to develop, lower cost, risk. \textbf{Cons}: Limit customizatn, third-party dependency, integration complexity.  
\end{itemize}


\subsubsection{Agile Software Engineering}
Agile frameworks (e.g. scrum) not specific to software dev. Designed for changing, unclear requirements and incremental dev, deliver value quickly.
\begin{itemize}
\item \textbf{Agile}: Both mindset and concrete mngmt engineering framework. Focus on deliver value, avoid waste. Feedback loops, customer involvement. Adaptive to change. Lightweight process, empower people, lean manufacturing, buzzword certifications.
\item \textbf{Historical Development and Origins}: 1980-90s: Trad. planning/dev processes. Late 1990s: Dissatisfaction, agile as alternative to rigid waterfall. 2001: Agile Manifesto by reps from frameworks like Scrum, XP, Feature-Driven Development (FDD). Influenced by \textit{lean manufacturing}, \textit{The New New Product Development Game (1986)} -- overlapping stages, built in instability, subtle control, self-organizing teams (autonomy, self-transcendence of teams, cross-fertilization, learning \& learning transfer cross teams).
\item \textbf{Lean software development}: Limit waste (hardship in daily work) -- partially done work, non-value adding processes/features, task-switching, waiting for input, defects, handoff motion.
\item \textbf{Manifesto Principles}:  Individuals \& interactions over processes. Working software over compreh. docs. deliver frequently. Customer collab over contract nego (comms daily), Respond to change over following plan (wlc. changing req.). Working software as progress measure, sustainable development. technical excellence and good design enhances agility, simplicity is essential. regular reflection.
\item \textbf{Agile Adoption }: Larger the org, more likely to use hybrid mode. Bigger teams likely still use waterfall. Agile has concrete benefits - better collaboration, alignment to business needs, better quality software. \textbf{Problems}: business side slow to embrace. Too many mixed systems, siloed teams delays. Incorrect practice, managment buy-in, pain of lacking documentn.
\end{itemize}

\subsubsection{Scrum}
'Agile synonym'. General, lightweight framework for project management. 
\begin{itemize}
	\item \textbf{Core Principles}:  Empirical process control and lean thinking. Focuses on delivering value through increments in sprints.  
	\item \textbf{Scrum Pillars}:  Transparency (work and process visibility), Inspection (frequent evaluation), and Adaptation (adjustments as needed).  
	\item \textbf{Scrum Team}: Self-managing, no hierarchies, typically $\leq$ 10members. \textit{Scrum Master}: Facilitates Scrum process, removes impediments. \textit{Product Owner}: Maximizes product value, manages Product Backlog. \textit{Developers}: Responsible for creating Increment each Sprint.  
	\item \textbf{Scrum Events}:  \textit{Sprint}: Timeboxed iteration ($\leq$ 1 month), deliver working Increment. \textit{Sprint Planning}: Defines Sprint Goal, selects backlog items. \textit{Daily Scrum}: 15-minute daily sync to track progress and adjust plan. \textit{Sprint Review}: Team present results, adjust Product Backlog. \textit{Sprint Retrospective}: Reflect on improvements for future Sprints.  
    \item \textbf{Scrum Artifacts}:  \textit{Product Backlog}: Ordered list of work items aligned with Product Goal. \textit{Sprint Backlog}: Selected items for Sprint w. actionable plan. \textit{Increment}: Deliverable output meeting defn. of Done.  
    \item \textbf{Timeboxing}:  Sprint(S): $\leq$ 1 mnth. S. Planning: $\leq$  8 hrs. Daily Scrum: 15 minutes.  S. Review:  $\leq$  4 hrs. S. Retrospective: $\leq$ 3 hrs.  
    \item \textbf{Kanban Board}: Often used in Scrum to visualize workflow. It helps teams track progress, limit work in progress (WIP), and improve flow (movement of potential value through a system).
    \item \textbf{Definition of Workflow (DoW)}: A shared understanding of how work items flow through the system. Includes \textit{Units of value} (work items or user stories), defined states (stages) work items flow through, policies for how items move through each state. WIP limit controls enforced. 
\end{itemize}

\subsubsection{Extreme Programming (XP)}
Highly influential agile methodology (late 1990s). "extreme" approach to iterative development and best practices. New ver may built several times/day, increments every 2 wks, All tests successful for accepted builds.
\begin{itemize}
\item \textbf{Pair Programming}:  One dev programming, other review, focus on big picture. (driver \& navigator). Both can think and interact at same level of 
interaction. If one greater expertise likely to dominate interaction. Switch roles after a time period, and switch partners frequently. \textit{Pros vs Cons}: Fewer bugs, better code understanding, peer learning, but lower cost / scheduling efficiency, personal clash.
\item \textbf{Collective Ownership}:  Everyone responsible for all code, anyone can change any code. Pair prog facilitates this, as everyone better 
understands larger system, contribute to different parts of code.
\item \textbf{Test-driven development}: Unit tests written before code, test all potential fail cases. helps development, facilitates other CI, refactoring etc.
\item \textbf{Continuous Integration}: Dev team work on latest ver. Integrate code to main branch freq. Facilitate using unit tests. (GH Actions, Jenkins).
\item \textbf{Simple Design, Refactoring}: “simple is best”, refactoring as part of the lifecycle, keep it maintainable, easier to extend.
\item Others: on-site customer for access system requirements, sustainable pace for net effect on code quality / long term productivity.
\end{itemize}

\subsubsection{DevOps}
In incremental development, challenge software deployment quickly \& reliably. Involves collaboration btw. dev (scrum teams) \& operations teams.

\begin{itemize}
    \item \textbf{DORA (DevOps Research and Assessment)}: Framework for measuring and improving DevOps performance through key metrics like deployment frequency, lead time for changes, change failure rates, mean time to recovery. \textit{Observability and Monitoring} for measuring DevOps performance. Monitoring of running code and infrastructure provides insights to optimize the value stream.
    \item \textbf{Silos}: Traditionally, dev and ops teams separated, conflicting goals. Developers focus on delivering features quickly, while operations prioritize stability and uptime. DevOps bridges gap by fostering collaboration.
    \item \textbf{DevOps Overview}: Unified approach, emphasize automation, collaboration, continuous delivery. Popularized $~$2010, aims for routine, predictable deployments. \textit{DevOps vs. Agile}: Agile focus on iterative dev, deliver value, DevOps extends by automating deployment pipeline. Emphasis on CI, delivery, feedback loops. ''Infinite loop'' of dev and ops.
    \item \textbf{DevOps Principles}: \textit{Flow}: Reduce batch sizes \& handoffs (work passing across depts/teams) to streamline delivery. \textit{Feedback}: Fast feedback loops to detect, resolve issues early. \textit{Continuous Learning}: Promote experimentation, learning, mechanisms to share knowledge. Safety culture.
        \item \textbf{Learning from Incidents}: Encourages \textit{blameless postmortems} to investigate failures, implement preventive measures. Fosters culture of experimentation and learning.
       \item \textbf{Value Stream Mapping}: Technique to visualize and analyze the flow of work, identifying inefficiencies and improving delivery processes. (E.g. develop unit test $\rightarrow$ code solution $\rightarrow$ PR reviews $\rightarrow$ QA $\rightarrow$ regression, performance test $\rightarrow$ deploy $\rightarrow$ smoke test $\rightarrow$ UAT test)
    \item \textbf{Continuous Integration and Deployment (CI/CD)}: Automates the integration, testing, and deployment of code changes, enabling frequent and reliable releases (push to production). \textit{Infrastructure as Code}: Treats infrastructure configuration like code, using version control, automation to manage servers and environments.
\end{itemize}

\subsection{3. \underline{Software Requirements Engineering}}
Functional vs. Non func. Req. Quality Attribute Scenarios. Elicitation \& Analysis. Documentation. Validation. Process Models. Change Mngmt.
\begin{itemize}
	\item \textbf{Requirements} describe services system should provide, constraints on its operation. Reflect customer needs for systems w certain purpose e.g. device control, order placement, or information retrieval.
    \item \textbf{Requirements Engineering (RE)}: Process of discovering, analyzing, documenting, and validating these services and constraints. RE focus on problem space, not solution space.
    \item \textbf{Wicked Problem}: No definitive formulation or stopping rule, solutions not true/false but better/worse, no immediate/ultimate test for solutions. Every solution is a "one-shot operation" with significant consequences. Each problem is unique, often a symptom of another problem. No exhaustive set of potential solutions or permissible operations. Social planners are accountable for the consequences of their actions.
\end{itemize}	

\subsubsection{Requirement Engineering (RE), Why \& Challenges}
\begin{itemize}
	\item \textbf{High Cost of Errors}: Errors during requirements phase costly.
    \item \textbf{Importance of RE}: Facilitates communication between stakeholders. (\textit{Customer Relations and Communication}). Provides the foundation for defining structure, behavior of software system. Serves as basis for testing, accepting final product. (\textit{QA, Acceptance}) Dictates quality of system, risks, and operational overhead. (\textit{Maintenance and Evolution})
    \item \textbf{RE Challenges}: Difficult to determine if all relevant requirements are collected. Requirements engineering is resource-intensive, often one-shot effort. Requirements cannot be generalized.\\
    • \textit{User-Related}: conflicted views, incomplete understandg of needs, limits.\\
    • \textit{Analyst-Related}: Poor problem domain knowledge, omit "obvious" info. \\
    • \textit{Communication}: Requirements evolve w. time, Ill-defined system boundary. Vague, untestable requirements ("user-friendly," "robust").
    \item \textit{NaPiRE} (RE pains): Incomplete/hidden req, comm. flaws, time-boxing (not enough time), moving targets, inconsistent/underspecified req...
\end{itemize}

\subsubsection{Functional vs. Non-Functional Requirements}
\begin{itemize}
	\item \textbf{Functional Requirements}: Describe what system should do. Stakeholders typically focus on functionality, not determine system architecture. (any functionality implementable using various designs.)
    \item \textbf{Non-functional Requirements}: Define system qualities, not specific services (e.g., performance, security, usability). Often more critical than FRs, may involve implicit stakeholder expectations. Can conflict (e.g., security vs. usability). Influence architectural tradeoffs (e.g., \textit{quality attributes}).
    \item Non-functional requirements should be quantitative to be testable. E.g. ("throughput suff. high." vs. "throughput to exceed 1,000 query/sec")
    \item \textbf{Quality Attribute Scenarios}: framework to clarify, document NFRs. Up to 6 elements: (\textit{Stimulus}: An event arriving at the system. \textit{Source}: Origin of stimulus (e.g., human, system), \textit{Artifact}: part of system affected by stimulus, \textit{Response}: system's reaction. \textit{Response Measure}: Quantifiable metrics for response. \textit{Environment}: scenario context).
\end{itemize}

\centerline{\includegraphics[width=1\linewidth]{QAScenarios}}

\textbf{Other Non-Functional Requirements and Metrics}
\begin{itemize}
    \item \textbf{Usability}: How easily users accomplish tasks, support provided. \textit{Metrics}: Task time, errors no., learning time, satisfaction.
    \item \textbf{Availability}: System readiness to perform tasks, including reliability and recoverability. \textit{Metrics}: Availability \%, time to detect/repair faults, etc.
    \item \textbf{Performance}: System responsiveness and throughput. \textit{Metrics}: Latency, throughput, jitter, resource usage, etc.
    \item \textbf{Modifiability}: The cost and effort of making changes to the system. \textit{Metrics}: Effort, elapsed time, new defects introduced, etc.
    \item \textbf{Deployability}: The ease of deploying and rolling back system changes. \textit{Metrics}: Cost, percentage of failed deployments, cycle time, etc.
    \item \textbf{Energy Efficiency}: System efficiency in energy usage (e.g IoT, AI).
    \item \textbf{Security}: Protecting data and systems from unauthorized access. (CIA Triad) \textit{Metrics}: Accuracy of attack detection, size of trusted execution 
    \item \textbf{Data Security and Privacy}: PDPA (Singapore), GDPR (EU).
    \item \textbf{Safety}: Avoiding system states that cause harm or damage.  \textit{Metrics}: Percentage of unsafe states avoided, recovery time, etc.
\end{itemize}


\subsubsection{Stakeholders and Requirements Engineering (RE) Activities}
 RE processes vary based on the organization and project type. \\
3 Cs of user stories map to key activities:   \\
\centerline{Elicitation and analysis $\rightarrow$ Conversation (w. client).} 
\centerline{Specification $\rightarrow$ Card (description).}
\centerline{Validation $\rightarrow$ Confirmation (acceptance tests to determine completeness).} \smallskip
\textbf{Agile vs. plan-driven approaches} overlap in elicitation but differ in emphasis: Agile focus on iterative feedback, collaboration. Plan-driven emphasize detailed specification and validation. \\ \smallskip
\textbf{SRS: Software Requirements Specification}: Central document, official statement of what should be implemented. May include user requirements, detailed specification of system requirements. Output of RE phase. \\ \smallskip
\textbf{Stakeholders}: person/org impacted / influencing system’s req. \textit{Identify stakeholders} as first step in RE, determines whose needs /desires addressed. Start with "baseline" stakeholders (e.g., users, decision-makers). Explore network to identify add. stakeholders.
 
\begin{itemize}
    \item \textbf{Elicitation and Analysis}: Work w. stakeholders to get requirements. Elicitation techniques: (Closed/Open Interviews, Existing Docs Analysis -- prior research reduces interaction time, (user-story) workshops -- multiple stakeholders \& resource intensive, FGs (users), prototyping, observe -- discover implicit req. reflecting actual ways, personas). Supports user stories.
    \item \textbf{Specification}: Convert req. into standardized form (user-centric view). \\
     \textit{User Stories}: represent. customer requirements ($<$As `usertype', want `goal', to `reason'.$>$) Three Cs - card, convo, confirm. Epics -- too large user stories to be split later. Include notes, NFRs (constraints). \\
    \textit{Use Cases}: interaction btwn actor \& system (e.g. check in flight). UML $\rightarrow$ use case diagram. May encompass multiple scenarios (single instance of usage e.g normal flow, crash, others etc). Natural Language -- use standard format, consistency, associate rationales, avoid jargon.
    \item \textbf{Validation}: Ensuring requirements accurately define the desired system. (Agile: freq comm. w stakeholder, Plan: unclarities in req. document). \textbf	\textbf{Techniques}: \textit{Informal Reviews}: Peer review, colleague reviews requirements. Informal feedback collection (e.g., deskchecks, passarounds, walkthroughs). \textit{Formal Reviews/Inspections}: Systematic analysis by a team of reviewers, roles: Moderator, reader, inspectors. Techniques: Defect checklists, requirement-by-requirement reviews. 
    \item \textbf{Requirement document checks}: \textit{Validity}: reflect real user current needs. \textit{Consistency}: Avoid contradictory req. \textit{Completeness}.  \textit{Realism}: feasible, within budget, tech constraints. \textit{Verifiability}: testable.
\end{itemize}

\subsubsection{Other Requirement Engineering Validations}
\begin{itemize}
    \item \textbf{Feasibility Study}: short study to assess: alignment with organizational objectives, budget and schedule, Integration with existing systems.
    \item \textbf{Prototyping}: Develop quick version of the system to validate requirements and design decisions. Reduces post-delivery changes by allowing users to experiment early.
    \item \textbf{Use Cases vs User Stories} (Use Cases -- Plan-Driven): Specify functional requirements and serve as test bases. (User Stories -- Agile): Act as placeholders for implementation, elaborated into acceptance tests.
    \item \textbf{Requirements as a Basis for Testing}: Requirements should be testable and used to derive test cases. User stories, cases as foundations for acceptance tests.
    \item \textbf{V-Model and Testing}: In plan-driven approaches, requirements validation aligns with testing phases in the V-Model.
\end{itemize}

\subsubsection{Requirement Engineering Process Models}
\textbf{Agile Approaches}: Agile avoids detailed requirements documents due to rapid changes. Relies on user stories and frequent stakeholder feedback.
Short supporting documents may still define business and dependability requirements. \\

\textbf{Plan-Driven Approaches}: Follow a structured process model. RE phase is completed before implementation. Produces a requirements document, often part of the development contract.
\begin{itemize}
    \item \textbf{User vs. System Requirements}: UR: High-level, natural language descriptions of system services and constraints. SR: Detailed descriptions of functions, services, and operational constraints.
    \item \textbf{RE Spiral Model}: iterative, plan-driven RE process model. Expands requirements incrementally, focusing on high-level business needs early and detailed system requirements later. Outputs SRS. Can incorporate agile development in later iterations.
    \item \textbf{RE Elicitation and Analysis Model}: \\
     \textit{Requirements Discovery} (Interact w. stakeholders to uncover needs) $\rightarrow$ 
    \textit{Classification and Organization} (Group req. to coherent clusters) $\rightarrow$
    \textit{Prioritization and Negotiation} (Resolve conflicts, prioritize req) $\rightarrow$
    \textit{Documentation} (Record requirements for next iteration) $\rightarrow$ (repeat)
    \item \textbf{Requirements Change Management}: \\
    \textit{Established Plan for to manage evolving requirements.} \\
    Unique identification of requirements (to cross-reference). \\
    Established change management process to assess impact and cost. \\
    Traceability policies to link requirements to design. \\
    Tool support for managing requirements
\end{itemize}

\subsection{4. \underline{System Modeling and Software Architecture}}
Abstractions. Modeling Perspectives. UML. C4. Different Architecture Structures, Drivers, Patterns, Tactics.

\subsubsection{Systems Modeling}
Develop abstract models of a system, usually some graphical notation based on diagram types in Unified Modeling Language (UML). \\
Means to an end (developing software). 
\begin{itemize}
	\item Emphasized in plan-driven development, also used in agile in lightweight manner (“just enough” design).
	\item Formal models (mathematical) can be developed for auto verification.
       \item Models are created during requirements eng, system design, and post-implementation documentation.
       \item \textbf{Abstraction vs Representation}: Abstraction simplifies systems, omits details. Representation maintains all system information.
       \item \textbf{Different perspectives}: External, Interaction, Structural, Behavioral.
\end{itemize}

\subsubsection{Modeling Languages}
Unified Modeling Language (UML, most known, rich tool support, stand. notn), C4, BPMN, SysML, etc.  \\ 
\smallskip
\textbf{UML Key Diagrams}:
\begin{itemize}
  	\setlength\itemsep{-0.1em}
	\item Class Diagrams: Show object classes and associations.
	\item Sequence Diagrams: Show interactions btw. actors \& components.
	\item Activity Diagrams: Show process or data flow activities.
	\item State Diagrams: Show system reactions to events.
	\item Use Case Diagrams: Show interactions btwn system \& environm.
\end{itemize}

\smallskip
\textbf{C4 Model}: Agile Architectural Modeling. For software architectures. Do "just enough" design / upfront thinking for starting point/ general direction.
\begin{itemize}
	\item Hierarchical architectural modeling (4Cs): System Context, Containers, Components, Code. Notation Independent.
\end{itemize}
    
\begin{itemize}
        \item \textit{System Context diagram} $\rightarrow$ starting point, how software fits into world.
        \item  \textit{Container diagram} $\rightarrow$ software system, high level building blocks.
        \item  \textit{Component diagram} $\rightarrow$ individual container, decomposes containers to identify major structural building blocks (i.e., components). Not recommended unless level of detail adds value.
       \item  \textit{Code diagram} (e.g. UML class) $\rightarrow$ indivdual component implementation. Not recommended for C4 / Agile context use.
\end{itemize}

\subsubsection{Software Architecture}
The overall structure of a system, including components, relationships, and properties.  How devs explain system at high level. 
\begin{itemize}
	\item S. Architecture vs S. Design: Software Architecture is part of design, focusing on high-level structures. Design (e.g. detailed class design)
	\item Influences quality attributes, modifiability, and communication among stakeholders. Mitigate highest priority risks. Difficult to change later.
      \item \textbf{Architectural Drivers}: Architecturally Significant Requirements (ASRs): Requirements that significantly impact architecture. Non-functional req. (e.g., availability, performance) are often ASRs. Functionality must have major influence on architecture. (E.g. the system should provide five nines (99.999 percent) availability). 
\end{itemize}
Often, system architec. modeled informally w. simple block diagrams.

\subsubsection{Architectural Reasons and Consequences}
\begin{itemize}
    \item \textbf{Quality Attributes}: Architecture significantly influences whether system meets quality attributes (non-functional requirements). (E.g. \textit{High Performance} -- require managing time-based behavior and shared resource access, \textit{Safety and Security}... )
    \item \textbf{Modifiability and Change}: Modifiability is a critical quality attribute. Requires assigning responsibilities to components to limit the impact of changes.
    \textit{Categories of changes}: Local -- affect only single component, Non-local -- Affect multiple components (e.g. UI). Architectural Change -- Affects entire system (e.g., single-thread to multi-thread). Good architecture ensures most changes local or non-local.
    \item \textbf{Communication Among Stakeholders}: Architecture as common abstraction for mutual understanding, negotiation, and consensus.
    \item \textbf{Additional}: Enables reasoning of cost, schedule, basis for reusable models in product lines, focuses on component assembly, channels developer creativity by restricting design alternatives, foundation for training new team members, enable early prediction of system qualities, defines constraints for subsequent implementation, influences org structure (Conway’s Law), supports incremental dev.
    \item \textbf{Conway’s Law}: Organizations design systems that mirror their communication structures -- Arch. often forms basis for work-breakdown structures.
\end{itemize}

\subsubsection{Architecture Patterns and Tatics}
Design is complex activity, architecture is a tradeoff of attributes. \\
\textit{Architectural tactic}: design decision that influences a quality attribute.
\begin{itemize}
\item \textbf{Attribute-Driven Design (ADD)}: Systematic approach to architecture design. Each design iteration, address an ASR. \\
\textbf{Steps}: Identify ASRs $\rightarrow$ establish iteration goals (satisfy set of ASRs) $\rightarrow$ refine structure $\rightarrow$ select designs $\rightarrow$ instantiate patterns $\rightarrow$ record decisions $\rightarrow$ analyze designs.
\end{itemize}

\textbf{Architectural Patterns}
\textit{Established architectural solution, may comprise multiple architectural tactics.} Often found useful over time/domains, documented and disseminated.
\begin{itemize}
\item \textbf{Antipattern -- Big Ball of Mud}: Common in practice. Lack of architectural design, Business pressure, Erosion of architecture over time. 
Poor maintainability, extensibility (Quality Attributes)
\end{itemize}

\subsubsection{Common Architectural Patterns}
\begin{itemize}
	\item \textbf{Layered Architecture}: Structures systems into layers with defined interfaces. Layer only uses layer directly beneath, through public interface. (constraints may be violated e.g. for performance, layer bridging, upper layer use deeper lower layer). \\
	 \textit{Pros}: portability (to diff env/OS), modifiability (lower layers changeable under hood, less interfaces to understand), reuse\\
	 \textit{Cons}: Layering possible performance penalty. If not properly designed, can impede (missing nec. low level abstraction needed at higher level).
	 
      \item \textbf{Pipe-and-Filter}: Processes data through independent filters connected by pipes. \textit{Filters}: processing components, take input, produce output, no assumption on other filters, stateless. \textit{Pipes}: connect multiple filters with each other. (E.g. MailMan - add header, digest, archive, outgoing). \\
      \textit{Pros}: modifiability (independent filters) and reconfigurability, evolution (add/combine filers differently) \\
      \textit{Cons}: format data transfer must be set. performance as every filter must parse input convert to output format.
      
      \item \textbf{Model-Centered}: Independent components interact with a central model than each other. Repository style. (E.g. IDEs). \\
      \textit{Pros}: components can be independent. highly modifiable. concurrency. State/data manged consistently (in one place).  \\
      \textit{Cons}: model/repo is single point of failure. change to model $=$ many changes. Distributing repo can be difficult. \\  \\
      \textbf{MVC design pattern}: ''instantiation" of model-centered, goal of MVC to separate model (business logic) from UI (controller/view).
      
      \item \textbf{Microkernel (Plug-in)}: Base system with plug-in components (e.g., Eclipse SDK, web browsers). \\
      \textit{Pros}: modifiability, extensibility, testability. Plugins can be developed, tested, evolved by diff. teams independently. \\
      \textit{Cons}: can introduce security /privacy vulnerabilities \\
      
      \item \textbf{Client-Server}: central server, provide service to multiple distributed clients. Client request service, server cannot initiate. (E.g. web server) \textit{Discovery}: client use discovery service, server respond w. agreed protocol. \textit{Interaction}: client sends request, server process, respond.   \\
      \textit{Pros}: Low coupling btwn server clients, no coupling among clients. Easily scale no. clients and server. Both can evolve indptly.

      \item \textbf{Microservices}: Independently deployable services communicating via APIs. Typically stateless, small teams, small code bases. Service dependencies acyclic. Popularized by large companies. Goal - decoupling, microservices expected to be independent w own domain/workflow. typically smaller than services in SOA. \\
      \textit{Pros}: quick time to market, indiv. deployability, test, scalability. \\
      \textit{Cons}: network comm. overhead, complex transactions, challenge in design /maintain sea of microservices\\
\end{itemize}

\subsection{5. \underline{Software Testing}}
Test levels. Flaky tests. Specification-based/Structural/Mutation testing. \\

\smallskip 
 
\textbf{Purpose of Testing}: \textit{Defect Testing}: Find bugs in software. (Tests show presence, but never absence.) \textit{Validation Testing}: Ensure system meets user requirements.

\begin{itemize}
	\item \textbf{Verification vs. Validation}: 
		\textit{Verify}: Build product right, conforms to specification. 
	       \textit{Validate}: Build right product, software meets user needs.
	\item \textbf{Test Case}: A test case consists of: 
		\textit{Test Input}: Arguments, system state, or actions, \textit{Test Oracle}: Mechanism, determine test pass or fail.
    \item \textbf{Test Oracle}: Can check functional properties (e.g., correctness) or non-functional properties (e.g., performance, security).
    \item \textbf{Manual vs. Automated Testing}: \textit{Automated}: Use tools to auto generate inputs and apply oracles (e.g., JUnit). \textit{Manual}: Tester manually inputs test cases and acts as oracle. (`Traditional' -  auto as in test automation).
    \item \textbf{Pesticide Paradox}: `Every method used to prevent/find bugs leaves residue of subtler bugs which those methods ineffectual'. Diff testing methods have pros, cons. Use many, similar to pests build immunity. (Law of diminishing return).
    \end{itemize}

\subsubsection{Testing Levels}
\begin{itemize}
    \item \textbf{Unit Tests}: Test indiv. components (e.g., single method or class, e.g. testing a method converting AST to string). 
    	\textit{Pros}: Fast execution, easy control \& write (no additional setup  of (e.g., no DB, web services). \\
    	\textit{Cons}: Lack realism, don’t represent real system execution. May miss integration bugs, often require mocks to simulate ext. dependencies.

    \item \textbf{Integration Tests}: Test interactions btw. multiple compnt. Focus on integrating target cmpnt. w. external cmpnt. (e.g., ext DB, web service).
    (e.g. SQLancer test query plan converted to expected internal repnstn.)

    \item \textbf{System Tests}: Test entire system as whole. \textit{Pro}: realistic test env. \textit{Cons}: slower execution, harder to write  (complex setup), prone to flakiness (non-deterministic results). (e.g: Ensuring SQLancer compatibility with database system.)

    \item \textbf{Test Flakiness}: Pass/fail non-deterministically. Low result confidence. \\
    \textit{Causes}: Concurrency issue (e.g., race conditions), async waits (e.g., not properly waiting for server responses), test order dependencies (e.g., improper cleanup), test timeouts, resource leaks. (e.g, test fail from \texttt{ConcurrentModificationException} in multi-threaded code.)

    \item \textbf{Test Pyramid}: strategy for balancing test granularity. Many small, fast unit tests. Fewer integration, system tests.
	 \textit{Antipatterns}: Too many high-level tests, slow execution, maintenance challenges.
\end{itemize}
\centerline{\includegraphics[width=0.9\linewidth]{testPyramid}}
\begin{itemize}
    \item \textbf{Test Sizes at Google}: Tests classified by size to for efficiency, determinism. \\
     \textit{Small}: Single process/thread, no I/O, fast, deterministic. \\
      \textit{Medium}: Multiple processes, allow localhost network calls. \\
      \textit{Large}: No restrictions, slower, less deterministic.
\end{itemize}

\subsubsection{Testing and Processes}
\begin{itemize}
    \item \textbf{V-Model}: extension of waterfall model. Testing is planned alongside RE, archi, design phases. (E.g. acceptance test derived during RE).
    \item \textbf{User Accept Testing}: validate system meets user req, w customer participation. In \textit{plan driven}, explicit phase after system implementation. In \textit{agile}, UAT is interleaved (e.g., acceptance criteria in user stories).

    \item \textbf{Test-Driven Development (TDD)}: Emphasized by XP. Use as design process, focus `happy path'. 
    	\textit{Pros}: Focus on req, provide quick feedback. Encourages testable code, allows incremental exploration. 
    	\\ \textit{Steps:} Write test $\rightarrow$ ensure fails $\rightarrow$ simplest code to pass $\rightarrow$ refactor.
	\\ \textit{When to Use}: Useful for complex prob, unclear soln (incremental experimentation). Less useful if solution already clear. \\
	Schools of thought: (Classicist/Detroit, Inside-out start e.g. business rules $\rightarrow$ UI). (London/Mockist Outside-In: Start outside, use mocks).

    \item \textbf{Black-box vs. White-box Testing}: 
    	\textit{Black-box `specification testing'}: No internal info, based on requirements or function documentation.
	\textit{White-box `structural testing'}: Internal info, focus code structure, logic.
\end{itemize}

\subsubsection{Black-box Testing}
\begin{itemize}
    \item \textbf{Specification-based Testing}: Derive from requirements (e.g., user stories, use cases, docs). Functional \& non-functional requirements. \\
	 \textit{Testing Workflow}: Understand requirements (inputs, outputs), explore program (functionality), identify partitions (eqv classes of input/output), analyze boundaries, devise and automate test cases, augment test suite with creativity, experience on common bugs.
    \item \textbf{Equivalence Partitioning}: Divides inputs into equivalent classes (e.g., null, empty, single-char string). Output partn may help spot input partn.
    \item \textbf{Boundary Value Analysis}: Tests edge cases (e.g., min/max).
\end{itemize}

\subsubsection{White-box Testing}

\begin{itemize}
    \item \textbf{Structural Testing}: use source code to guide testing. Catch requirement independent implementation aspect (e.g. cache, DSA). Focus coverage criteria.  (e.g. Jacoco basic Java line coverage.)
    \item \textbf{Coverage Criteria}: \textit{Line Coverage} (percentage executed). \textit{Branch, Condition Coverage}: Percentage of branches (if [true/false], fors, whiles), ($a || b$) executed. Condition coverage does not imply branch coverage. \textit{Path Coverage}: Strongest criterion. Often impossible (e.g. loop).
    
    \item \textbf{Modified Condition/Decision Coverage (MC/DC)}: \\
     Test impt combinaton of cond, less cost.= $\frac{\# \text{conditions independently affecting decisions}}{\text{total \#conditions}}$. \\ 
      Every condition in a decision (e.g., if ($A \&\& B$)) takes every possible outcome ($T$ and $F$).
      Ensures conditions independently affect decision outcome. Final set of tests, less than needed for path coverage. ($n+1$ test cases common lower bound for $n$ conditions).
    \end{itemize}

\centerline{\includegraphics[width=1\linewidth]{MCDC}}

\begin{itemize}
\item \textbf{Mutation Testing (White-box)}: Evaluate test suite quality by introducing bugs (mutants) and checking if tests detect them. (test case should 'kill' mutant - fail the test case). \% of bugs detected $=$ quality of test suite. \\
\textbf{Steps}: Select statement in code, mutate code, run test suite, record outcome. Undo change, repeat. Calculate mutation score: \(\frac{\text{\#killed mutants}}{\text{\#mutants}} \times 100\). \\
(e.g. Pitest: Mutation testing tool for Java.). \\
	\textit{Pros}: Identify undertested code.\\
	\textit{Cons}: Comptn expensive; equivalent mutants may not change behavior.
\end{itemize}

\subsection{6. \underline{Debugging and Fault Localization}}
Scientific Method to Debugging (Systematic Approach). Statistical Fault 
Localization. Input Reduction. Isolating Bug inducing Changes. \\
\textit{Mainly, build mental model to approach debug from different angles, and some techniques useful as tools (e.g. reduction tools).}

\subsubsection{Debugging}
Software developers spend 35–50\% of time validating, debugging software. Est. cost of debug, test, verification up to 50–75\% project budget. Identify systematic, effective approaches, enhance productivity. 
\begin{itemize}[itemsep=-1pt]
\item \textbf{Shifting Left}: Debug during software development (e.g., due to failing tests or static analysis reports), but also after deployment (user reports).
\item \textbf{How NOT to approach debugging}: Can change code and try until works. But if don't understand underlying cause, may not fix bug’s root cause.
\item \textbf{Typical strategy to debug?}:
\begin{itemize}[itemsep=-1pt]
	\item \textbf{Printf debugging}: Simple, intuitive, language tool agnostic. But can quickly be confusing, forget to remove print, may require recompilation.
	\item \textbf{Logging}: More systematic alternative to print statements. Multiple debugging levels supported (E.g. INFO, WARN, ERROR, FATAL).
	\item \textbf{Debugger}: Language-specific debugger. Set breakpoints, stepping in/over/out methods, stepwise execution, inspect program state (variables, stack trace.) Can be more systematic, display more info, set breakpoints properly. However, still require strategy with debuggers.
\end{itemize}
\item Challenges: Program states very large, challenging to search all manually. Not clear if (intermediate) states correct or not. Execution could have millions of steps. Hence, need good debug strategy to focus search.
\end{itemize}

\textbf{Fault vs. Defect vs. Failure}:
\begin{itemize}[itemsep=-1pt]
\item \textbf{Fault}: Location of flaw in code, causes incorrect behavior/unwanted state.
\item \textbf{Defect (Bug)}: Manifestation of fault in software. (Error in program code)
\item \textbf{Failure}: Deviation of behavior from expected output. (Externally visible)
\end{itemize}
Through unit test, observed a failure. In order to debug the failure, we need to trace it back to the defect that caused the first fault.


\subsubsection{Scientific Method to Debugging}
Systematic process of identifying faults. Basically, observe failure, generate hypotheses on cause, test hypotheses by experiment (e.g., add debug , assert statements). Refine or confirm hypotheses based on results.
\begin{enumerate}[itemsep=-1.5pt]
\item Formulate a question.
\item Come up w. hypothesis based on knowledge obtained while formulating question, that may explain observed behavior.
\item Determine logical consequences hypothesis, formulate prediction that can support or refute hypothesis. Ideally, prediction would distinguish hypothesis from likely alternatives.
\item Test prediction (and thus hypothesis) in experiment. If prediction holds, confidence in the hypothesis increases; 
otherwise, it decreases.
\item Repeat Steps 2–4 until no discrepancies between hypothesis and predictions and/or observations.
\end{enumerate}
\begin{itemize}
\item \textbf{Scientific process Theory}: a hypothesis that is consistent with earlier observations, predict future obsv (program behavior). $\rightarrow$ Diagnosis.
\item \textbf{Diagnosis} (Debugging): explains both causality, (how failure came to be), and incorrectness (how to correct the code accordingly), then it is time to actually fix the code accordingly.
\end{itemize}
For complex issues, might have days/weeks to debug, systematic debugging strategy is useful. Also helps to systematically log and create a table etc.  \\ \smallskip
\textbf{Rubberducking}: Explaining code line-by-line to an inanimate object (or another person) to identify logical errors or misunderstandings.

\subsubsection{Program Slicing}
Identifying parts of the program (slice) that influence/ are influenced by specific variable/ statement. Automatically determine which earlier variables influenced the current erroneous state.
\begin{itemize}[itemsep=-1pt]
\item \textbf{Definition}: Slicing extracts a subset of program that potentially affects variables/ values at specific program location. A slice identifies the subset of the program that could have influenced the variable/returned value.
\item \textbf{Tracking Origins}: Start with faulty state (failure), trace origins to earlier states. Identify if origins faulty or correct. Continue tracing till faulty state with only correct origins found, indicating the defect.
\item \textbf{Advantages}: Narrows scope of debugging, rule out locations that cannot have effect on failure. Bring together possible origins that may be scattered across code. AKA helps consolidate scattered dependencies into a single, manageable view.
\item \textbf{Types of Dependencies}: \textit{Data Dependency}: Variable's value depends on prior variable. (e.g. fn params). \textit{Control Dependency}: Execution of statement depends on condition. Can reason using program dependence graph.
\item \textbf{Static vs. Dynamic Slicing}: \textit{Static Slicing}: Considers all possible executions of the program. (e.g. include whole method, both if and else branch). \textit{Dynamic Slicing}: Focuses on a specific execution path based on concrete inputs. (e.g. only consider if branch, as else branch not executed).
\item \textbf{Forward vs. Backward Slicing}: \textit{Backward Slicing}: Identifies what influenced a particular value. \textit{Forward Slicing}: Identifies what statements are influenced by a particular value.
\end{itemize}
Slicing applications: As mental model, some support in IDEs, papers published, program understanding, maintenance, security analysis.

\subsubsection{Statistical Fault Localization}
Automatically localize faults using statistical reasoning.
\begin{itemize}
\item \textbf{Observation}: Program failures correlate with events that precede them. (Correlation does not imply causation, but can help find faults.)
\item \textbf{Tarantula Algorithm}: Assigns suspiciousness scores to program elements based on involvement in failing and passing test cases. Hue $= [0,1]$
	\begin{itemize}[itemsep=-1pt]
	\item Formula:	[\text{Suspiciousness}(line) = $\frac{  \frac{failed(line)}{total failed}  }{\frac{failed(line)}{total failed} + \frac{passed(line)}{total passed}}$	]
	\item Visualize using color coding (red: suspicious, green: safe).
	\end{itemize}
\item \textbf{Limitations}: Provides no direct information about root cause beyond identifying suspicious lines. Effectiveness depends on complexity of bug. Limited tool support in IDE integrations. Research shows such approaches provide only limited support to experts.
\end{itemize}

\subsubsection{Test-Case Reduction}
Reduce large failure-inducing inputs to minimal reproducible test cases. E.g. Mozilla BugAThon to simplify bug reports.
\begin{itemize}[itemsep=-1pt]
\item \textbf{Small Scope Hypothesis}:  “A high proportion of errors can be found by testing a program for all test inputs within some small scope''. Most bugs triggerable w. small, simple inputs. Can reduce the bug-inducing input.
\item \textbf{Test-case reduction tools}: reduce input element, apply (user-supplied) test oracle, check whether the bug is still being triggered
 If so, continue applying another reduction. If not, undoes change, attempts another reduction. \textbf{E.g.}: Using C-Reduce to minimize SQL queries that expose bugs in SQLite.
\item \textbf{Delta Debugging}:
	\begin{itemize}
	\item Systematically removes elements from the input while ensuring the bug is still triggered. Behaves like binary search but explores combinations of smaller blocks when binary search fails. Iteratively increases granularity if neither partitions nor complements trigger the bug.
	\item Simply: start reducing, consider granularity of n=2 (two halves). Consider partitions of input, and then complements (Whole input minus the specific partition). If any of partitions cause test to fail, continue reducing partition. Otherwise, reduce complement. If both do not work, increase granularity (create more partitions).
	\end{itemize}
\centerline{\includegraphics[width=1\linewidth]{deltaDebugging}}
Finding the global minimum would have an exponential complexity $(2^{|c \chi|})$, which is why Delta Debugging only
 gives us a local minimum: no subset of the reduced test case the test to fail, which is called 1-minimality.
\item \textbf{Reducer Characteristics}: Advantages: Simplifies debugging (easier to debug, analyze reason), aids in identifying duplicate bugs, and improves communication of bug. Challenges: Interestingness tests can be complex; inefficient for highly structured languages without hierarchical reduction techniques.
\end{itemize}

\subsubsection{Isolating Failure-Inducing Changes}
\begin{itemize}[itemsep=-1pt]
\item \textbf{Regression Bugs}: Features work in previous versions, fail in newer ones.
\item \textbf{Git Bisect}: Automates the process of identifying the commit that introduced a regression bug using binary search.
	\begin{itemize}
		\item Steps: Mark a known good version (\texttt{git bisect good}) and a bad version (\texttt{git bisect bad}). Test intermediate versions until the first bad commit is identified. Can be automated using scripts that build and test the program for each version.
	\end{itemize}
\item \textbf{Delta Debugging on Changes}: Applies delta debugging to individual patches within a commit. Granularities include hunks (consecutive differing lines) or entire changesets.
\end{itemize}

\subsubsection{Source Control (SCM)}
Primary output of a SWE is code! But source control $\neq$ git. 
\begin{itemize}[itemsep=-1pt]
\item \textbf{Questions to ask}: Who is allowed to view / change code? How are changes managed? dependencies managed? How does source control integrate with your tools? Branches, tags, merges, etc.
\item \textbf{SCM Tool Considerations}:
	\begin{itemize}
	\item \textbf{Centralized vs Decentralized}: Centralized systems have single repository, decentralized allow multiple repositories w. synchronization.
	\item \textbf{Dependency Management}: Tools (Maven, Gradle) help manage deps.
	\item \textbf{Scalability}: Ensure SCM tool can handle large repositories and teams.
	\item \textbf{Development Tool Support}: Integration with IDEs like VS, XCode.
	\item \textbf{Expertise/opinions in team}: Choose tools that align with whole team's expertise, preferences.
	\end{itemize}
\item \textbf{Good SCM Practices}:
	\begin{itemize}
	\item \textbf{Single Source of Truth}: Maintain single authoritative repository.
	\item \textbf{Consistency}: Consistent naming conventions (branches, tags, commits).
	\item \textbf{Small, Focused Changes}: Commit small, independent changes that are easier to review and revert if necessary.
	\item \textbf{Clarity}: Clear commit messages explaining what was changed and why.
	\item \textbf{Use Branches and Tags Appropriately}: Use branches for feature development and tags for releases.
	\item \textbf{Avoid Long-Lived Branches}: Merge branches frequently to reduce integration challenges.
	\item \textbf{Use Toolset for Managing Dependencies}: Leverage dependency management tools to handle external libraries.
	\end{itemize}
\end{itemize}

\subsubsection{Coding Style}
Consistent coding style improves readability, maintainability, collaboration. Also, probably need to revisit, read own code in the future.

\begin{itemize}
\item \textbf{Why Care About Style?}:
	\begin{itemize}
	\item Unnecessary changes in SCM due to formatting differences.
	\item Inconsistencies make code harder to read and understand.
	\item Differences in style can lead to confusion and inefficiency.
	\end{itemize}
\item \textbf{Key Elements of a Style Guide}:
	\begin{itemize}
	\item \textbf{Consistency $>>$ Optimality}: Consistent code is more important than "clever" or overly optimized code.
	\item \textbf{Focus on Clarity}: Code should be clear and unsurprising to readers.
	\item \textbf{Practicality $>>$ Clever/Pretty}: Practical solutions are preferred over clever or aesthetically pleasing ones.
	\item \textbf{Idioms and Practices}: Include guidelines on how tasks should be approached, not just formatting rules.
	\item \textbf{Autoformatters}: Use tools like Prettier, clang-format, or Black to automate formatting.
	\end{itemize}
\end{itemize}

\subsubsection{Versioning and Releases}
Depends on deploy method. Web services w. rolling releases, app stores, binaries, embed systems will be diff. in deployment, releases.

\subsubsection{Software Versioning}
Process of assigning unique identifiers to bundles of software. Identifiers help track, manage diff releases of software over time. Primary goals: 
\begin{itemize}[itemsep=-1pt]
\item Allow users to know which version of the software using, enable developers to identify version customers are using. 
\item Managing dependencies between software components.
\end{itemize}

\subsubsection{Semantic Versioning (SemVer)}
Semantic Versioning is a widely adopted versioning scheme, particularly for software with public APIs. It uses a three-part version number: \textbf{MAJOR.MINOR.PATCH}.
\begin{itemize}[itemsep=-1pt]
    \item \textbf{MAJOR version}: Increment: incompatible API changes are made.
    \item \textbf{MINOR version}: Increment: backward-compatible functionality is added.
    \item \textbf{PATCH version}: Increment: backward-compatible bug fixes.
    \item \textbf{Hyrum's Law}: With a sufficient number of users of an API, it does not matter what you promise in the contract: all observable behaviours of your system will be depended on by somebody. 
\end{itemize}
This system ensures clarity and consistency in communicating changes to users and developers.  However, these labels are slapped on by a human - no perfect guarantee it will not break your system!!

\subsubsection{Versioning Schemes}
\begin{itemize}
    \item \textbf{Commits as Identifiers}: Source control systems like Git assign unique hashes to commits (e.g., \texttt{2d54f09b}). \textbf{Pros}: Automatic, no additional effort required; useful for internal tracking. \textbf{Cons}: Not all commits correspond to release versions; difficult to remember and interpret.
    \item \textbf{Assigned Identifiers}: Includes code names (e.g., Android's "Lollipop," "Marshmallow") or version increments (e.g., v1, v2, v3).
 Can be combined with tags indicating release stages (e.g., alpha, beta, rc for release candidate). \textbf{Pros}: Easier to remember; code names aid branding and communication. \textbf{Cons}: Requires manual assignment and management.
 	\item \textbf{E.g. Versioning in Practice}: \textbf{Android}: Uses both numeric versions and dessert-themed code names (e.g., Android 9: Pie). Code names follow alphabetical order, aiding in identifying newer versions. \textbf{macOS}: Combines numeric versions with thematic names (e.g., macOS Big Sur, macOS Monterey). \textbf{Ubuntu}: Uses calendar-based versioning (YY.MM) and distinguishes Long-Term Support (LTS) releases.
	\item \textbf{Choosing Versioning Scheme}: The choice of versioning scheme depends on organizational needs, deployment strategies, release frequency, and user expectations. For example: web services with rolling releases may prefer frequent, small increments. Embedded systems/ safety-critical software may strict versioning/ long-term support. (Needs of marketing / users?)
	\item \textbf{Best branching strategy?}: Anything that gives a single source of truth, consistent, depends on your organization, deployment strategy, etc!
\end{itemize}

\subsubsection{Dependencies}
Probably most important, most difficult part of SWE. Dependencies: external components for software to function correctly, but not directly controlled by development team. Modern software: lot of dependencies! \\ \smallskip
\centerline{\includegraphics[width=0.9\linewidth]{dependencies}}
\begin{itemize}
    \item \textbf{Examples}: Libraries (e.g., React, TensorFlow), Build tools (e.g., Maven, Gradle), External services (e.g., APIs, cloud platforms).
    \item \textbf{Dependency Hell}: when multiple dependencies conflict, when outdated libraries cause integration issues. Modern software numerous dependencies, increasing complexity of dependency management.
    \item \textbf{Managing Dependencies} Strategies include: Embedding small or critical libraries directly into project, hosting medium-sized libraries in a private repository, using submodules or package managers for large, well-established libraries. Employing lockfiles and containers to ensure consistent runtime environments.
\end{itemize}

\subsubsection{Deprecation}
Process of orderly migration away from, eventual removal of obsolete systems. Planning, executing a transition strategy to minimize disruption.
\begin{itemize}
    \item \textbf{Why Deprecate?} Code / Dependencies are liability, not an asset. Maintaining outdated systems incurs operational costs. Legacy systems hinder the evolution of newer systems due to compatibility requirements. Deprecation allows organizations to focus resources, maintain and improve current systems. (Google: having multiple systems performing same function impedes evolution of newer system as still expected to maintain compatibility with old one).
	\item \textbf{Challenges}: Emotional attach. old systems. Difficulty in funding, executing deprecation efforts. High costs migrating to entirely new systems.
	\item \textbf{Types of Deprecation}: \textbf{Advisory Dep}: Informing users about deprecated features without enforcing immediate action. \textbf{Compulsory Dep}: Setting deadlines for removal and ensuring compliance through enforcement.
	\item \textbf{Deprecation During Design}: Designing systems with deprecation in mind can simplify future decommissioning. For example:
Planning for incremental replacement of components. Ensuring clear documentation and migration paths for users (give alternative).
\end{itemize}

\subsubsection{Code Review}
Before deploying new code, critical to ensure quality, correctness. Unreviewed code: lead to bugs, poor design decisions, maintainability issues. Mitigate risks by involving others in process of inspecting, improving code.
\begin{itemize}[itemsep=-1pt]
    \item \textbf{Risk Mitigation}: Code reviews catch defects early, formal reviews identifying up to 60\% of defects (comparatively - 30\% for testing).
    \item \textbf{Maintainability}: Studies: up to 75\% of code review comments address evolvability, maintainability, not just functionality.
    \item \textbf{Other Benefits}: Solicit feedback on code design, practices. Teaching, demonstrating coding methods. Raising awareness of product's state. Highlighting potential future problems.
  	\item \textbf{Challenges}: \textit{Speed vs. Thoroughness}: Review time increases exponentially with the size of the change, leading to diminishing returns on thoroughness. \textit{Balancing Priorities}: if speed or depth of review more important.
\end{itemize}

\subsubsection{Good Practices for Code Reviews}
To ensure effective code reviews, \textbf{authors} should:
\begin{itemize}[itemsep=-1pt]
    \item Keep reviews small and focused. Clear desc, annotate to guide reviewers.
    \item Choose appropriate reviewers, balance feedback quality w. team awareness.
    \item Open to feedback, implement suggested changes unless strong reason not.
    \item Reflect on feedback to improve future work.
\end{itemize}
\textbf{Reviewers} should:
\begin{itemize}[itemsep=-1pt]
    \item Push back on overly broad or poorly described changes.
    \item Focus on code, not person. Ask qns, point out problems, suggest solutions.
    \item Consider edge cases, failure scenarios, and future maintainability.
    \item Be responsive while balancing the severity and importance of changes.
\end{itemize}

\subsubsection{Software Quality Assurance (SQA)}

\subsubsection{Limitations of Testing}
\begin{itemize}
\item \textbf{Testing} widely used to identify bugs, but has significant limitations. Demonstrates presence of bugs but cannot guarantee their absence. Often time-consuming and resource-intensive. Edge cases and rare conditions may remain untested.
\item \textbf{Historical Context of Software Failures}: significant financial losses and even endangerment of human lives. E.g. Mars Climate Orbiter (1998), Knight Capital Group (2012) trading glitch loss \$440 million. Wannacry Ransomware Attack (2017). Boeing 737 MAX Crisis (2019).
\item \textbf{Static analysis, type systems} can help play a crucial role in improving software reliability and reducing the incidence of costly bugs (Fewer runtime errors).
\end{itemize}

\subsubsection{Static Analysis}
\begin{itemize}
\item \textbf{Static analysis}: examination of code without executing it. 
\item \textbf{Primary goals}: identifying potential errors, adherence to coding standards, optimizing performance.
\item \textbf{Why Static Analysis}: Early detection of bugs, reduce fix cost later in dev process. Improved code quality by enforcing best practices.
	Reduced debugging time through automated checks. Enhanced maintainability by ensuring consistent coding styles and fewer runtime errors.
\item \textbf{Types of Static Analysis}:
	\begin{itemize}
	\item \textbf{Linters and Style Checkers}: Focus on formatting and adherence to coding conventions without deeper semantic analysis.
	\item \textbf{Data-Flow Analysis}: Tracks the flow of data through a program to determine possible values at different points in the execution.
	\item \textbf{Control-Flow Analysis}: Analyze order of statement/function execution.
	\item \textbf{Type Checking}: Verifies that variables and expressions are used consistently according to their declared types. (Focus on this)
	\end{itemize}
\end{itemize}

\textbf{The Problem with Unsafe Languages}: E.g. Python, C, C++, and JavaScript, are inherently unsafe. These languages attempt to execute programs that may fail at runtime due to type mismatches or other errors.
\begin{itemize}
\item Python evaluates unsafe programs, throw runtime error when issues arise.
\item C and C++ place the burden of writing safe programs entirely on the programmer, often leading to manual errors.
\item Relying on manual approach to avoid errors proven unsuccessful.
\end{itemize}


\subsubsection{Type System, Role in Static Analysis}
\begin{itemize}
\item \textbf{A type system}: tractable syntactic method for proving absence of certain prog. behaviors by classifying phrases according to kinds of values they compute. (Benjamin Pierce, Types and Programming Languages)
\item Type systems serve as critical component of static analysis, detect type-related errors before runtime. A type system acts as a filter.
\item\textbf{Well-Typed Programs}: Adhere to type rules, allowed to execute. (e.g. $0 + 1$)
\item \textbf{Ill-Typed Programs}: Prog w. Type mismatch reject before execution (e.g. $false \; 0$ - cannot apply boolean to integer).
\item \textbf{Benefits of Type Systems}: 
	\begin{itemize}
	\item \textbf{Safety}: Prevents runtime errors caused by type mismatches.
	\item \textbf{Early Error Detection}: Identifies errors during the development phase rather than at runtime.
	\item \textbf{Improved Readability and Maintainability}: Clear type annotations make code easier to understand and modify.
	\end{itemize}
\end{itemize}

\subsection{$\lambda$-Calculus}
\begin{itemize}
\item \textbf{Prog. language} invented in 1930s by Alonzo Church and Stephen Cole Kleene.
\item "Core language" w. essential features to express all computation. (Lambda calculus is Turing complete). No redundancy, encode extra features as `syntactic sugar.'
\item Foundations of functional programming (e.g., Lisp, ML, Haskell).
\item Often used as a core language to study language theories. (Type systems, Scope and binding, Higher-order functions, Denotational semantics, Program equivalence)
\end{itemize}
    

\subsection{Overview: $\lambda$-Calculus as a Language}
\begin{itemize}
\item \textbf{Syntax} (How to write program): Keyword "$\lambda$" for defining functions.
\item \textbf{Semantics} (How to describe execution): \textit{reduction} as calculation rules.
\item Type system, Model theory (not covered)
\end{itemize}
    
\subsubsection{Syntax}
\begin{itemize}
\item $\lambda$-terms or $\lambda$-expressions: $ \text{(Terms)} \quad M, N ::= x \mid \lambda x. M \mid M N $
\item Lambda abstraction ($\lambda x.M$): Anonymous functions.
\item  Lambda application ($M N$). Examples:
	\begin{itemize}
	\item $ \texttt{int f(int x) \{ return x; \}} \Leftrightarrow \lambda x. x $
	\item $\texttt{f(3);} \Leftrightarrow (\lambda x. x) 3$
	\end{itemize}
\item \textbf{Pure/Extended $\lambda$-Calculus}: Pure $\lambda$-calculus only has $\lambda$-terms. Extended has added extra operations and data types. (E.g. $\lambda x. (x + 1), \quad \lambda z. (x + 2y + z)$)
\item \textbf{Conventions (Associativity)}
	\begin{itemize}
	\item \textbf{Body of $\lambda$ extends as far to the right as possible}: \\
	$\lambda x. M N \quad \text{means} \quad \lambda x. (M N), \quad \text{not} \quad (\lambda x. M) N$
	\item \textbf{Function applications are left-associative}: \\
	$M N P \quad \text{means} \quad (M N) P, \quad \text{not} \quad M (N P) $
	\item Examples: \\
	$(\lambda x. \lambda y. x - y) 5 3 \quad = \quad ((\lambda x. \lambda y. x - y) 5) 3$ \\
	$(\lambda f. \lambda x. f x) (\lambda x. x + 1) 2 \quad = \quad ((\lambda f. \lambda x. f x) (\lambda x. x + 1)) 2$
	\end{itemize}
\end{itemize}

\subsubsection{Higher-Order Functions}
\begin{itemize}
\item Functions as \textbf{return values}: $\lambda x. \lambda y. x - y$
\item Functions as \textbf{arguments}: $(\lambda f. \lambda x. f x) (\lambda x. x + 1) 2$
\item \textbf{Example}: Function Composition: \\
Given function $f$, return function $f \circ f: \quad \lambda f. \lambda x. f (f x)$
\end{itemize}
\centerline{\includegraphics[width=0.7\linewidth]{HOF}}

\subsubsection{Curried Functions}
\begin{itemize}
\item $\lambda$ abstraction is a function of one parameter.
\item $\lambda x. \lambda y. x - y \quad \leftrightarrow \texttt{int f(int x, int y) \{ return x - y; \}}$: \\
Computationally equivalent (can be transformed into each other).
\item \textbf{Curry}: Transform $(\lambda (x, y). x - y)$ to $(\lambda x. \lambda y. x - y)$. Uncurry: Reverse of Curry.
\end{itemize}

\subsubsection{Free and Bound Variables}
\begin{itemize}
\item E.g. $\lambda x. x + y$. $x$: Bound variable. $y$: Free variable.
\item Bound variables renameable ($\alpha$-equivalence): $\lambda x. (x + y) \Leftrightarrow  \lambda z. (z + y)$
\item Name of free variables matters: $\lambda x. (x + y) \neq \lambda x. (x + z)$
\item \textbf{Occurrences}: $ (\lambda \underline{x. x} + y) (x + 1):$ $x$ has both free and \underline{bound} occurrence.
\end{itemize}
    
\subsection{Processes in Lambda Calculus}
\begin{enumerate}
\item \textbf{Alpha Conversion}: If are applying two lambda expressions w. same variable name inside, change one of them to a new variable name. E.g. 
$(\lambda x.xx)(\lambda x.x) \rightarrow  (\lambda x.xx)(\lambda y.y)$
\item \textbf{Beta Reduction}: Basically just substitution. Process of calling lambda expression with input, and getting output. E.g. $(\lambda x.xy)z \implies zy$.
Substitution: $(\lambda x. M) N \to M[N/x] $. (`N replaces x in M'). Repeatedly apply the reduction rule to any sub-term. 
\item \textbf{Eta Conversion/Eta Reduction}: Special case reduction. Converts between $\lambda x.(f x)$ and $f$ whenever $x$ does not appear free in $f$. Basically means $\lambda x.(f x) = f$ if $f$ does not make use of $x$. E.g. $(\lambda x.(\lambda y.yy)x) = (\lambda y.yy)$
\end{enumerate}


\subsection{Formal Definitions}
\textbf{Terms}:
    \[
    M, N ::= x \mid \lambda x. M \mid M N
    \]
\begin{itemize}
\item \textbf{Set of free variables} in $M$: $fv(M)$
    \[
    fv(x) \coloneqq \{x\}, \quad fv(\lambda x. M) \coloneqq fv(M) \setminus \{x\}, \quad fv(M N) \coloneqq fv(M) \cup fv(N)
    \]
E.g.: $fv((\lambda x. x) x) = \{x\}, \quad fv((\lambda x. x + y) x) = \{x, y\}$

\item \textbf{Substitution}: 
\[ M[N/x]: N \text{ replaces } x \text{ in } M \]
- Defined by induction on terms:
    \[
    x[N/x] \coloneqq N, \quad y[N/x] \coloneqq y \quad \text{(if $y \neq x$)}
    \]
    \[
    (M P)[N/x] \coloneqq (M[N/x]) (P[N/x])
    \]
    \[
    (\lambda x. M)[N/x] \coloneqq \lambda x. M \quad \text{(Only replace free variables!)}
    \]
Substitution – Avoid Name Capture. Rename bound variables before substitution:
        \[
        (\lambda x. x - y)[x/y] = (\lambda z. z - y)[x/y] = \lambda z. z - x
        \]
\item \textbf{Alpha-equivalence}: $\lambda x. M = \lambda y. M[y/x], \quad \text{where } y \text{ is fresh.}$. Two terms are $\alpha$-equivalent iff one convertable to other purely by renaming bound variables.
\item \textbf{Beta-reduction} (substitution): $(\lambda x. M) N \to M[N/x] $. (`N replaces x in M'). \\
Repeatedly apply the reduction rule to any sub-term.
\end{itemize}

\subsubsection{Normal Form}
\begin{itemize}
\item \textbf{\underline{Red}ucible \underline{Ex}pression} ($\beta$-redex): A term of the form $(\lambda x. M) N$.
\item $\beta$-normal form: A term containing no $\beta$-redex. 
\item Stopping point: Cannot further apply $\beta$-reduction rules. \\
\centerline{ E.g. $(\lambda f. \lambda x. f (f x)) (\lambda y. y + 1) 2 \to 2 + 1 + 1 \quad (\beta\text{-normal form})$}
 Can further reduce to $4$ if reduction rules for $+$ are defined.
 \item E.g.: $\lambda x. \lambda y. x$ (normal), $(\lambda x. \lambda y. x) (\lambda z. z)$ and $\lambda x. (\lambda y. x) (\lambda z. z)$ (not normal)
\end{itemize}

\subsubsection{Confluence (Church-Rosser Property)}
\begin{itemize}
\item Terms can be evaluated in any order. Final result (if exists) is uniquely determined.
\item `When applying reduction rules to terms, the ordering in which the reductions are chosen does not make a difference to the eventual result.'
\item \textbf{Confluence Theorem}: $\text{For all } M, M_1, M_2, \text{ if } M \to^* M_1 \text{ and } M \to^* M_2, \text{ then } \exists M' \text{ such that } M_1 \to^* M' \text{ and } M_2 \to^* M'.$
\end{itemize}

\subsubsection{Non-Terminating Reduction}
\begin{itemize}
\item Some terms have no normal forms. 
\item E.g. $(\lambda x. x x) (\lambda x. x x) \to (\lambda x. x x) (\lambda x. x x) \to \dots$
\item Term may have both terminating and non terminating reduction sequences. E.g.
\end{itemize}
    \[
    (\lambda u. \lambda v. v) ((\lambda x. x x)(\lambda x. x x))
    \]
    \[
    \to \lambda v. v \quad \text{(Terminating)}
    \]
    \[
    \to (\lambda u. \lambda v. v) ((\lambda x. x x)(\lambda x. x x)) \to \dots \quad \text{(Non-terminating)}
    \]


\subsection{Reduction Strategies}
\begin{itemize}
\item \textbf{Normal-order reduction}: Choose the left-most, outer-most redex first.
    \[
    (\lambda u. \lambda v. v) ((\lambda x. x x)(\lambda x. x x)) \to \lambda v. v
    \]
\item Normal-order reduction will find a normal form if it exists.
\item \textbf{Applicative-order reduction}: Choose the left-most, inner-most redex first.
\[
    (\lambda u. \lambda v. v) ((\lambda x. x x)(\lambda x. x x)) \to (\lambda u. \lambda v. v) ((\lambda x. x x)(\lambda x. x x)) \to \dots
    \]
\end{itemize}

\subsection{Programming in $\lambda$-Calculus}
\begin{itemize}
\item \textbf{Encoding Boolean Values and Logical Operators}
	\[
    \text{True} \coloneqq \lambda x. \lambda y. x, \quad \text{False} \coloneqq \lambda x. \lambda y. y
    \]
        \[
        \text{Negation: not} \coloneqq \lambda b. b \, \text{False} \, \text{True}
        \]
        \[
        \text{Conjunction: and} \coloneqq \lambda b. \lambda b'. b \, b' \, \text{False}
        \]
        \[
        \text{Disjunction: or} \coloneqq \lambda b. \lambda b'. b \, \text{True} \, b'
        \]
        \[
        \text{Conditional: if b then M else N} \coloneqq b \, M \, N
        \]
        \[
        \text{Alternative negation: not'} \coloneqq \lambda b. \lambda x. \lambda y. b \, y \, x
        \]
\item \textbf{Church Numerals}:
- Encoding natural numbers:
    \[
    0 \coloneqq \lambda f. \lambda x. x, \quad 1 \coloneqq \lambda f. \lambda x. f \, x, \quad 2 \coloneqq \lambda f. \lambda x. f \, (f \, x)
    \]
    \[
    \text{General form: } n \coloneqq \lambda f. \lambda x. f^n \, x
    \]
    \[
    \text{Successor function: succ} \coloneqq \lambda n. \lambda f. \lambda x. f \, (n \, f \, x)
    \]
    \[
    \text{Example: succ n} \to \lambda f. \lambda x. f \, (n \, f \, x) = \lambda f. \lambda x. f^{n+1} \, x = n+1
    \]
    \[
    \text{Zero-check function: iszero} \coloneqq \lambda n. \lambda x. \lambda y. n \, (\lambda z. y) \, x
    \]
        \[
        \text{Addition: add} \coloneqq \lambda n. \lambda m. \lambda f. \lambda x. n \, f \, (m \, f \, x)
        \]
        \[
        \text{Multiplication: mult} \coloneqq \lambda n. \lambda m. \lambda f. n \, (m \, f)
        \]
\item \textbf{Pairs and Tuples}:
    \[
    \text{Pair encoding: } (M, N) \coloneqq \lambda f. f \, M \, N
    \]
    \[
    \text{Projection functions:} \pi_0 \coloneqq \lambda p. p \, (\lambda x. \lambda y. x), \quad \pi_1 \coloneqq \lambda p. p \, (\lambda x. \lambda y. y)
    \]
    \[
    \text{Tuple encoding: } (M_1, \dots, M_n) \coloneqq \lambda f. f \, M_1 \, \dots \, M_n
    \]
    \[
    \text{Projection functions:} \pi_i \coloneqq \lambda p. p \, (\lambda x_1. \dots \lambda x_n. x_i)
    \]
\item \textbf{Lists}: can be encoded using pairs. Operations on lists (e.g., head, tail, length) can be defined similarly. \textbf{Others}: Trees, Recursive functions etc.
\item \textbf{Main Points About $\lambda$-Calculus}: Succinct function expressions using $\lambda$.Bound variables can be renamed ($\alpha$-equivalence). Reduction via substitution ($\beta$-reduction). Can be extended with: Types (e.g., simply-typed $\lambda$-calculus), and side-effects (not covered here).
\end{itemize}

\subsection{Typed Lambda Calculus}
\begin{itemize}
\item Untyped $\lambda$-calculus is powerful but lacks safety guarantees.
\item Add type system ensures correctn, prevent certain errors (e.g., apply non-functions).
\item Provides formal framework for reasoning about programs. \textbf{type safety}:'Well-typed programs cannot go wrong.' Enables static analysis and optimization. 
\item \textbf{Type System}: Typing rules (assign types to terms), and Type safety (soundness of rules). Well-typed terms cannot go 
wrong.
\end{itemize}
    
\subsection{Simply-Typed Lambda Calculus (STLC)}
\begin{itemize}
\item Extends untyped $\lambda$-calculus with a simple type system. \textbf{Syntax}:
    \[
    \text{(Types)} \quad \tau, \sigma ::= T \mid \sigma \to \tau
    \]
    \[
    \text{(Terms)} \quad M, N ::= x \mid \lambda x : \tau. M \mid M \, N
    \]
\item Functions classified using argument and result types. $(\sigma \to \tau)$
\item $\to$ is right-associative: $\tau \to \tau \to \tau \text{ is } \tau \to (\tau \to \tau)$
\item \textbf{Typing Context ($\Gamma$)}: a set of typing assumptions  (to assign types to terms):
\begin{itemize}
\item  $[\Gamma \vdash M : \tau ]$ means `Under typing context $\Gamma$, term M is well-typed, has type $\tau$.'
\item Typing context $[\hspace{0.2em} \Gamma \hspace{0.2em} ::=\boldsymbol{\cdot} \mid \hspace{0.2em} \Gamma , x : \tau \hspace{0.5em}]$ (Empty context + extended context)
\item $\vdash$ (pronounced `turnstile'), also means `proves / entails'. (e.g. $\Gamma$ proves $x : \tau$).

\end{itemize}
\item \textbf{Typing (inference) rules} (to derive the typing judgement):
	\begin{itemize}
	\item \textit{Variable rule}: ($x$ is type $\tau$ under context where it is defined as $\tau$)
			\centerline{\includegraphics[width=0.5\linewidth]{variableRule}}
	\item \textit{Application rule}: (Type of fn. application determined by type of fn, and param).
        \[
        \frac{\Gamma \vdash M : T_1 \to T_2 \quad \Gamma \vdash N : T_1}{\Gamma \vdash M \, N : T_2}
        \]
	\item \textit{Abstraction rule}:
        \[
        \frac{\Gamma, x : T_1 \vdash M : T_2}{\Gamma \vdash \lambda x : T_1. M : T_1 \to T_2}
        \]
	\end{itemize}
\item \textbf{Typing Judgement}: a formal statement in type theory that asserts that a term (or expression) in a programming language has a specific type, under a given set of assumptions about the types of variables.
\end{itemize}
\centerline{\includegraphics[width=1\linewidth]{typingDerivations}}

\subsubsection{Soundness and Completeness}
\begin{itemize}
\item \textbf{Soundness}: A sound type system never accepts a program that can `go wrong.' No false positives: The language is type-safe. Ensures execution never reaches a "meaningless" state.
\item \textbf{Completeness}: A complete type system never rejects a program that cannot go wrong. No false negatives.
\item For any Turing-complete programming language, the set of programs that may "go wrong" is undecidable. Type systems cannot be both sound and complete.
\item In practice, we prioritize soundness and try to minimize false positives.
\end{itemize}
  


\subsubsection{Soundness in STLC}
\begin{itemize}
\item \textbf{Type Safety Theorem}: (Reduction of a well-typed term either diverges, or terminates in a value of the expected type.) Follows from two key lemmas.
    \[
    \text{For any } M, M' \text{ and } \tau, \text{ if } \cdot \vdash M : \tau \text{ and } M \to^* M', \text{ then:}
    \]
    \[
    \cdot \vdash M' : \tau, \quad \text{and either } M' \in \text{Values or } \exists M''. M' \to M''.
    \]
\item \textbf{Preservation (Subject Reduction)}: well-typed terms reduce only to well-typed terms of same type. ($\to$ means reduces to)
        \[
        \text{If } \cdot \vdash M : \tau \text{ and } M \to M', \text{ then } \cdot \vdash M' : \tau.
        \]
\item \textbf{Progress}: a well-typed term is either a value or can be reduced.
        \[
        \text{If } \cdot \vdash M : \tau, \text{ then either } M \in \text{Values or } \exists M'. M \to M'.
        \]
\end{itemize}

\subsubsection{Properties of STLC}
\begin{itemize}
\item \textbf{Strong Normalization Theorem}: Well-typed terms in STLC always terminate. 
E.g. $(\lambda x. x x) (\lambda x. x x) \text{ cannot be assigned a type.}$
\item \textbf{Limitation: Not Complete}: Some valid programs may be rejected by type system.
    \[
    (\lambda x. (x (\lambda y. y)) (x 3)) (\lambda z. z)
    \]
- Cannot find types $\sigma, \tau$ such that: $[ x : \sigma \vdash (x (\lambda y. y)) (x 3) : \tau ]$
 
- However, reduces successfully: $[ ((\lambda z. z) (\lambda y. y)) ((\lambda z. z) 3) \to (\lambda y. y) 3 \to 3 ] $
\end{itemize}

\centerline{\includegraphics[width=1\linewidth]{STLC}}



\subsubsection{Extending STLC}
Use STLC as a foundation for understanding other common language constructs.  
\begin{itemize}[itemsep=0pt]
\item Extend the syntax (types \& terms), operational semantics (reduction rules)
\item Extend the type system (typing rules), soundness proof (new proof cases)
\item \textbf{Adding Product Types ($\sigma \times \tau$)}:
	\begin{itemize}
	\item Represent structured data, combining two values into a pair. Logical intuition: To make a $\sigma \times \tau$, we need both a $\sigma$ and a $\tau$. Operations: Construct pairs, Extract components using projections, E.g.: Swapping components of a pair.
	\end{itemize}
\item \textbf{Sum Types ($\sigma + \tau$)}: 
	\begin{itemize}
	\item Represent choices between alternatives. Logical intuition: To make a $\sigma + \tau$, we need either a $\sigma$ or a $\tau$. Operations: Inject values into the sum type (left or right). Handle alternatives using case analysis. Example: Encoding booleans as $ \text{true} + \text{false} $.
	\end{itemize}
\item  Extended STLC includes functions, products, and sums.
\item Products ($\sigma \times \tau$) and sums ($\sigma + \tau$) are logical duals.
\item These constructs model common programming patterns like structs, unions, and enums.
\end{itemize}

 Static analysis. Property-based testing. Differential testing.

\subsection{Static Analysis: A High-Level Perspective}
Static analysis involves reasoning about code without executing it. It encompasses various techniques, including:
\begin{itemize}
\item \textbf{Type Checkers}: Ensure variables used consistently w. declared types (Topic 8).
\item \textbf{Linters and Style Checkers}: Enforce coding standards, formatting violations.
\item \textbf{Data-Flow Analysis}: Tracks flow of data through program to identify issues.
\item \textbf{Control-Flow Analysis}: Analyzes the possible execution paths of a program.
\end{itemize}
    

\subsubsection{Static Analysis Tools in Practice}
Several tools developed to detect style violations and potential bugs in programs. E.g. \textbf{SpotBugs}: Detects common bug patterns in Java programs, \textbf{PMD}: Focuses on code quality and detects issues like overly complex methods or unused variables. 
\begin{itemize}
\item These tools aim to improve code quality but often face challenges such as false positives, false negatives, and integration difficulties.
\end{itemize}
    

\subsubsection{Soundness vs. Completeness in Static Analysis}
\begin{itemize}
\item \textbf{Completeness}: If tool reports an issue, guaranteed to be true (no false positives).
\item \textbf{Soundness}: If an issue exists, the tool will always report it (no false negatives).
\end{itemize}
Static analysis tools balance the two key properties. Achieving both is undecidable (no algorithm can definitively determine a "yes" or "no" answer for all possible inputs) in practice, leading to trade-offs between the two.

\subsubsection{Challenges with Static Analysis}
Tools face several challenges such as slow execution times, false positives (incorrectly flagged issues) and false negatives (missed bugs), limited applicability to complex features not modeled by tool. Other more practical challenges include:
\begin{itemize}
\item Warnings that are not actionable or lack sufficient guidance for resolution.
\item Difficulty integrating into developers' workflows. See \textbf{Case Studies}:
\end{itemize}
\begin{itemize}
\item  \textbf{Facebook's Infer Deployment}:
	\begin{itemize}
	\item Initial deployment: running Infer nightly on the entire codebase generated 2,500 alarms, but developers ignored most due to workflow disruptions.
	\item Subsequent deployment: Integrating Infer during code reviews (on diffs) increased fix rates to over 70\%.
	\end{itemize}
\item \textbf{Google's FindBugs Deployment}:
	\begin{itemize}
	\item Attempt 1: Centralized bug dashboard outside developers' workflows not used.
	\item Attempt 2: Manually filing bug reports for FindBugs issues resulted in only 16\% of reviewed warnings being fixed.
	\item Attempt 3: Integrating FindBugs into code reviews improved adoption but faced issues with false positives and inconsistent views.
	\end{itemize}
\end{itemize}
Case studies show \textbf{timeliness of reports} crucial; developers more likely to address issues when integrated into current tasks. Reporting only new issues (on diffs) reduces noise and improves developer responsiveness.

\subsubsection{Key Principles for Successful Static Analysis}
To maximize the effectiveness of static analysis:
\begin{itemize}
\item Focus on developer happiness, ensure understandable, actionable outputs.
\item Maintain low false positive rate (less than 10\%) to build trust in the tool.
\item Integrate seamlessly into developers' workflows (e.g., during code reviews).
\item Provide timely feedback to ensure relevance to the current task.
\item Successful static analysis platforms, like Google's Tricorder, focus on delivering valuable results that align with developer workflows.
\end{itemize}



\subsection{Automated Testing}
Automated testing is where testing tool automatically generates test input and/or applies an automatically-constructed test oracle.

\begin{itemize}
\item Automated testing is preferred for complex systems (E.g. OS, compilers, DBMS), as manually written tests may miss bugs or may be incomplete.
\item Example-based testing is simpler but less comprehensive than property-based testing.
\item \textbf{Black, Grey, White-box Approaches}: No standard def
	\begin{itemize}
	\item Black-box: no internal information (e.g., works on the binary only)
	\item White-box: internal information (heavyweight approaches, systematically analyze program)
	\item Grey-box: some internal information (e.g., coverage)
	\end{itemize}
\end{itemize}

\subsection{Automated Testing Approaches}
\subsubsection{Property-Based Testing}
Property-based testing involves specifying properties that the system should satisfy. The testing framework generates test inputs to check if these properties hold. (Test framework tries to find counterexample to break property / falsify it).

\begin{itemize}
\item \textbf{Example Property}: For a function $ \texttt{Math.abs(x)} $, the property is $ |x| \geq 0 $. (Using jqwik, java property based testing framework).
\begin{verbatim}
@Property
void positiveAbs(@ForAll int val) {
    assertTrue(Math.abs(val) >= 0);
}
// arg0: -2147483648 is input that falsifies property.
\end{verbatim}
\item \textbf{Advantages}: Provides greater confidence than example-based unit tests. Useful for communicating specifications.
\item \textbf{Challenges}: Requires creativity to define meaningful properties.
\item Property based testing frameworks also allow constraining of input domain. Also provide ways to adapt existing generators or create new ones. Also provide shrinkers (test-input reduction tools).
\item \textbf{In practice}: used primarily for testing components of complex systems.  Especially in `high-leverage'
scenarios, where properties are easy to identify and test. 
\item \textbf{Example}: property based testing on Google Translate, properties include round-trip translation similarity, idempotency (output deterministic same result for same input), word count etc.
\end{itemize}

\subsubsection{Differential Testing}
Differential testing compares outputs from multiple implementations or versions of the same functionality, or a simple reference engine, to detect discrepancies.
\begin{itemize}
\item \textbf{Approach}: Common input, compare outputs of diff. versions, configurations, or implementations. If outputs differ, at least one system may be affected by bug.
\item \textbf{Comparing Versions}: Check behavior against known-working base version (`golden version'), form of regression testing. Though change might be intended.
\item \textbf{Comparing Configurations}: E.g. different optimization levels, different engines.
\item \textbf{Comparing against Reference Engine}: E.g. mocked component.
\item \textbf{Comparing Implementations}: For many important software systems, multiple (competing 
implementations exist).  If sufficiently similar, they can be used for differential testing. (E.g. DB engines, XML processors, compilers.)
\item \textbf{Challenges}: Small overlap in functionality between system can produce false alarms, may miss out common bugs (e.g. stem from common library used), non deterministic output.
\end{itemize}


\subsubsection{Metamorphic Testing}
Use source test case and its result to generate \textbf{follow-up test cases}, where differential testing might be inapplicable. Rely on \textbf{metamorphic relations} to infer expected results. Special case of property based testing. Black box approach.

\begin{itemize}
\item \textbf{Example Metamorphic Relation}: $ \sin(\pi - x) = \sin(x) $. Test both $0.5$, $\pi - 0.5$.
\item E.g.  Test a sorting function whether relative order of sorted elements maintained when an element is removed from an input array. First result acts as oracle for second result.
\item E.g. EMI (Equivalence Modulo Inputs) for Compiler testing, create programs that are equivalent only for a given input. Mutate unexecuted part of program running input I, and check if same output for I. Finds bugs as compiler optimizes across both executed and unexecuted parts.
\item \textbf{Strengths}: Avoids need for multiple systems (unlike differential testing). Simple, effective if metamorphic relation is straightforward.
\item  \textbf{Weaknesses}: Finding bug-revealing metamorphic relations can be challenging.
\item E.g. M. testing on Google Translate: Property: Exchange Nouns Preserves Sentence Structure.
\end{itemize}
 

\subsubsection{Fuzzing}
Fuzzing involves feeding random or semi-random inputs to a program to uncover crashes or other unexpected behaviors.

\begin{itemize}
\item \textbf{Black-box Fuzzing}: Sends random inputs without knowledge of the program's internals. Simple, efficient test-case generation, but unlikely to uncover deep bugs especially if input format complex. (e.g. image parsers), as inputs probably invalid. (Partly addressed by grammar-based fuzzing).
\item \textbf{Mutation-based Fuzzing}: mutate existing inputs over random inputs. Higher quality inputs with diverse input seed corpus, but requires seed inputs to mutate.
\item \textbf{White-box Fuzzing}:  White-box Fuzzing Techniques are often powered by constraint 
solvers and symbolic execution. Uses symbolic execution to systematically explore paths in the program.
\item \textbf{Grey-box Fuzzing}: Instruments the program to collect code coverage and guide input generation.  (E.g.  American Fuzzy Lop (AFL), AFL++)
	\begin{itemize}
	\item  Balance the benefits of black-box fuzzing (efficient test case generation) and white-box fuzzing (high-quality inputs). 
	\item For each mutated input, check whether it resulted in a gain of code coverage (or code coverage pattern), if so, mutate further.
	\end{itemize}
\item \textbf{Fuzzing Test Oracles}:  Crashes, hangs (pre-set thresholds), and dynamic analysis tools (detect issues e.g. race conditions, undefined behaviours).
\end{itemize}

\subsubsection{Constraint Solvers}

Constraint solvers: powerful tools used in various swe techniques, symbolic execution, white-box fuzzing, hardware /software verification, program synthesis, program repair. Work by analyzing formulas to determine whether they are satisfiable (SAT) or unsatisfiable (UNSAT). If a formula is satisfiable, the solver provides a model—a valuation of variables that satisfies the formula. \\

\textbf{Types of Solvers}:
\begin{itemize}
\item \textbf{SAT Solvers}: Solve propositional formulas with Boolean variables. For example, given the formula $(A \lor B) \land C$, a SAT solver might return $A = \text{true}, B = \text{false}, C = \text{true}$. (NP complete, but modern solvers efficient)
\item \textbf{SMT Solvers}: Extend SAT solvers to handle more complex theories, such as linear integer arithmetic. (Satisfiability Modulo Theories) For example, given the formula $(a > 5) \land (a \neq 6)$, an SMT solver might return $a = 7$. (NP hard)
\item E.g. Z3 is a widely-used SMT solver developed by Microsoft. It supports various theories and is accessible via APIs in multiple programming languages.
\item \textbf{Challenges}: Solving SAT problems is NP-complete, SMT problems often NP-hard / undecidable for certain theories. Performance can degrade with complex path conditions or large formulas.
\end{itemize}

\subsubsection{Symbolic Execution}
Technique for systematically exploring all possible execution paths of a program. Instead of using concrete inputs, symbolic execution uses symbolic values to represent inputs and \textit{tracks constraints (path conditions)} on these values. A constraint solver is then used to determine whether a given path is feasible.
\begin{itemize}
\item \textbf{Key Idea}: Execute the program symbolically, maintaining a symbolic state ($\sigma$) that maps variables to symbolic expressions. Use a theorem solver to check the feasibility of path conditions and generate test cases for different execution paths.
\item A path condition encodes all branch decisions on the symbolic variables taken so far. Path conditions can be 
feasible or infeasible.

\item \textbf{Execution Tree}: An execution tree represents all possible execution paths of a program. Each branch corresponds to a decision based on symbolic variables. Path conditions encode the constraints on symbolic variables for each path. For example:
        \[
        \alpha \land (\beta < 5) \land (\neg\alpha \land \gamma)
        \]
Infeasible paths are pruned using an SMT solver.
\item E.g. KLEE Tool: popular symbolic execution tool for C programs built on the LLVM compiler framework. Running KLEE generates test cases that explore all feasible paths through the program.
\item \textbf{Strengths}: Systematically generation of inputs to cover different execution paths.
 \item \textbf{Challenges}: Exponential Path Explosion, difficulty in Environment Modeling (library calls, external interacts), infinite Loops, Heap Modeling (Representing heap memory symbolically can be computationally expensive), Solver Performance (Complex path conditions can strain solver performance).
\end{itemize}




\subsubsection{Automated Testing \& Static Analysis}
Static analysis and automated testing are complementary approaches to improving software quality. While static analysis provides insights without execution, automated testing validates behavior under various conditions. Both require careful integration into developer workflows to ensure they deliver value without disrupting productivity.
